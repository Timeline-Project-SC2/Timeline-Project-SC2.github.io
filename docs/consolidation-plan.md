консолидация выполнена в PR #304 по инвентарной карте шага 0; итог и

## 1. Что такое консолидация и зачем она нужна

PR #302 **разрезал** монолиты на файлы ≤ 200 строк, но без минимального
размера файла. Получилась гиперфрагментация: агент читает тему не за
1 файл, а цепочкой «хаб → индекс → паспорт → регистры → заметка», где
значимая часть текста — повторяющиеся шапки «Назад». **Консолидация —
обратная операция там, где резка зашла слишком далеко:** однотемные
микрофайлы склеиваются обратно в плотный документ 80–200 строк, сироты и
дубли убираются, разорванные «-1/-2» части сшиваются. Цель измеряется не
красотой дерева, а ценой чтения: тема целиком за 1–2 открытия файла,
ноль файлов без входящих ссылок, ноль прыжков `H1 → H3`.

## 3. Возражения критика: где план аудита рискован

1. **Сворачивание всех регистров в секции `plan.md` отменяет модель
   владельца** (5 типов данных на этап), а не чинит её реализацию.
   Принят гибрид (решение §6.1): пустые и не начатые этапы файлов-регистров
   не имеют; пока регистр короче ~60 строк, он живёт секцией в `plan.md`,
   вырос или стал самостоятельно цитируемым — выносится в отдельный файл.
2. **Цели склеек впритык (180–190 строк) не оставляют запаса роста:**
   первая же запись волны заставит резать заново. Цель — 120–170 строк,
   190 — только для замороженных исторических отчётов.
3. **Общий допуск «+50» отклонён** (решение §6.2): 200 строк — норма для
   системных инструкций проекта и схожее правило для остальных файлов.
   Неделимый контекст больше 200 строк не превышает лимит молча: он
   точечно раскладывается по конкретной среде (этап, домен, папка) по
   смысловой границе, а не по числу строк; точечное исключение сверх 200 —
   только как отдельное решение в конкретной задаче, с записью причины.
4. **Переименования ломают ссылки вне `docs/`.** Корневой `AGENTS.md`
   ссылается на `waves/stage-6-dx.md` §7, код — на номера `§17.*`;
   `CHANGELOG.md` и старые PR — на прежние пути. Склейка волн и переезд
   файлов между этапами требуют сначала `grep` по всему репозиторию,
   а для путей со внешними ссылками — редирект-хаба, а не перемещения.
5. **Сшивать отменённый `unit-ly.md` (§17.23) с его отменой можно только
   с баннером «ОТМЕНЕНО» в начале файла**, иначе риск чтения отменённых
   чисел как действующих выше, чем риск раздельного чтения.
6. **Оценка «358 → 115–125 файлов» в аудите не доказана:** таблицы
   покрывают часть папок, полной инвентарной карты «файл → куда» нет.
   Без неё исполнитель снова будет резать по впечатлению — это и есть
   ошибка первого промпта, повторённая наоборот.

## 4. Порядок консолидации: три очереди вместо одного рывка

| Очередь | Содержание | Риск | Решение владельца |
|---|---|---|---|
| **P0 — гигиена без перемещений** | Сироты в оглавления, двойные `H1`, пустые таблицы, дублирующиеся п. 6 в `README.md`, устаревшее `L0…L9`, сортировка `notes/README` по логике чтения | Нулевой: правится текст на месте | Не требуется |
| **P1 — склейки внутри папки** | Пары дублей (`*-note.md`), части `-1/-2`, микрозаметки в профильный файл того же этапа; цели 120–170 строк | Средний: только внутриконтекстные ссылки | Требуется карта склеек |
| **P2 — модель и переезды** | Регистры-гибрид (§6.1), переезды между этапами в контексте конкретной задачи (§6.3), точечные исключения сверх 200 строк (§6.2) | Высокий: ссылки из кода, PR, `AGENTS.md` | Решения §6 приняты; каждый переезд обосновывается в карте своей задачи |

Запускать всё одним промптом в один PR нельзя: P0 утонет в диффе P1/P2,
и откатить плохую склейку будет нечем. Каждая очередь — свой PR, свой
красный/зелёный гейт (см. [методику](ai-workflow.md): тесты до кода —
здесь «тесты» это `check_docs`, граф ссылок и счётчики метража).

## 6. Решения владельца (приняты 26.10.2026)

1. **Регистры этапов — гибрид.** По умолчанию `ОШИБКИ`, `БАГИ`, `РЕШЕНИЯ`
   и `TODO` живут секциями `##` в паспорте этапа `plan.md`. В отдельный
   файл регистр выносится, когда сама секция перерастает ~60 строк или
   на неё нужно ссылаться самостоятельно из других этапов и регистров.
   Пустым и не начатым этапам файлы-регистры не заводятся. Систематические
   ошибки по-прежнему уходят в безлимитный `registers/errors-systemic.md`.
2. **Лимит строк — 200 как норма точечного контекста.** Исходя из правила
   «200 строк под системные инструкции к проекту»: управляющие файлы
   (`AGENTS.md`, доменные инструкции, правила и хабы) проектируются до
   200 строк, и для остальных документов действует схожее правило. Смысл
   не в механической резке, а в **кратной диверсификации — многоуровневом
   контексте по ссылкам**: системные инструкции → паспорт среды → паспорт
   темы → точечный файл → приложение. Контекст хранится точечно в своей
   конкретной среде (этап, домен, папка), одним цельным файлом на тему.
   Общего допуска «+50» нет; неделимый остаток сверх 200 не прячется в
   файл, а либо делится по смысловой границе на точечные файлы среды,
   либо оформляется точечным исключением с причиной в конкретной задаче.
   **Глубина чтения (чтобы уровни не превратились в обход всего дерева):**
   глубина 0 — файл, названный в задаче, и обязательный SSoT домена;
   глубина 1 — обязательные ссылки из него; глубина 2 — **один** профильный
   документ, выбранный из хаба по теме задачи (не все соседи по хабу);
   глубина 3 — приложение к нему под конкретный пункт плана. Дальше
   глубины 3 хода нет. Из одного файла разрешено не более 3 переходов по
   **семантическим** ссылкам («контракт», «источник чисел», «гейт»);
   навигационные ссылки («Назад», индексы, «см. также») чтением не
   являются и углубления не разрешают, обратные ссылки не читаются.
   Бюджет задачи: стартовый набор — не более 6 документов и не более
   1 000 строк документации суммарно (4 уровня × 200 + резерв; код и данные
   задачи в бюджет не входят, машинный подсчёт метража и графа ссылок
   чтением не считается). Хаб сначала читается только по оглавлению.
   Если нужен 7-й документ, глубина 4 или бюджет превышен — **стоп**:
   агент показывает таблицу «файл → глубина → зачем открыл → что извлёк»,
   задаёт вопрос или оформляет выжимку в файл задачи, а не продолжает
   обход. Один файл дважды не перечитывается; история и регистры читаются
   только при совпадении симптома или ID, а не профилактически.
3. **Переезды между этапами — разрешены в контексте конкретной задачи.**
   Не «перетасовать всё дерево», а: в инвентарной карте у каждого переезда
   есть строка-обоснование (какой задаче он нужен, почему файл лежит не
   в своём этапе по предмету), проверены `grep`-ом ссылки со всего
   репозитория (код, `AGENTS.md`, `CHANGELOG.md`, старые PR), а на старом
   пути остаётся редирект-хаб, если на него есть внешние ссылки.

Что это меняет для исполнителя: вопросов на шаге 0 больше нет, решения
вшиты в промпт §5. Разрешён только шаг 0 (инвентарная карта и базовые
замеры) до отдельного «да» владельца по карте — именно отсутствие этих
решений и карты в первом промпте породило 160 микрофайлов.
