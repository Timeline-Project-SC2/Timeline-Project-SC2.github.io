# Инструкция для Воркера при параллельной сплит-разработке (Split-Work / Tri-Agent Wave)

Настоящий документ управляет работой агента-исполнителя (**Воркера 1, 2 или 3**), когда пользователь явно направляет задачу по методу параллельного сплита (`Split-Work`), координируемому Гайдлайнером (`docs/agents_task_orchestration/agents_task_orchestration.md`).

---

## 1. Соотношение со стандартным `AGENTS.md`

При работе по настоящей инструкции:
- **Сохраняют полную силу** все инженерные и качественные требования базового [`AGENTS.md`](../../AGENTS.md): русский язык интерфейса/комментариев/ответов, запрет на легаси в `src/`, инварианты `docs/CHANGE_REQUEST_PLAN.md` (И-1…И-6), обязательный `git commit + git push` после каждого завершённого шага и полный прогон проверок перед финишем.
- **Переопределяются настоящим документом** правила владения файлами, порядок первого коммита на Шаге 0 и правила обновления общих файлов документации (`docs/HANDOFF.md`, `CHANGELOG.md`).

---

## 2. Позиция Воркера в звене (Role & Boundary Card)

В сплит-режиме ты работаешь **не один**, а в параллельной тройке агентов (`Воркер 1`, `Воркер 2`, `Воркер 3`), каждый из которых одновременно выполняет свою часть волны в отдельной ветке, ответвлённой от общего `main`.

Из этого следуют три обязательных правила поведения:
1. **Не ищи в своей ветке код соседних воркеров текущей волны.** Соседние агенты работают параллельно с тобой, их ветки ещё не слиты в `main`.
2. **Не пиши часть работы за соседнего воркера.** Даже если ты видишь в его карточке знакомую задачу, она выполняется в его ветке; дублирование приведёт к гарантированному конфликту при слиянии в `main`.
3. **Соблюдай контракт на стыках символ в символ (`Interface-First`).** Если в твоём промпте задан блок `Контракт на стыках`, экспортируемые имена типов, функций и полей должны совпадать с ним до буквы.

---

## 3. Жёсткий контур владения файлами (`OWNED_FILES` vs `FORBIDDEN_FILES`)

В каждом сплит-промпте заданы два списка:
- **`РАЗРЕШЕНО ПРАВИТЬ (OWNED_FILES)`** — исчерпывающий перечень файлов, которые твоя ветка имеет право создавать, изменять или удалять.
- **`ЗАПРЕЩЕНО ТРОГАТЬ (FORBIDDEN_FILES)`** — все остальные файлы репозитория.

### Обязательная самопроверка перед каждым коммитом
Перед каждым `git commit` и перед финальной сдачей PR выполни:

```bash
git status --short
git diff --name-only origin/main...HEAD
```

- Каждый путь в выводе `git diff --name-only origin/main...HEAD` **обязан** входить в твой список `РАЗРЕШЕНО ПРАВИТЬ`.
- Если при прогоне тестов (например, Python-тестов синхронизации или генераторов) был затронут файл вне твоего списка, немедленно восстанови его:

```bash
git checkout -- <путь_к_чужому_файлу>
```

---

## 4. Правило «Сохранность работы» в сплит-режиме (без конфликтов в `HANDOFF.md`)

В стандартном одиночном режиме агенты часто делают первый WIP-коммит и финальный коммит в `docs/HANDOFF.md` и `CHANGELOG.md`. В параллельной волне из 3 воркеров это создаёт 100 %-ный конфликт слияния в `main`.

Поэтому в режиме `Split-Work` действует следующий порядок:

1. **Для Воркеров 1 и 2 (кодовые потоки):**
   - **ЗАПРЕЩЕНО** изменять `docs/HANDOFF.md`, `CHANGELOG.md` и `docs/PREPARATION_PLAN.md` (эту обязанность из `AGENTS.md` за всю волну централизованно закрывает **Воркер 3**).
   - **Шаг 0 (проверка контура сохранения):** первый содержательный коммит делается **сразу в свой целевой файл из `РАЗРЕШЕНО ПРАВИТЬ`** (например, объявление экспортируемых интерфейсов/констант Шага 1 или завершённый Шаг 1), после чего сразу выполняется:

```bash
git push -u origin HEAD
git rev-parse HEAD origin/$(git branch --show-current)
git status --short
```

   - Как только `HEAD` равен `origin/<ветка>`, открой WIP PR (`gh pr create`) и продолжай делать `git commit + git push` после каждого следующего шага.
2. **Для Воркера 3 (поток документации и планов):**
   - В список `РАЗРЕШЕНО ПРАВИТЬ` входят именно `docs/PREPARATION_PLAN.md`, `docs/HANDOFF.md`, `CHANGELOG.md` (и иные явно указанные документы).
   - Воркеру 3 **запрещено** трогать любые файлы кода и тестов (`site/*`, `src/*`, `tools/*`, `tests/*`).

## 5. Дисциплина экономии контекстного окна Воркера

Чтобы не исчерпать контекстное окно до финального пуша и зелёного CI:
1. **Не читай крупные файлы целиком.** Вместо полного чтения файла на 1 000+ строк используй точечный поиск:
   - `grep -n "имяФункции" <файл>`
   - `sed -n '120,200p' <файл>`
2. **Подавляй лишний шум в терминале.** При установке временных пакетов линтера/компилятора используй флаги `--no-save --no-package-lock --no-audit --no-fund --silent` и проверяй после них `git status --short`, чтобы `package.json` не оказался случайно изменён.
3. **Не откладывай `git push` на конец сессии.** Завершил шаг → проверил `npx tsc --noEmit` → закоммитил свои файлы → сразу `git push` и сверка `git rev-parse HEAD origin/<ветка>`.

## 6. Чек-лист перед завершением работы и формат отчёта Гайдлайнеру

Перед остановкой перед merge убедись, что:
1. `git diff --name-only origin/main...HEAD` содержит **только** твои файлы из `РАЗРЕШЕНО ПРАВИТЬ`.
2. Все применимые локальные проверки зелёные:
   - `npx tsc --noEmit`
   - `npx eslint site src`
   - `npm run build`
   - `npm run verify:publish` и `npm run verify:contract`
   - `node --test`
   - `git diff --check`
3. Ветка запушена (`HEAD == origin/<ветка>`), открыт PR и все 4 проверки `check.yml` на PR имеют статус `pass` (`gh pr checks <N>`).
4. **Остановись строго перед merge** (слияние всей волны в `main` координирует пользователь с Гайдлайнером).

### Формат финального ответа Воркера (компактная сводка на 10–15 строк)
В конце сессии выдай короткий структурированный отчёт, который пользователь сможет переслать Гайдлайнеру без перегрузки контекста:
- **Позиция и PR:** `Воркер [N] · Волна [Код] · PR #[Номер] · Ветка <имя_ветки> (HEAD == origin)`
- **Затронутые файлы (`Zero File Overlap`):** точный список из `git diff --name-only origin/main...HEAD`
- **Таблица шагов:** `Шаг | Коммит | Краткая суть`
- **Результаты проверок:** `tsc`, `eslint`, `build`, `node --test`, `verify:publish`, `check.yml (4/4 pass)`
- **Готовность к merge:** `Стоп перед merge — готов к приёмке Гайдлайнером`.

---

## 7. Ответы на спецификации поиска Гайдлайнера (правило О-5)

Гайдлайнер не работает с кодом напрямую. Отдельно от карточки (или внутри неё) он может
прислать **спецификацию поиска** — точечный запрос фактов о репозитории. Это полноценное
задание, отвечай по следующей форме:

1. Ищи строго в указанной области (пути и маски файлов); не расширяй её без вопроса.
2. Возвращай только запрошенный формат: `путь:строка`, сигнатура символа, «да/нет»,
   короткая таблица. Дампы файлов, полные логи и простыни кода не присылай.
3. Каждый факт — с привязкой к файлу и номеру строки; если что-то не найдено, скажи это
   явно, не домысливай и не подменяй соседним символом.
4. Чистый вопрос правок не требует и коммитом не закрепляется. Если спецификация вскрыла
   необходимость изменения кода — остановись и верни Гайдлайнеру найденное + предложение,
   не начинай правку без карточки.
