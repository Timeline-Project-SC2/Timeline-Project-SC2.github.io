# Волна `ADM`: data-only админка на GitHub Issues и Actions

> **Статус:** архитектура принята владельцем 26.10.2026; [`ADM-0`](../wave_cards/ADM-0-execution.md)
> принята `PASS` с оговорками. Текущий гейт — [`ADM-0P`](../wave_cards/ADM-0P.md):
> профили planet-generation входят в v1, но `ADM-1` не выдаётся до её отчёта.
> Назад: [оркестрация](../README.md) · [протокол О-1…О-5](protocol.md).

## 1. Решение и границы

- Весь контур остаётся внутри GitHub: статический редактор на Pages, служебное issue как
  транспорт и подтверждение, GitHub Actions как доверенный исполнитель, существующий Pages
  deploy как публикация.
- Внешний backend, serverless-платформа, собственная OAuth/API, БД, отдельный сервер и
  ПК-исполнители запрещены.
- В браузере нет токенов, секретов, сессии и права записи. Браузер только редактирует
  публичные данные и формирует пакет.
- Редактируются только разрешённые CSV/JSON-данные: точки, координаты, связи, границы и
  профили. Код, конфигурация, workflow и служебные источники в пакет попасть не могут.
- После переключения GitHub — единственный источник истины. Старый Sheets-sync не имеет
  права записи и не может перезаписать результат админки.

## 2. Поток публикации

1. Кнопка «Доступ администратора» открывает статический редактор. Pages не определяет
   права пользователя и не изображает вход: авторизация подтверждается только позже,
   по фактическому аккаунту автора issue.
2. Редактор загружает опубликованный снимок данных и его `baseRevision`, ведёт черновик,
   показывает человекочитаемую сводку изменений и локальные ошибки формы.
3. «Отправить результат» открывает предзаполненное служебное issue: сводка плюс ровно
   один версионированный блок пакета операций с `baseRevision`.
4. Администратор проверяет сводку на GitHub и нажимает **Submit new issue**. Это второй
   клик и единственное подтверждение личности/намерения.
5. Workflow на `issues.opened` проверяет автора, роль, протокол, схемы, связи и ревизию.
6. При успехе создаётся один атомарный коммит только по allowlist данных; issue получает
   комментарий со ссылкой на коммит и закрывается. Push запускает существующий Pages deploy.
7. При любом отказе коммита нет: issue получает причину отказа и закрывается как
   неприменённое. Частичное применение пакета запрещено.

## 3. Авторизация и credentials

- Принципал — неизменяемый `issue.user.login` из события GitHub, а не имя из тела пакета.
- Перед записью workflow обязан получить membership автора в `Timeline-Project-SC2` и
  требовать одновременно `state = active` и `role = admin`.
- Обычный `GITHUB_TOKEN` для этого недостаточен: у него нет organization permission
  `Members: read`; кроме того, push этим токеном не запускает следующий workflow/Pages.
  Поэтому доверенная личность исполнителя — отдельный GitHub App, установленный только
  на этот репозиторий; его App ID и private key лежат только в секретах Actions.
- Минимальные права App: organization `Members: read`; repository `Contents: write`,
  `Issues: write`, `Metadata: read`. Права на workflows, administration и secrets не выдаются.
- Токены установки выпускаются короткоживущими и по возможности раздельно понижаются:
  один — только на проверку membership, второй — только на коммит и отчёт в issue.
- Владелец создаёт/устанавливает App, вводит секреты и настраивает правила ветки.
  Агентам секреты не сообщаются; в репозитории допустимы только публичные идентификаторы
  и имена секретов.
- Прямой машинный коммит в `main` — узкое исключение из PR-процесса только для этого App
  и только после всех гейтов ниже. Если ruleset не даёт App bypass, публикация обязана
  падать закрыто, а не искать обходной путь.

## 4. Протокол пакета v1

- Тело issue содержит ровно один машинный блок; всё вне блока workflow не исполняет.
- Обязательные поля конверта: тип пакета, `version`, `batchId`, `baseRevision`, сводка и
  список операций. Неизвестные поля, дубли и вторая версия блока — отказ.
- Операция адресована не пути файла, а логическому датасету и стабильному ID записи.
  Объём v1 — полный CRUD с предохранителями: новые числовые ID только `max+1` без
  повторного использования, rename ID запрещён, delete запрещён при входящих связях.
  Update — patch только изменёнными полями; точный allowlist фиксирует `ADM-1`.
- Профили planet-generation входят в v1: пакет присылает только редакционные поля, а
  seed, `generation_key` и версии в Actions вычисляет существующий доверенный
  генератор. Границу полей и вызов генератора замораживает `ADM-0P`.
- Человекочитаемая сводка не доверенная: workflow заново строит её из операций и
  сверяет с присланной. Несовпадение — отказ: администратор должен подтверждать именно
  тот пакет, который будет применён.
- Пакет детерминированно канонизируется; его хэш и номер issue пишутся трейлерами в
  коммит. Повторный запуск сначала ищет этот след и не создаёт второй коммит.
- До живой no-submit пробы клиентский лимит предзаполнения — **7000 байт на весь URL**;
  8192 из разведки считается кромкой отказа, а не безопасным запасом. Превышение
  редактор показывает до открытия GitHub и требует разбить работу только на
  независимые пакеты; молча обрезать пакет запрещено.
- Точную базу даёт publish-only `/_admin/revision.json` из сборки: commit SHA и хэши
  опубликованных копий датасетов. В git этот файл не существует и источником данных
  не является.

## 5. Проверка и атомарность

Workflow выполняется только для служебного маркера и только на `opened`; правка, переоткрытие
или комментарий не становятся новой командой публикации. Тело issue считается враждебным:
оно не подставляется в shell, не исполняется и разбирается строгим парсером как данные.

Порядок гейтов:

1. Маркер, размер, ровно один блок, строгий JSON и поддерживаемая версия.
2. Автор-человек и активное `admin`-членство в организации.
3. Allowlist датасетов/операций/полей; типы, диапазоны, enum и обязательные значения.
4. Применение к полному снимку `baseRevision` в памяти/рабочем дереве раннера.
5. Сквозная проверка результата: уникальные ID, все связи, координаты/границы, профили,
   производные и защищённые поля, канонический CSV/JSON-формат.
6. Существующие релевантные валидаторы и проверки публикации из main; состав команд
   фиксируется карточкой `ADM-2` по факту разведки.
7. Текущий `main` всё ещё равен `baseRevision`; diff содержит только allowlist-пути данных.
8. Один коммит от имени GitHub App и нефорсированный fast-forward push в `main`.
   Если ветка ушла вперёд, push отклоняется целиком, а пакет считается устаревшим.

Публикации сериализуются одной concurrency-группой без отмены уже running job. Секреты не
нужны шагу первичного синтаксического отсева; доверенный токен выпускается как можно позже.

## 6. Редактор на Pages

- Формы строятся по сущностям, а не предлагают загрузку файлов или сырой CSV/JSON.
- Для связей используются выбираемые существующие ID; свободный ввод ссылок допустим
  только там, где разведка докажет, что справочника нет.
- Редактор показывает исходное и новое значение, список операций, локальные ошибки и
  признак устаревания открытой ревизии. Клиентская валидация — удобство, не гейт:
  авторитетна только проверка Actions.
- Незавершённый черновик не является источником истины и не должен незаметно переживать
  смену ревизии данных.
- После Submit администратор следит за результатом в самом issue: применено/отклонено,
  причина, коммит и ссылка на workflow. Статический сайт не притворяется, что знает
  результат до комментария бота.

## 7. Переключение со Sheets

1. До живой приёмки Sheets остаётся источником, а publisher работает только в dry-run.
2. На переключении: заморозка правок Sheets, финальный снимок и его проверка, затем
   отключение именно пишущего расписания/триггера sync.
3. Только после доказанного отключения sync включается запись publisher и делается
   живой контрольный пакет владельца/администратора.
4. Документация администратора переписывается с модели «Sheets — источник, CSV не трогать»
   на модель «GitHub — источник, правка только через админку». Ручной sync в обратную
   сторону не сохраняется как штатная кнопка.

## 8. Карточки волны

| Карточка | Содержание | Входной гейт |
|---|---|---|
| `ADM-0` | Read-only разведка данных, схем, UI-поверхности, workflows, ruleset, sync и лимитов issue URL | принята `PASS` с оговорками, см. вердикт |
| `ADM-0P` | Профили: поля, жизненный цикл, генератор seed/key на временных фикстурах | решение владельца «профили в v1» |
| `ADM-1` | Протокол пакета, валидатор и применитель CRUD + тесты; без живой записи | принятый отчёт `ADM-0P`, стоп-проверка meta, замороженные матрицы |
| `ADM-2` | Issue-workflow, GitHub App-контур, dry-run, отчётность и runbook владельца | `ADM-1` PASS; App и секреты заведены владельцем |
| `ADM-3` | Редактор на Pages и кнопка «Доступ администратора» | протокол `ADM-1` заморожен; нет пересечения с текущей волной F |
| `ADM-4` | Живое переключение: финальный снимок, отключение Sheets-write, контрольный пакет, документация | `ADM-2`/`ADM-3` PASS и отдельное разрешение владельца |

`ADM-0` не конфликтует с F-4, потому что ничего не меняет. Кодовые карточки `ADM` не
выдаются, пока разведка не докажет `Zero File Overlap` с активной карточкой волны F либо
та карточка не слита.

## 9. Отклонённые варианты

- Cloudflare/Vercel/Netlify и любая внешняя serverless-функция — отклонены владельцем:
  контур должен остаться GitHub-only.
- Собственный OAuth/API и браузерная сессия — отклонены: GitHub issue уже даёт аккаунт
  автора и явное подтверждение Submit.
- Один `GITHUB_TOKEN` на всё — отклонён технически: нет `Members: read`, а его push не
  запускает Pages workflow.
- Долгоживущий PAT человека в секретах — отклонён в пользу GitHub App: права уже,
  личность машинная, ротация и отзыв не привязаны к администратору.
- Полные файлы в issue вместо операций — запрещены до доказательств `ADM-0`: операции
  меньше, проверяемее и не дают пакету задавать произвольные пути.
