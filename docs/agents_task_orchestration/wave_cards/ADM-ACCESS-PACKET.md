# ADM-ACCESS-PACKET: черновик пакета и записи в репозиторий

> **Статус:** рабочий проект для критики, не утверждённый контракт и не разрешение
> менять код, источники, настройки или данные. Владелец выбрал автоматическое
> применение, первую отправленную заявку и предложил источник в репозитории вместо
> Sheets. По `A0-H2` надёжный порядок первых Submit пока не доказан; `HOLD` сохраняется.
>
> [Источник и очередь](ADM-ACCESS-REPO.md) · [доступ](ADM-ACCESS-CONTRACT.md) ·
> [данные A0-S/S2](ADM-ACCESS-S-REPORT.md) · [GitHub A0-H/H2](ADM-ACCESS-H-REPORT.md).

## 1. На что распространяется проект

Цепочка после согласованного перехода данных: редактор → пользователь отправляет
issue → упорядочивание → проверка подлинного автора и действующей роли Owner →
проверка изменений и исходной базы → автоматическая запись в репозиторий → сборка
и подтверждённая публикация. Ни второй модерации, ни ручного переноса каждой заявки
не предусматривается. Текущая Sheets и синхронизация до отдельного решения не меняются;
планетарные профили на паузе.

В качестве первого вертикального среза **рассматривается** изменение разрешённых
полей существующих непланетарных записей. Наборы, поля, создание и удаление пока
не утверждены. Идентификаторы по отчёту `A0-S2`: `system_id` для систем, `ID` для
мест и `faction` для фракций. Их устойчивость при переименовании, валидаторы и
взаимные ссылки требуют проверки; не считать любой текст универсальным ID.

## 2. Пакет — иллюстрация, не действующая схема

Пример описывает вымышленное изменение названия; имена полей и версия не утверждены:

```json
{
  "schemaVersion": "draft-1",
  "baseVersion": "<версия опубликованных данных>",
  "changes": [
    {
      "dataset": "systems",
      "id": "example-system",
      "operation": "update",
      "fields": {"name": {"before": "Прежнее", "after": "Новое"}}
    }
  ]
}
```

- `schemaVersion` задаёт согласованный формат, `baseVersion` — доказуемую версию
  данных, которую видел редактор. `data/meta.json.version = null` на базе `661165b`
  для этого недостаточно; происхождение `meta.sha` также не установлено.
- `dataset` и `id` — логические идентификаторы; `operation` и поля ограничены
  согласованным каталогом возможностей модуля. Путь к файлу определяет доверенный
  адаптер, а не текст issue. Внешние ссылки, произвольный код и пути не исполняются.
- `before`/`after` могут помочь выявлять конфликт, но не доказывают авторство,
  отсутствие промежуточных правок или допустимость объединения. `before` нужно сверять
  с доверенной базовой версией и актуальными данными, а не принимать на слово.
  Предусловия, типы, значения, Unicode, размер и канонизация ещё требуют контракта.
- Автор, организация, репозиторий и ID issue устанавливаются из доверенного GitHub
  события, не из пакета. Локальная метка сессии и `isSameAdmin` не авторизуют запись.
  Публичная issue не должна содержать секреты или непубличные данные.

## 3. Очередь и конфликты

Приоритет — выбранный владельцем порядок Submit в GitHub, не порядок запуска Actions.
По `A0-H2` обработка задержанных или потерянных событий, точность времени и
восстановление исходного содержимого не дают пока доказательства строгого порядка.
При неопределённости не применять конкурирующие пакеты и не выдавать успех. Договорённость
о ничьих и способ обнаружить пропуск ещё нужны; приоритет владельца не заменён на
«кто раньше попал в очередь».

До каждой записи проверяются автор и роль, схема и модуль, разрешённые действия,
база и затрагиваемые значения, ссылки и предметные ограничения. Если два разных
автора на одной базе меняют одно поле, выигрывает первая **доказанно отправленная**
и успешно проверенная заявка; вторая не перезаписывает её молча. Непересекающиеся
изменения можно объединять лишь после повторной предметной проверки.

Для серии одного автора каждая заявка отдельно авторизуется; последующая может
продолжить предыдущую, если её подтверждённая база включает результат предыдущей.
Совпадение автора и общая старая база сами по себе не доказывают связь или намерение.
Поведение при изменении старой issue до применения остаётся отдельным открытым
вопросом; сохранённый снимок не является разрешением применить его после правки.

## 4. Кандидат атомарного результата внутри Git

Воркер `A0-H2` предложил `createCommitOnBranch` с `expectedHeadOid`: API принимает
ожидаемый HEAD и набор изменений файлов в одном коммите
[1](https://docs.github.com/en/graphql/reference/commits). Кандидат: поместить в этот
коммит и данные, и надёжный ключ обработанной заявки. При расхождении HEAD нужно
остановить запись, перечитать состояние, повторно проверить очередь, роль и конфликты.
Это кандидат, а не проверка реальных прав, полная гарантия идемпотентности или
транзакция с проверкой роли и Pages.

Ключ обработки привязывать к доверенным ID репозитория и issue, а не к свободному
полю пользователя. После таймаута, когда запись могла состояться, сначала проверить
защищённую историю и целостность журнала, не повторять вслепую. Доступы и условия,
при которых историю или журнал можно подделать, ещё требуется спроектировать.
Не сохранять токены и непубличные сведения; полное копирование issue в Git может
надолго сохранить удалённое из публичной заявки содержимое и требует отдельной оценки.

Права writer, `contents: write`, фактические правила `main`, требуемые проверки и
согласованная настройка ещё неизвестны. Не предполагать, что API обходит защиту,
и не включать bypass. Документация об ограничениях `GITHUB_TOKEN`
[1](https://docs.github.com/en/actions/concepts/security/github_token) означает, что
запуск следующей сборки нельзя молча приписать обычному push; dispatch или другой
допустимый механизм нужно проверить. Отдельный постоянно работающий сервер не выбран.

## 5. Публикация, перенос и доказательства

В issue показываются отдельные стадии `в очереди`, `проверяется`, `конфликт`/отказ,
`записано`, `сайт обновлён` и неопределённое состояние. Успех Pages подтверждается
для нужной версии и содержимого; один зелёный workflow этого автоматически не доказывает.
Если более новая версия успела заменить результат до публикации, нельзя объявлять
его видимым на сайте без проверки. Повтор публикации не должен повторять запись.

Переход от Sheets — отдельный план с инвентаризацией, полным резервом, проверкой
контрольного снимка, точкой смены источника, защитой от старого sync и обратной сверкой
новых данных при откате. Общий sync не отключать без проверки неперенесённых данных,
включая планетарные; живой переход требует отдельного разрешения.

До допуска к реализации независимый `rc-08` оценивает: доказуемость порядка Submit и
снимка при потере или правке события; каждую проверку роли; атомарность коммита и
журнала; повтор после таймаута; защиту ветки и сохранность; область версий и конфликтов;
запуск Pages и честность результата. Нужны проверяемые негативные сценарии, в том
числе два автора/одно поле, один автор/два устаревших черновика, пропущенное событие,
смена HEAD, отказ API и сбой после коммита. Точная матрица `OWNED_FILES` и интерфейсы
появятся только после критики и закрытия блокеров.
