## Воркер 2 (A0-G / A0-H / A0-K / A0-K2) → A0-K3

Один исполнитель и обычная проверка CI, без новой волны разведок и критиков. Передать
в прежний чат воркера 2; сначала только подготовка PR, без настоящего App и секретов.

~~~~text
Ты — воркер 2, продолжение A0-G/A0-H/A0-K/A0-K2. Задача A0-K3: подготовить
небольшой workflow для будущей ручной проверки GitHub App, только на чтение.

База origin/main 70cd3c19f98faac79974fd9b5cc258976acf1a92. Работай в своей
разрешённой ветке. Если HEAD старее, обнови только безопасно, без потери изменений;
при сомнении остановись и сообщи. Первым и единственным изменением будет новый файл:
OWNED_FILES: .github/workflows/app-owner-readonly.yml
FORBIDDEN_FILES: все остальные, включая docs, существующие workflow, данные и сайт.
Путь отсутствовал в main по Git-метаданным Гайдлайнера; перепроверь перед созданием.

Контракт:
1. Только workflow_dispatch; никаких issue, push, schedule или PR-триггеров.
   Один job, без записи в GitHub, Sheets, Discord и без публикации Pages.
2. Разрешён только репозиторий Timeline-Project-SC2/Timeline-Project-SC2.github.io
   и ref refs/heads/main. Явно запрети остальные цели; не запускай чужой код и не
   делай checkout PR. Для встроенного GITHUB_TOKEN — минимум без write, например
   permissions: {}. Используй candidate environment app-owner-readonly. В будущем
   владелец отдельно ограничит environment веткой main; if в workflow сам по себе
   не считается защитой секрета от изменения другого workflow.
3. Создай временный installation token официальным actions/create-github-app-token,
   закрепив проверенный release полным commit SHA. Явно выбери установку организации
   Timeline-Project-SC2 и запроси только Members: read. Важно: owner без repositories
   охватывает все репозитории, доступные установке, хотя сейчас по словам владельца
   репозиторных прав нет. Не запрашивай лишние permissions и не меняй App.
4. Через API проверь только инициатора ручного запуска github.actor: активный Owner
   организации означает state=active и role=admin. Передавай значения контекста в
   shell через env, не вставляй выражения в команды. 403, 404, ошибка и неопределённый
   ответ — отказ, не успешная авторизация. Это проверка вручную, не логика заявки.
5. Не выводи ключ, токен, полный ответ API, сведения об участниках или действующие
   имена секретов. Публичные логи показывают успешность job и инициатора: отметь в
   отчёте, что по результату проверки собственной роли может раскрываться членство.
   Избегай verbose/debug; укажи имена только НОВЫХ предлагаемых переменной и секрета
   для будущей настройки владельцем, но не их значения. Не проси ключ в чате.

Сделай один PR с этим файлом и обычной самопроверкой: синтаксис workflow, события,
права, отказ при ошибке, git diff --check и стандартный CI. Дополнительных агентов,
тестового репозитория и PAT не требуется. Настройки, App, environment, секреты, данные
и иные ветки не менять. Сам workflow не запускать, ключ не размещать, реальных членов
не запрашивать. Не сливай PR, не используй --admin и не включай автоматическую запись.

Отчёт кратко: ссылка PR, HEAD, список файлов, что проверено/CI, названия новых
переменной и секрета и что владельцу предстоит настроить позже. Укажи, что для
workflow_dispatch файл должен быть в default branch и реальный App не проверялся.
~~~~

Следующий шаг после результата — один обычный разбор отчёта и CI; размещение ключа,
ограничение environment и один реальный запуск обсуждаются отдельно с владельцем.
Существующий sync, сайт, данные и планетарный контур не меняются.
