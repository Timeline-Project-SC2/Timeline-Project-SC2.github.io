## 2. Уточнения к событиям и матрице

- Для `pull_request` из публичного fork GitHub обычно ограничивает токен чтением и
  не передаёт остальные секреты. Это нельзя переносить на все события: в контексте
  `pull_request_target` workflow базового репозитория может иметь доступ к секретам и
  правам; исполнение чужого кода в таком контексте опасно
  [1](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).
  Внутренний PR также зависит от конкретных разрешений и политик.
- Q1 повторил, что `schedule`, `workflow_dispatch` и `repository_dispatch` в fork
  не запускаются. **Безусловно это неверно:** Actions в fork и расписания публичного
  fork по умолчанию отключены, но их можно включить. Ручной запуск требует workflow
  с `workflow_dispatch` в default branch и права записи; `repository_dispatch` —
  подходящее событие и workflow в default branch. Сам PR не является ни одним из этих
  событий [1](https://docs.github.com/actions/using-workflows/events-that-trigger-workflows)
  [2](https://docs.github.com/actions/managing-workflow-runs/manually-running-a-workflow).
  Это общая документация GitHub, не проверка настроек какого-либо fork.
- Воркер предложил тест записи с отдельным PAT и реальный Pages в тестовом репозитории.
  Это **идеи**, не разрешённые шаги: дополнительный пользовательский токен не требуется
  для первой проверки; запуск Pages выходил бы за рамки задания. Кандидат для оценки —
  выдаваемый GitHub токен только изолированной job с минимальными правами, проверка
  фиктивной записи исключительно в заранее выбранном тестовом репозитории и только
  после разрешения. Его успех не докажет работу боевого sync или Pages.
- Q1 предлагает фиктивные ответы загрузки и симуляцию публикации. Для локального
  этапа подмена одного URL недостаточна: исходящие запросы должны быть исключены,
  ответы — полностью фиктивны, без подключения к Sheets и другим сервисам.
- Чтобы проверить недоступность секретов, одной их отсутствующей настройки недостаточно;
  позитивный контроль и безопасный фиктивный маркер требуют отдельного проектирования
  и согласия. Не создавать и не перечислять секреты сейчас.

## 3. Следующий шаг

Получены Q1 и [отчёт критика](ADM-ACCESS-TR-REPORT.md): направление фиктивных тестов
принято с условиями, смена default — `HOLD`. Фактические права и точная строка начала
sync job всё ещё не подтверждены. Тестовый репозиторий не выбран, создание не поручено.
Следующий кандидат — спроектировать локальные проверки без сети и спросить согласие
владельца на исполнение. Реальный App, размещение ключа, смена default, живая запись
и текущий sync остаются на отдельных `HOLD`; зелёный CI при прежних настройках не
доказывает совместимость с изменёнными правами.
