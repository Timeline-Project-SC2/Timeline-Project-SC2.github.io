## 1. Роль App в предлагаемой архитектуре

Рассмотреть **частное GitHub App организации + GitHub Actions** в этом репозитории.
Это не три независимые установки и не отдельный сайт:

- **GitHub App** — зарегистрированная служебная идентичность с разрешениями,
  выдаваемыми аккаунтом установки; она не является Owner организации. Скриншот
  указывает `Timeline-Project-SC2` как разработчика App, но не аккаунт установки.
- **GitHub Actions** — выполнение сценария на стороне GitHub, например по созданию
  issue. Приложение в таком варианте может использоваться для доступа к API и не
  требует собственного постоянно работающего сервера
  [3](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow).
- **Закрытый ключ App** (`.pem`) позволяет процессу удостоверить приложение. Сам
  ключ долговременный и чувствительный; созданный для установки токен обычно живёт
  один час [1](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app).
  При каждой обычной заявке пользователь не получает и не вводит этот ключ.

Кандидатная цепочка: редактор → автор вручную отправляет issue под своей учётной
записью GitHub → Actions получает сведения от GitHub → проверяет, что автор — активный
Owner **организации** → при выполнении остальных условий автоматика применяет пакет,
запускает публикацию и сообщает результат в issue. Это целевое поведение, не готовая
функция. Автору не выдаётся новая роль; вход на демо-странице не авторизует запись.

## 2. Какие права потребуются — кандидаты

| Право | Зачем | Реальная область и ограничения |
|---|---|---|
| Организация: `Members: read` | Читать статус и роль автора через API. | Это чтение сведений об участниках **организации**, а не только выбранного репозитория. Не даёт менять роли. Результат может затрагивать приватность. |
| Репозиторий: `Issues: write` | Комментировать результат в issue, если комментирует App. | Шире одного комментария. Возможен вариант использовать ограниченный встроенный `GITHUB_TOKEN` Actions; разделение токенов ещё не выбрано. |
| Репозиторий: `Contents: write` | Будущая запись данных и журнала в Git, если пишет App и источником выбран репозиторий. | Это не разрешение только на `data/`: право затрагивает содержимое выбранного репозитория с учётом защиты веток. Ограничение путей в коде само по себе не ограничит украденный токен. |

Для запроса членства GitHub документирует `Members: read` и установочный токен App
[1](https://docs.github.com/en/rest/orgs/members#get-organization-membership-for-a-user).
Встроенный `GITHUB_TOKEN` ограничен репозиторием и не следует считать его
подтверждённым средством чтения ролей всей организации
[1](https://docs.github.com/en/actions/concepts/security/github_token). Полный набор
прав и то, какие из них выдаются App, а какие конкретному заданию Actions, не утверждены.
Права администратора организации, изменение её участников и `Members: write` не нужны
для заявленной проверки. Запись в рабочие данные сейчас не разрешена.

Защита `main` может не разрешить запись даже при `Contents: write`. Обход защиты,
автоматическое слияние и правила проверок — отдельное решение владельца, а не скрытое
следствие установки App. Стандартный `GITHUB_TOKEN` также имеет ограничения на запуск
других workflow; способ запуска Pages и подтверждение публикации ещё не доказаны.

## 3. Разовая настройка владельцем

На показанном экране установка имеет `Read access to members` и `No repositories`.
Для чтения роли организации репозиторий сейчас выбирать не требуется; аккаунт установки
по этому кадру не подтверждён. Владелец разрешил перейти к подготовке ключа, настройки
уточняются по ходу. Секрет и workflow описаны как следующие шаги, не как выполненные.

1. В GitHub открыть настройки организации → **Developer settings → GitHub Apps →
   New GitHub App**. Зарегистрировать частное приложение организации, установить
   **Only on this account**. В качестве Homepage URL подходит страница проекта.
2. Для сценария, где события получает Actions, у App можно отключить **Webhook →
   Active**; отдельный адрес приёмника и авторизация OAuth каждого пользователя не
   нужны. Выбрать согласованные минимальные разрешения
   [1](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app).
3. Через **Install App** установить приложение в организацию. При запрашиваемых правах
   на репозиторий выбрать **Only select repositories** и нужный репозиторий. Если App
   не запрашивает репозиторных прав, GitHub может вообще не показать этот выбор — для
   проверки `Members` он не нужен. Выбор репозитория не ограничивает организационное
   `Members: read` до его сотрудников [7](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app).
4. Владелец сообщил, что скачал `.pem`; его хранение помощник не проверял. Ключ нужно
   хранить в защищённом месте вне проекта. GitHub хранит публичную, но не закрытую часть;
   закрытый ключ не истекает автоматически
   [1](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps).
   Не отправлять ключ, токены или пароли в чат, issue, код, журнал или на сайт.
5. [Отчёт воркера 2 A0-K](ADM-ACCESS-K-REPORT.md) получен; отдельное окружение с
   `main` без reviewer на каждую заявку — кандидат, а не подтверждённая защита.
   [Независимый rc-08](ADM-ACCESS-KEY-CRITIC.md) отдельно оценит хранение ключа,
   read-only тест и живую запись. До оценки секрет не размещать; его название и
   права workflow не утверждены. Выпуск токена, проверка роли и запись не атомарны.

При нормальной работе владелец один раз управляет установкой, а каждый автор просто
входит в GitHub и отправляет issue. Отзыв или приостановка установки, ротация ключа
и аварийное отключение должны быть описаны и проверены до запуска; хранение секрета
в GitHub не защищает от кода доверенного workflow, который может его прочитать.
Нужно также защитить изменение workflow и ветку, не передавая секреты недоверенному
коду [8](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions).

## 4. Что сначала проверить

- Скриншот установленного App показывает `Read access to members` и `No repositories`;
  разработчик — `Timeline-Project-SC2`, аккаунт установки на кадре не указан. Проверить
  нужный аккаунт можно в **Your organizations → Settings → Third-party access →
  GitHub Apps → Configure** [7](https://docs.github.com/en/apps/using-github-apps/reviewing-and-modifying-installed-github-apps).
  Репозиторные права не выдавать лишь для появления выбора. Если они понадобятся App

  достаточно названий и уровней, без ключей, токенов и URL вебхуков.
- Право и возможность владельца зарегистрировать App в организации; правила её
  установки, доступность Actions и фактическая защита репозитория без изменения настроек.
- Минимальные разрешения по отдельным операциям, включая более широкий доступ к
  членству и содержимому; возможно ли и полезно ли разделить токены/задания.
- Защиту ключа, доверенного workflow и данных публичной issue, сценарии отзыва ключа,
  отключения App и ошибки проверки роли без ложного успеха. В отчёте A0-K полные
  политики ветки и Actions вернули `403`; `github-pages` не доказывает защиту нового
  окружения. Доступные сейчас правила `main` отличаются от ранее виденных метаданных;
  причину не устанавливать без фактов.
- Необходимые условия защищённой записи, запуска Pages и старого sync. До разрешения
  записи не проверять это изменением живых данных или защиты ветки.
- Доказуемость первого Submit и неизменности заявки. **Сам App не решает очередь,
  потерянные события, edit→restore или гонку отзыва роли.** Отдельный устойчивый
  приёмник остаётся альтернативой для исследования, не принятым требованием.

Стандартные исполнители Actions на GitHub для публичного репозитория бесплатны
[1](https://docs.github.com/en/actions/reference/runners/github-hosted-runners);
платные исполнители, хранение и внешние сервисы могут иметь отдельные условия.
Реальные расходы и ограничения организации не проверены.

## 5. Уведомления в Discord — часть плана

Владелец поручил включить в план Discord-уведомления об ошибках, рассогласованиях
и обновлениях данных и сохранить план в `main`. Это дополнительный канал, **не
разрешение на запись и не замена результату в issue**. Точные события, канал и
способ подключения ещё не выбраны.

- Для коротких диагностических сообщений кандидат — Actions → входящий вебхук
  Discord: без отдельного Discord-бота или постоянно работающего сервера
  [2](https://docs.discord.com/developers/platform/webhooks). В этом варианте URL
  вебхука — отдельный секрет Actions, не поле Webhook приложения GitHub и не ключ App.
  Выдача секрета и включение уведомлений пока не согласованы.
- У Discord есть и приёмник GitHub-событий `/github` для прямого вебхука репозитория
  [1](https://docs.discord.com/developers/resources/webhook#execute-github-compatible-webhook).
  Он поддерживает не все типы событий и не формирует сам предметные сообщения о
  рассогласовании. Прямой путь и доставка из поля GitHub App не проверялись и не
  выбраны; адрес Discord нельзя бездумно считать обычным URL без секрета.
- В плане различать: ошибку проверки или обработки; конфликт данных/версий; подтверждённую
  запись; публикацию подтверждённой версии сайта или её сбой. Точные поводы, текст и
  частоту согласовать; не объявлять публикацию лишь на основании коммита или запуска.
- В сообщениях предусмотреть ссылку на issue или запуск и стадию результата; не отправлять
  секреты, текст пакета или лишние сведения о приватном членстве. Защищать канал от
  шума и атак через содержимое публичных issue.
- Недоступность Discord не должна менять результат заявки или вызывать повторную запись
  данных: при необходимости повторяется только уведомление. Отсутствие сообщения не
  доказывает, что всё в порядке: Actions или Discord могут не работать. Доставку,
  неоднозначный таймаут и защиту от повторов ещё нужно спроектировать и проверить.
