## 1. Доказательства и риски

- Событие `issues.opened` содержит объект исходной issue, репозиторий и инициатора
  [1](https://docs.github.com/en/webhooks/webhook-events-and-payloads). GitHub сообщает,
  что Actions сохраняет исходный payload для повторного запуска workflow
  [1](https://github.blog/changelog/2019-09-30-github-actions-deterministic-re-runs-for-workflows/).
  Это кандидаты для исходного снимка, но не журнал применений и не гарантия успешной доставки.
- Текущий текст issue может быть изменён; история описания доступна, пока автор или
  пользователь с правом записи её не удалил
  [1](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/editing-an-issue).
  Сравнение текущего и исходного текста не доказывает отсутствие edit→restore.
- Сверка настоящего автора по стабильному ID и активной роли Owner необходима, но
  отражает момент запроса к GitHub; она не атомарна с последующей записью в Sheets.
- По документации Actions стандартная очередь `concurrency` заменяет предыдущую
  ожидающую задачу; `queue: max` ограничена 100 ожидающими
  [1](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
  Сама по себе очередь не является устойчивым журналом заявок или результатов записи.
- При повторной доставке webhook GitHub сохраняет `X-GitHub-Delivery`
  [1](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks).
  ID доставки не заменяет ключ заявки для дедупликации разных событий и не должен
  предполагаться доступным в Actions в том же виде без проверки.

## 2. Предложение воркера — не выбранная архитектура

Воркер предлагает привязывать применение к исходному payload `opened`, сохранять
его и идентификаторы репозитория, issue и автора, ограничить срок исполнения,
проверять права непосредственно перед записью и сохранять уникальный ключ заявки.
Далее — последовательный доверенный writer, устойчивое состояние и проверка результата
после таймаута. Другая версия изменений должна отправляться новой issue.

Воркер также рассматривает доверенный сервис с долговечным журналом. Это **кандидат**,
а не доказанная необходимость отдельного платного или постоянно работающего сервера;
вариант на Actions и доступных хранилищах ещё нужно оценить. Одно атомарное
резервирование в журнале не доказывает отсутствие повторной записи во внешний источник:
нужен подтверждённый идемпотентный или иной безопасный способ на стороне записи и
восстановление после неизвестного результата. Не обещать общую транзакцию GitHub,
Sheets и Pages.

## 3. Нерешённая семантика и следующий гейт

Предложение применять **оригинал даже после редактирования issue** не следует из
выбора владельца «исправленный вариант отправляется новой issue». Владелец не выбрал,
должна ли исходная заявка при такой правке до её обработки оставаться исполнимой.
Текущий черновик требует инвалидировать подтверждение при любой правке, но надёжный
способ установить edit→restore не доказан. Не считать предложение `A0-H` разрешением
применять старую версию или допуском к коду.

Это исключительный технический случай, а не вторая модерация или обязательный шаг
обычной работы: цель остаётся «отправить → автоматически проверить и применить →
обновить сайт». Реальную запись, подключение App и настройки без отдельного согласия
не включать; после проработки нужны независимая критика и матрица файлов.
