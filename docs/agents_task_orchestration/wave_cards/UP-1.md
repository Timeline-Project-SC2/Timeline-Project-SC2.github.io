# Карточка `UP-1` — один проход по подтверждённому перегрузу

> Назад: [карточки и оркестрация](../README.md) ·
> [правила отбора контекста](../../consolidation-plan.md) ·
> [долг планетарных тестов](../../stages/stage-08/todo.md).

**Статус:** проект карточки, не запущена. Выполнять по отдельной команде владельца.
**Режим:** один агент, одна последовательная задача, одна ветка и один итоговый PR;
перед слиянием остановиться. Не создавать подкарточки, новые волны и отдельные
отчёты ради отчётов: результат и доказательства — в описании PR.

## 1. Что значит «починить за один проход»

Устранить выявленные причины перегруза в актуальной документации, правилах
работы, планетарных тестах и одном конкретном узле кода. Это не обещание
отсутствия всех возможных ошибок в проекте. Если часть нельзя завершить без
решения владельца или потери проверок, выполнить независимые безопасные части
и честно указать блокер; не объявлять всю задачу выполненной.

**Не менять продуктовую функциональность, данные, единицы измерения, контракты,
инварианты генерации и внешний вид по своему усмотрению.** Не считать размер
файла или количество тестов дефектом без содержательной причины. Не делать
массовый перепил сайта или документации ради метрики.

## 2. Старт и базис

1. Проверить ветку, `git status --short`, версии Node и Python; сохранить
   чужие незакоммиченные изменения. Использовать версии из `.nvmrc` и
   `.python-version`, установить зависимости по lock-файлу.
2. Стартовый контекст: корневой `AGENTS.md`, эта карточка, актуальный
   `docs/handoff/status-and-state.md` и `AGENTS.md` затрагиваемых доменов
   `site/`, `src/`, `tools/`. Соблюдать действующие лимиты чтения и глубины;
   при необходимости расширения сначала остановиться, показать таблицу
   прочитанного и оформить выжимку в этой карточке, затем продолжить только
   точечное чтение. Не обходить дерево документации и не требовать нового
   согласования, если решение владельца не требуется.
3. До правок зафиксировать в отчёте состав полного Node-набора и имена
   карантина из `tools/known-test-failures.json`, результаты `npm run test:raw`,
   `npm test` и `npm run verify:docs`. Измерить время `npm test` на той же
   машине и версии Node, что и после правок. Красный `test:raw` не скрывать.

На базе `2fd9eb0` ранее наблюдались 37 Node-файлов, 8 известных падений и
двойной прогон примерно за 114 секунд. Это ориентир для проверки, а не
обещание времени и не замена собственному базису исполнителя.

## 3. Работа — не останавливаться после инвентаризации

### 3.1. Актуальная документация и правила

- Сверить обязательный статус и команды в `AGENTS.md`,
  `docs/handoff/status-and-state.md` и `docs/handoff/repo-zoom-and-rules.md`
  с кодом, `package.json` и текущими `data/`. Исправить ложные сведения о
  числе систем/мест, секторных тайлах, источниках и состоянии проверок;
  считать строки CSV при выполнении, не переносить старые числа на веру.
- В статусе отделить текущие факты от истории; для подробной истории
  использовать существующие документы или Git. Сохранить значимые старые
  пути и ссылки, не удалять первоисточники. Новый итог добавлять в
  `CHANGELOG.md`, не переписывая его существующие записи.
- Упростить `docs/ai-workflow.md`: для однозначной малой правки — проверка
  по её риску, без обязательного опроса и отдельного красного теста на
  каждый пункт; для изменения поведения — тесты контракта и гейты домена,
  для визуала — проверка владельца. Не ослаблять CI и не отменять требования
  корневого и доменных `AGENTS.md`.
- Сохранить решения владельца о 200 строках, стартовом бюджете контекста,
  глубине чтения, гибридных регистрах и защите старых ссылок. Менять эти
  решения только по отдельному явному указанию владельца. Изменить навигацию
  там, где это необходимо, но не плодить новые регламенты и хабы.

### 3.2. Восемь падений и двойной тестовый прогон

- Для **каждой** записи реестра установить причину: ошибка кода, устаревшее
  ожидание или неразрешённое противоречие требований. Исправить причину;
  обновлять ожидания и golden-хэши только с независимым обоснованием по
  действующему контракту, а не под фактический вывод сломанного кода.
- Запрещено удалять проверки, расширять карантин, добавлять `skip`/`todo`,
  ослаблять пороги или скрывать ошибки через `continue-on-error`. При замене
  проверки показать соответствие старого сценария новому и его смысл.
- Пока хотя бы одно падение не исправлено, сохранить действующую защиту
  карантина; удалять запись только вместе с доказанной починкой и обновлять
  связанные проверки стража. Оставшиеся имена и новые падения должны
  продолжать проверяться, а незакрытый долг — оставаться видимым.
- После исправления **всех** записей и полного зелёного `test:raw` снять
  карантин и убрать необходимость двух прогонов: `npm test` должен один раз
  запускать полный набор без фильтрации. Обновить `package.json`, CI,
  проверки раннера и актуальную документацию, закрыть пункт `S8-Q1` с
  доказательствами; исторические ссылки сохранить.
- До приёмки доказать на временных тестовых примерах, что `npm test` краснеет
  при неожиданном падении теста и аварийном завершении процесса. Новый
  тестовый файл не должен молча теряться: он либо исполняется автоматически,
  либо его отсутствие в списке приводит к явной ошибке. Временные файлы
  удалить, не затрагивая чужую работу.

### 3.3. Одна проверяемая граница в коде

Выделить из `site/planet-globe/planet-globe.ts` самостоятельную чистую
логику камеры, включая `rebaseLocalCameraState`, в отдельный модуль; сохранить
публичные экспорты и поведение страницы. Проверить численные результаты для
направлений перехода, нулевого радиуса и сохранения ракурса. При переносе
заменять привязанные к написанию исходника проверки поведенческими только с
сохранением их смысла. Не разделять остальные 3557 строк механически и не
создавать вторую реализацию камеры. Если безопасно выделить границу нельзя,
оставить код без рискованной правки и указать конкретный блокер.

## 4. Файлы и защита границ

Разрешены адресные правки к указанным документам и их навигации,
`CHANGELOG.md`, `docs/stages/stage-08/todo.md`, `package.json`,
`.github/workflows/check.yml`, тестам, стражу и реестру в `tools/`,
`tools/stand_local_map.mjs`, планетарному коду в `site/planet-globe/`,
`site/shared/`, `src/local-map/` и `src/planet/` — только если это нужно
для пунктов §3. Остальные файлы и домены не менять без объяснения владельцу.
Не менять `data/`, `assets/src/`, контракты `src/contracts/`, зависимости,
исходники в `site/assets/vendor/` и другие workflow. Не выполнять живую
синхронизацию Google Sheets и не публиковать сайт.

Это отдельная задача по планетарному долгу, не продолжение секторной волны;
инварианты планетарного контура и правила его домена по-прежнему действуют.

## 5. Проверки и критерии приёмки

Выполнить и показать команды, коды возврата, число тестов и непройденные
проверки. Минимум: `npm run verify:docs`, `git diff --check`, `npm run lint`,
`npm run build`, `npm run verify:publish`, `npm run verify:contract`,
`npm run check:planet-core`, `npm run verify:hashes`, `npm run test:py`,
`npm run test:raw` и `npm test`; для затронутого домена — остальные проверки
из `.github/workflows/check.yml`. Подготовить необходимые локальные ассеты,
не затирая данные и чужие изменения. При правках камеры или рендеринга
проверить страницу в браузере, если среда позволяет, и передать визуальную
приёмку владельцу. Полную матрицу CI проверить в PR, если она доступна;
недоступные браузерную проверку или CI не называть пройденными.

**Готово** только если одновременно:

1. Актуальные документы не выдают указанные исторические сведения за текущие,
   малые задачи не требуют лишней процедуры, правила отбора контекста целы.
2. Все восемь исходных сценариев выполняются и проходят без карантина;
   все прочие тесты из базиса сохранены или имеют обоснованную замену,
   нет новых `skip`/`todo`, `test:raw` и `npm test` проходят.
3. `npm test` выполняет полный набор один раз, проверки из §3.2 подтверждают,
   что новые падения и пропущенный тестовый файл не проходят молча.
   Показано время до/после в одной среде, без жёсткого порога в секундах.
4. Граница камеры выделена и проверена без изменения поведения; сборка,
   доменные гейты и полная матрица CI зелёные. Если CI недоступен, результат
   ожидает CI. При правках камеры или рендеринга визуальная приёмка — за
   владельцем; до неё результат не финальный.

Иначе итог — **«частично / заблокировано»**, с перечнем сделанного, именами
оставшихся падений, результатами проверок и одним конкретным вопросом по
каждому решению, которое действительно должен принять владелец.
