# Карточка `ADM-0P` — профили planet-generation: разведка и прототип

> **Статус:** первая выдача заблокирована без расхода попытки (карточка была только в
> draft PR, а промпт противоречил сам себе про fetch/сеть); действует самодостаточная
> перевыдача `R1` в чат. Вердикт и урок — [`ADM-0P-execution.md`](ADM-0P-execution.md).
> **Основание:** [`ADM-0`](ADM-0-execution.md) принята `PASS` с оговорками. **Режим:**
> read-only в репозитории; допустимы только временные копии вне рабочего дерева.
> **Решение владельца:** профили входят в v1, производные поля вычисляет доверенный
> генератор в Actions, а не браузер и не пакет.

## 1. Цель

Заморозить факты, без которых нельзя включить `data/planet-generation.csv` в протокол
`ADM-1`: жизненный цикл профиля, границу «редакционные поля ↔ производные поля»,
безопасный вызов существующего генератора и операции create/update/delete/freeze.

Готово — это таблица полей и переходов, воспроизведённые на временных фикстурах
сценарии генератора и точное предложение контракта. Не готово — пересказ названий
колонок без доказательства, что Actions сможет детерминированно получить валидную
строку только из редакционного ввода и текущего дерева.

## 2. Запреты и поверхность

- `OWNED_FILES`: **нет**. Ветки, коммиты, PR, issue и записи в GitHub запрещены.
- Не изменять живые `data/*`, код, workflow, документы и настройки репозитория.
- Существующие CLI можно запускать только на копиях во временном каталоге вне
  репозитория; после работы временные файлы удалить и доказать чистое дерево.
- Сеть, Sheets-sync, генерация в живые пути и передача полных строк профиля в отчёт
  запрещены. Seed/key в отчёте показывать только длиной/префиксом формата, не значением.
- Если CLI нельзя безопасно перенаправить во временный корень, не запускай его вслепую:
  зафиксируй это стоп-фактом с `путь:строка`.

## 3. Вопросы

### P1. Поля и жизненный цикл

Для всех 37 колонок дай сгруппированную таблицу:

| Группа | Что установить |
|---|---|
| Идентичность | `place_id`: уникальность, допустимые типы мест, неизменяемость |
| Редакционный ввод | поля, enum, типы, диапазоны, defaults и зависимости preset/surface |
| Служебные версии | кто задаёт `profile_revision` и версии алгоритмов; когда увеличиваются |
| Производные | `master_seed_hex`, `generation_key`, grid/noise/geography и иные вычисляемые поля |
| Утверждение | `approved_by/at`, условия frozen и допустимые переходы статусов |

Отдельно ответь:

- Что обязательно на create и что редактор обязан прислать явно, а что генератор
  обязан достроить сам.
- Какие поля можно менять в `draft`, `review`, `frozen`, `disabled`; есть ли
  unfreeze и что происходит с ключом после любой редакционной правки.
- Кто является источником `approved_by` и `approved_at` в GitHub-only контуре.
  Кандидат Гайдлайнера — фактический автор и `created_at` issue из события, а не
  значения из пакета и не локальные часы раннера; подтверди или опровергни кодом.
- Семантика delete: физическая строка, только `disabled` или запрет после freeze;
  что блокирует удаление места при наличии профиля.

### P2. Генератор seed/key и версий

По существующим функциям/CLI установи:

- Точную формулу входа `generation_key`: какие поля канонизируются, какие исключены,
  где манифест участвует в сверке и что произойдёт при смене каждого редакционного поля.
- Когда рождается `master_seed_hex`, какой источник энтропии используется и можно ли
  создать профиль без seed в пакете так, чтобы дальнейший результат был полностью
  воспроизводим из закоммиченных данных.
- Какие значения версий берутся из констант кода, а какие являются данными профиля.
- Можно ли вызвать генератор как библиотечную функцию на кандидатной строке в памяти
  или только CLI с файловыми путями. Дай сигнатуры/команды одной строкой и побочные
  эффекты каждого кандидата.
- Использует ли путь генерации сеть, время, случайность вне seed, GPU, внешние файлы
  или ручные артефакты. Каждый ответ — `путь:строка`, не предположение.

### P3. Прототип на временных фикстурах

На копиях вне репозитория воспроизведи, не меняя живые данные:

1. Минимальный create для допустимого места → `validate` успешен.
2. Одна редакционная правка → пересчёт производных → `validate` успешен; укажи,
   какие именно поля изменил генератор.
3. Переход к frozen, если поддерживается → какие поля заполнились и откуда.
4. Негативы: дубль `place_id`, недопустимый тип места, присланный чужой/битый
   `generation_key`, правка запрещённого производного поля.
5. Повтор той же операции на уже применённом результате: идемпотентность или явный
   отказ, без второго изменения данных.

В отчёте нужны команды без секретов, exit-статусы и имена изменившихся полей. Сами
сгенерированные строки, seed и key целиком не прикладывай.

### P4. Контракт для `ADM-1`

Предложи до буквы, но не реализуй:

- Формы операций профиля: достаточно ли `create/update/delete`, или freeze требует
  отдельной операции перехода из-за производных эффектов.
- Allowlist полей по операции и исходному статусу; поля пакета, которые всегда отказ.
- Фазу применителя: когда генератор достраивает строку относительно CRUD мест,
  сквозной валидации и пересчёта сводки пакета.
- Как показывать производный результат в issue-сводке, не публикуя seed/key целиком и
  не позволяя сводке врать о применённой строке.
- Точный интерфейс, который `ADM-1` оборачивает: функция/CLI, аргументы, stdout/exit,
  временные файлы, детерминированность и тесты-фикстуры.
- Черновое дополнение к матрице `ADM-1`, если существующий генератор нельзя вызвать
  без изменения его файла. Само изменение не делай.

## 4. Стоп-факты

Вынеси отдельным списком, если хотя бы одно верно:

- валидный профиль нельзя получить из редакционных полей без ручного файла/ключа;
- генератор требует сеть, секрет, GPU или невоспроизводимую случайность вне seed;
- key зависит от артефакта вне репозитория либо от ручного манифеста администратора;
- CLI жёстко пишет в живые пути и не имеет безопасного временного режима;
- frozen-семантика противоречит полному CRUD владельца;
- создание профиля требует изменить код или сгенерированные файлы вне allowlist данных.

## 5. Формат отчёта

Одна сводка до 180 строк: база и чистота дерева; таблицы P1–P2 с `путь:строка`;
результаты P3 по пяти сценариям; предложение P4; стоп-факты либо «стоп-фактов нет».
Полных листингов, строк CSV и значений seed/key не присылать. Стоп после отчёта:
`ADM-1` выдаёт только Гайдлайнер после приёмки.
