## Решения владельца

1. Цель UX: редактор формирует изменения → владелец подтверждает в панели → вход/
   разрешение GitHub при необходимости → issue создаётся автоматически → после
   проверок автоматическое применение и публикация без второй ручной модерации.
   Ручная предзаполненная форма GitHub — альтернатива, но владелец не выбрал её как
   замену. Не считать работу над ней разрешением менять выбранный сценарий.
2. У каждого администратора своя issue и случайный редактируемый долгоживущий код,
   которым можно поделиться. Общая корневая issue и общий код группы не предполагались.
   Владелец хочет возможность вносить данные в чужую issue и приветствует синхронизацию;
   код не является секретом и не даёт прав. Способ общей записи не выбран.
3. Предложены стадии существующей issue: черновик и явная отправка; до Submit правки
   допустимы. При сравнении текущего и загруженного черновика загруженная сторона имеет
   меньший приоритет; нужны видимые различия. В очереди первой идёт первая именно
   отправленная заявка. Как связать существующий общий черновик с автоматически
   создаваемой при подтверждении issue и каким событием надёжно обозначить Submit,
   ещё не определено; не подменяй это решением без владельца.
4. Проверять реального отправителя и активного Owner ОРГАНИЗАЦИИ, не просто админа
   репозитория. Если после Submit до записи изменён title/body, старую заявку не
   применять, исправление — новая issue. Если отсутствие правки не доказано — стоп.
   При успехе дополнительное ручное утверждение каждой заявки не требуется.
5. Публичная issue, автор и результат могут раскрыть роль. Предупреждать до отправки;
   ни секретов, ни непубличных данных в issue, URL и логах. Код issue не авторизация.
   Результат можно показывать в той же issue; комментарий App — от бота, не организации.

## Состояние и ограничения

- Владелец сообщил, что App установлен, и подтвердил Issues: read and write в
  установке с выбранным репозиторием. Ранее был Members: read-only; помощник последние
  настройки независимо не проверял. Ручной read-only запуск проверки роли прошёл.
- При пользовательском токене действия относятся к человеку и App; при токене
  установки — к боту App. Бот-автор не доказывает, кто из людей отправил изменения.
- GitHub-only способ встроенного входа пока не доказан; roadmap GitHub #1153 для SPA
  OAuth помечен Paused. Варианты с банковской картой или недоступностью в РФ не
  предлагать; новые внешние сервисы, OAuth и настройки не подключать без разрешения.
- Живое применение, изменение данных, Sheets/sync, планеты и карточка A0-P — HOLD.
  Неизвестно, передавал ли владелец A0-P в другой чат: чужой чат остановить нельзя.
  Sheets пока источник; переход к данным репозитория предложен, но не включён.
- PR #344 и #346 слиты: только изолированные проверки роли и конфликтов. Модуль #344
  принимает issues.opened и проверяет sender = issue.user, но не подключён к живой
  обработке и не покрывает отправителя B в issue A. Workflow issue-owner-check.yml
  или issue_owner_check.yml не создан; app-owner-readonly.yml — ручная проверка,
  не автоматический приём заявок.
- JSON в ADM-ACCESS-PACKET — иллюстрация, не утверждённая схема; источника надёжной
  baseVersion ещё нет. Хеш снимка не доказывает неизменность, роль или авторство.
- Полнота/порядок очереди, восстановление потерянного события, edit→restore, удалённая
  история и атомарность роли/правки с записью не доказаны. При неопределённости HOLD.
  Одна тестовая issue #347 ранее разрешена и закрыта; нового разрешения на тест нет.
- Пользователь предпочитает краткие статусы и меньше воркеров для мелких задач.
  При выдаче задания укажи конкретного воркера, прежний чат и прямую карточку.
  Админ-обходы GitHub разрешаются отдельно для каждого PR, не переносить старые.
