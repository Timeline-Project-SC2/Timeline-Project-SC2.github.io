# Карточка `ADM-0` — разведка GitHub-only админки данных

> **Статус:** выдана Гайдлайнером `rc-07` 26.10.2026. **Режим:** read-only.
> **База:** `origin/main = 2fd9eb0` или новее; фактический HEAD воркер фиксирует в отчёте.
> **Волна:** [`ADM`](../waves/admin-github-issues.md). Код, данные и настройки GitHub не менять.

## 1. Цель

Собрать факты, без которых нельзя честно заморозить протокол пакета, матрицы файлов и
гейты `ADM-1…ADM-4`: инвентарь данных и схем, поверхность статического редактора,
механику workflows/ruleset/Pages и точку отключения пишущего Sheets-sync.

Готово — это не мнение «можно сделать», а компактный отчёт с привязками `путь:строка`,
таблицами схем и явным списком стоп-фактов. По отчёту Гайдлайнер выпускает `ADM-1`.

## 2. Позиция и запреты

- Ты — воркер-разведчик волны `ADM`, роли по смыслу: `rc-08` (угрозы и векторы отказа)
  + `rc-04` (доказательства). Реализацию не начинаешь.
- `OWNED_FILES`: **нет**. Не создавать ветку, коммиты, PR, issue, labels, GitHub App,
  токены и секреты. Не запускать sync и любые команды с записью в репозиторий/GitHub.
- Разрешено читать репозиторий целиком и публичные метаданные GitHub через `gh api`
  только GET-запросами. Значения секретов не запрашивать и не выводить; допустимы
  только имена секретов/переменных, если API их показывает.
- Сырой код, полные CSV/JSON и логи в отчёт не пересылать. Нужны заголовки, сигнатуры,
  имена, диапазоны строк, размеры и выводы.

## 3. Вопросы разведки

### A. Данные и схемы

Для каждого файла-кандидата в `data/` и каждого CSV/JSON, реально потребляемого сайтом,
дай таблицу: путь; формат; строки/записи и размер; назначение одной фразой; первичный ID;
поля и типы; обязательность; enum/диапазоны; исходящие связи; кто читает; кто пишет сейчас.

Отдельно классифицируй каждый файл: `редактируемый`, `конфигурация/запрещён`,
`производный/генерируемый`, `не определён`. Для редактируемых отметь защищённые и
производные поля, которые админка не должна принимать напрямую (ключи генерации, хэши,
версии, служебные отметки и подобное — по факту валидаторов, не по догадке).

Ответь таблицей связей: датасет → поле → целевой датасет/ID → что происходит при
отсутствии цели, дубликате или удалении цели. Для границ укажи представление геометрии,
порядок/замкнутость/ориентацию, допустимые координаты и где это проверяется.

### B. Канонический формат и действующие валидаторы

- CSV: заголовок и порядок колонок, разделитель, quoting, кодировка, перевод строки,
  сортировка строк, представление пустых/числовых/дата-время значений.
- JSON: сортировка ключей/массивов, отступы, финальный newline, числа и unicode.
- Все существующие команды проверки данных и публикации: команда, файл реализации,
  что именно доказывает, можно ли запускать на изменённом рабочем дереве до коммита.
- Где уже живут парсеры/сериализаторы CSV/JSON, пригодные для применителя пакета, а где
  логика продублирована между сайтом, sync и верификаторами.

### C. GitHub: workflows, ruleset, Pages, issues

Только GET-метаданные и чтение workflow-файлов:

- Каждый workflow: имя файла, триггеры, permissions, каким токеном пишет, может ли его
  push запустить Pages. Отдельно — точный существующий Pages deploy и его условия.
- Sheets-sync: workflow/скрипт, расписание и ручные триггеры, checkout-ветка, какие
  файлы пишет, как коммитит/пушит, минимальный дифф отключения именно записи.
- Rulesets/branch protection для `main`: имена правил, required checks, linear history,
  кто/что имеет bypass; есть ли уже GitHub App/бот, которому разрешён машинный push.
  Секреты и ключи не трогать; только факт наличия имён, если виден.
- Issue-инфраструктура: шаблоны, labels, ограничения и существующие автоматизации на
  `issues`; не создаст ли служебное issue цикл с другим workflow.
- Проверь по документации GitHub и локально собранному URL безопасный практический
  лимит длины `issues/new?...` для предзаполнения. Живое тестовое issue без отдельного
  разрешения владельца не создавать.

### D. Статический редактор и ревизия

- Где строится/публикуется сайт, куда встроить кнопку и отдельный редактор с минимумом
  пересечений с волной F; перечисли кандидатные новые и существующие файлы.
- Откуда опубликованный сайт берёт каждый датасет и можно ли рядом детерминированно
  получить полную ревизию коммита и/или хэши отдельных файлов без ручных `?v=`.
- Какие существующие UI-компоненты уже умеют карту, выбор точки, формы, таблицы,
  поиск и показ ошибок; что придётся создавать новым.
- Оцени размер URL пакета после URL-encoding для сценариев: одна изменённая запись,
  десять записей, одна типичная граница, худший найденный реальный объект. Дай метод
  подсчёта и числа байтов, не сами данные.

### E. Предложение по протоколу и матрицам

На основании фактов A–D предложи, ничего не реализуя:

- Точный allowlist датасетов и полей v1; типы операций; как адресовать запись; какие
  операции запретить в v1, если удаление/создание опасно для связей.
- Минимальный конверт пакета и правило канонизации/сводки.
- Состав pre-commit гейтов publisher из существующих команд.
- Черновые `OWNED_FILES`/`FORBIDDEN_FILES` для `ADM-1`, `ADM-2`, `ADM-3`, `ADM-4` и
  все пересечения с F-4/F-5/F-6.

## 4. Стоп-факты

Остановись и вынеси отдельным нумерованным списком, если найдёшь хотя бы одно:

- датасет нельзя безопасно изменить операциями без исполнения кода или ручной загрузки;
- нет стабильного ID либо связь держится на порядке строк/имени;
- опубликованный сайт не может получить точную ревизию своих данных;
- прямой App-коммит не запускает существующий Pages deploy или требует прав шире
  зафиксированных волной `ADM`;
- типичный пакет не проходит в предзаполненный issue URL;
- Sheets-sync нельзя отключить только на запись, не сломав чтение сайта;
- существующие валидаторы не проверяют результат целиком и пропуск нельзя закрыть
  внутри data-only контура.

## 5. Формат отчёта

Одна сводка не длиннее 220 строк:

1. База: HEAD, дата, подтверждение `git status --short` чист до и после.
2. Таблицы A–D с привязками `путь:строка`; для GitHub-метаданных — endpoint без секретов.
3. Предложение E и черновые матрицы.
4. Стоп-факты либо строка «стоп-фактов нет».
5. Вопросы владельцу — только те, что нельзя решить фактами репозитория.

Не прикладывай полные листинги и содержимое датасетов. Если таблица схем не входит в
лимит, сгруппируй поля по типам и дай диапазон строк источника схемы вместо дампа.
