## 1. Результат, который нужен владельцу

Вторая часть после демо-оболочки — **настоящая проверка через GitHub и запуск заявки
на изменение**. Она связывает будущий редактор, модули и их данные, но не делает вид,
что редакторы модулей, формат пакета или публикация уже существуют.

Готовый сценарий должен позволять собрать поддерживаемый черновик изменений, явно
показать его состав и исходную версию, передать его в GitHub и получить понятный
результат проверки. До отдельного решения о рабочей записи результатом этой части
является **проверенная заявка без изменения данных**, а не опубликованное изменение.
Если ни один редактор ещё не умеет собирать пакет, исполнитель предлагает минимальный
проверочный сценарий и отдельно отмечает, что настоящая отправка изменений не готова.

## 2. Где именно проверяются личность и права

1. Существующий условный код открывает только публичную демо-оболочку; его можно
   извлечь из страницы. Фраза об «расширенных правах» остаётся частью демо, рядом
   необходимо ясно пояснять, что реальных прав она не выдаёт.
2. Редактор готовит черновик локально и открывает в GitHub **предзаполненную заявку**
   (issue). Само открытие ссылки ничего не отправляет и ничего не подтверждает.
3. Пользователь входит в GitHub при необходимости, проверяет публичное содержимое и
   сам нажимает создание заявки. Автор берётся из подтверждённого GitHub события,
   а не из текста заявки, поля в браузере или демо-кода.
4. Сценарий GitHub Actions на доверенной стороне заново проверяет действующего автора
   и его полномочия для **каждой** заявки. Ранее согласованный вариант — активный
   администратор организации `Timeline-Project-SC2`; применимость проверки и её
   минимальные права нужно сверить. При недоступной проверке — отказ, не допуск.
5. Там же проверяются формат, допустимость операций и исходная версия. Результат
   виден в заявке: принят на проверку без записи, отклонён или проверка невозможна.
   Публичный комментарий об успехе не является переносимой сессией или разрешением
   на другие заявки. Никакая клиентская надпись сама по себе не подтверждает вход.

Это развитие ранее выбранного публичного размещения без собственного сервера.
Проверки личности **на экране ввода кода** и безопасной GitHub-сессии у статической
страницы нет. Если они понадобятся, потребуется отдельное решение об архитектуре.
Issues публичного репозитория тоже публичны: никаких ключей, персональных или иных
непубличных данных в заявках, ссылках, браузере, комментариях и отчётах.

## 3. Черновой контракт редактора и модулей

Формат ниже — требования к проектированию, **не утверждённая готовая схема**. После
разведки имена, типы, допустимые значения и стыки фиксируются до выдачи кодовых задач.

| Состав | Что необходимо определить и проверять |
|---|---|
| Конверт | Версия схемы, уникальный идентификатор заявки, краткое описание, исходная версия опубликованного снимка и список операций. Автор и права только из GitHub. |
| Операция | Логические идентификаторы модуля, набора данных и объекта; разрешённый вид действия и изменяемые значения. Для обновления и удаления предусмотреть проверку прежнего состояния. |
| Модуль | Явный перечень поддерживаемых типов объектов, действий, полей и собственных проверок. Путь к файлу определяется доверенным адаптером, а не присылается пользователем. |
| Связи | Проверка ссылок и зависимостей между модулями; связи данных, пространственное влияние и порядок отрисовки не смешиваются. Исходная геометрия не меняется из-за одного лишь визуального наложения. |
| Результат | Предпросмотр и сводка изменений; проверка всей партии целиком, устаревшей основы и конфликтов. Неизвестная версия или поле, несогласованные ссылки и частичная ошибка останавливают пакет. |

Создание, изменение и удаление — прежнее продуктовое направление, а не обещание
немедленного доступа ко всем данным. Для каждого модуля их нужно отдельно разрешить
и снабдить предохранителями. Нельзя принимать произвольные пути, конфигурацию,
служебные файлы или исполняемый код. Лимит размера предзаполненной ссылки и безопасный
путь для больших контуров выяснить отдельно; ничего не обрезать молча.

Google Sheets остаётся источником синхронизируемых таблиц, снимки и синхронизация не
меняются. Перед возможной записью нужна отдельная договорённость об источнике истины,
всех путях синхронизации, защите от перезаписи, откате и разрешении владельца. Планеты
на паузе; старый гейт профильной разведки `ADM-0P` не снимается этой карточкой.

## 4. Безопасность и действия владельца

- Проверять неизменяемые идентификаторы и роль автора по данным GitHub, не доверять
  указанному в заявке логину; автоматические учётные записи не допускать по умолчанию.
  Недостаточные права приложения, отсутствие ключа, ошибка API или спорный результат —
  отказ. Содержимое заявки считать враждебным и не вставлять его как команду оболочки.
- Для проверки можно использовать отдельное зарегистрированное приложение GitHub App
  с минимальными правами: членство организации на чтение и доступ к заявкам, если он
  необходим. Точный набор прав и имена секретов должен сначала подтвердить исполнитель.
  Право записи содержимого и обход защиты ветки для текущей проверки не нужны.
- Настройки приложения и ключа выполняет администратор организации **только в GitHub**:
  установка на нужный репозиторий, затем секреты сценариев в настройках GitHub. Никакие
  пароли, токены, приватные ключи или коды подтверждения не присылать в чат и не класть
  в клиент. До готовой инструкции создавать приложение и менять настройки не требуется.
- Проверочный сценарий не записывает в данные. Настоящее тестовое обращение, включение
  рабочей записи, изменение синхронизации и исключения из правил ветки — отдельные
  действия по согласованию с владельцем. Ошибки, повторные запуски и гонки не должны
  приводить к повторной или частичной публикации.

[PR #323](https://github.com/Timeline-Project-SC2/Timeline-Project-SC2.github.io/pull/323)
с прежним вариантом GitHub-only **закрыт без слияния**. Это историческая разведка,
а не установленное приложение или готовый workflow; не восстанавливать его настройки
автоматически. [PR #325](https://github.com/Timeline-Project-SC2/Timeline-Project-SC2.github.io/pull/325)
также закрыт без слияния.

## 5. Порядок и гейты

| Шаг | Роль и границы | Условие перехода |
|---|---|---|
| `A0-F` | Интерфейс и модули (`rc-03`): только чтение, `OWNED_FILES` пуст | Краткая карта текущего входа, данных, стыка и точных путей |
| `A0-G` | GitHub и риски (`rc-08`): только чтение, `OWNED_FILES` пуст | Текущие права, события, синхронизация, угрозы и пути проверены или отмечены как неизвестные |
| Подготовка реализации | Оркестратор: документация | Свести результаты, зафиксировать точную схему и непересекающиеся `OWNED_FILES`, назначить общий файл одному исполнителю |
| Реализация | Исполнители интерфейса и GitHub Actions | Запускать параллельно только после общего контракта и матрицы файлов; иначе последовательно. Без записи в рабочие данные |
| Приёмка | Независимый проверяющий (`rc-04`) | Проверки безопасности и интерфейса, четыре задания PR, реальные допущенный и отказанный сценарии по возможности; непроверенное указать |
| Подключение | Владелец и исполнитель | Настройка приложения и отдельная публичная тестовая заявка только по согласованию; без неё реальную проверку не объявлять доказанной |

Обе разведки независимы и могут идти одновременно. Они не создают файлов, коммитов,
заявок и приложений; правило первого коммита к ним неприменимо. Для кодовых задач
первый содержательный коммит — в свой разрешённый файл, затем push в разрешённую
ветку и запрос на изменение; остановка до слияния. Общие шаблоны, `package.json`,
сценарии `.github/workflows/`, данные и централизованную документацию нельзя делить
между воркерами без явного единственного владельца.

Минимум проверок: настоящий автор против подставленного имени; активный администратор,
не-администратор и отказ API; отсутствие секретов; невалидная или устаревшая партия;
повтор и гонка; чрезмерный размер; отсутствие записи при любой ошибке; явное подтверждение
на GitHub; доступность на телефоне и с клавиатуры. Успешные имитации не заменяют
реальной проверки после настройки приложения. Не объявлять вторую часть завершённой,
пока подтверждённый пользователь не отправил реальную проверочную заявку и не увидел
результат, а передача настоящего пакета изменений остаётся неподтверждённой.
