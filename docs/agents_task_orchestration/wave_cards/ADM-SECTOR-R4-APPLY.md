# ADM-SECTOR-R4-APPLY (Р4): занесение изменений по отчётам Р2 и Р3

> **ID:** `ADM_SECTOR_R4_APPLY_V1` · **Место:** отдельная выдача, **не** часть цепочки 1-2-3.
> **Условие выдачи:** получены отчёты **Р2 и Р3** (отчёт Р2 — дословно, отчёт Р3 — как есть). Отчёт Р1 **не** передаётся; детали карточек Р1–Р3 не раскрываются — «без деталей второго».
> **Вход:** только эти два отчёта и актуальный `main`. Ничего не додумывать «из кода» сверх отчётов.
> **База:** `origin/main = 3554e92` ([PR #359](https://github.com/Timeline-Project-SC2/Timeline-Project-SC2.github.io/pull/359)); активная ветка сессии с влитым `main`.
> **Адресат:** назначается владельцем при выдаче. Язык — русский.

## 1. Цель

Внести **минимальные подтверждённые правки в документы**, чтобы они соответствовали факту из отчётов Р2 и Р3. Всё, что требует решения владельца или выходит за документы, — не вносить, а вынести в отчёт как `предложение`.

## 2. Порядок работы

1. Прочитать оба отчёта; составить список правок, где для каждой есть `файл:строка`, формулировка «было → стало» и ссылка на пункт отчёта Р3, подтверждённый отчётом Р2.
2. Отсечь пункты с пометкой «требует решения владельца», исторические записи и всё, что касается кода, данных, тестов, CI и настроек.
3. Вносить правки по одной, после каждого завершённого шага `git commit` + `git push` по `AGENTS.md` §6; не делать `reset` и force-push, не менять ветку.
4. Подготовить PR в `main` (только по правилу PR-only). **Слияние, `--admin`, публикация и живое применение — только по отдельному решению владельца.**

## 3. Контур владения файлами

`OWNED_FILES` — только документы, явно перечисленные в отчёте Р3:

- `CHANGELOG.md`, `docs/HANDOFF.md`, `docs/handoff/status-and-state.md`;
- `docs/stages/stage-09-12-sector/todo.md`, `plan-to-close-sector.md`, `notes/*`;
- `docs/admins/*`, `docs/agents_task_orchestration/README.md`, `docs/agents_task_orchestration/wave_cards/*`;
- `docs/concepts/*`, `docs/README.md`, `docs/registers/*` — **только если** указаны в отчёте Р3.

`FORBIDDEN_FILES` — всё остальное: `src/*`, `site/*`, `tools/*`, `tests/*`, `data/*`, `.github/*`, `package.json`, `package-lock.json`, настройки и rulesets. Файлы отчётов не создавать: отчёты передаются текстом.

## 4. Что проверить перед каждым коммитом

- `git status --short` и `git diff --name-only origin/main...HEAD`: каждый путь обязан входить в `OWNED_FILES`.
- `git diff --check` — без ошибок.
- `python3 tools/check_docs.py` — `OK`; новые документы должны иметь входящую ссылку, лимит 200 строк и один H1.
- Ни одного изменения в коде, данных, тестах, workflow, правилах и настройках.

## 5. Режим проверок

По решению владельца от 05.11.2026 — только критический минимум: `npm run build`, короткий ручной smoke `/`, `/sector/`, `/sector/admin-edit/`, `git diff --check`, `tools/check_docs.py`, сверка затронутых файлов. Полный набор тестов, браузерные сценарии, доступность, телефон, производительность, визуальная приёмка и независимый критик — `TODO (конец сессии)`, не запускать. Новые тесты не добавлять.

## 6. Формат отчёта

До **30 строк**, метки `доказано / наблюдение / предложение / выбрано`: база и `HEAD`; что внесено с точными файлами; что отклонено и почему; что оставлено владельцу; итоги `tools/check_docs.py` и `git diff --check`; номер подготовленного PR (если создан) и явная пометка «слияние не выполнялось».

## 7. Границы

Живое применение и публикация, живые Sheets/sync, планеты, OAuth/App/секреты/workflow/сервер, тестовые данные и новые issue, Submit, общая запись, `baseVersion`, очередь, `edit→restore`, атомарность, вторая модерация, слияние/закрытие PR #348 — `HOLD`. Исторические записи не стирать; расхождения решать сложением, а не переписыванием истории. Если отчёты противоречат друг другу — не выбирать самому, а вынести `предложение` владельцу.
