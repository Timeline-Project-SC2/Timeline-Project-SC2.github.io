## Цель и разделение ролей

У каждого администратора своя публичная issue; код позволяет найти её, но не
авторизует. Администратор может поделиться кодом для сравнения или будущей
совместной работы. Создание и сохранение черновика не равны финальному Submit.
После него в очереди первой должна идти первая отправленная заявка, а не первая
начатая сессия или первый запустившийся Actions.

| Действие | Чья личность / право нужны |
|---|---|
| Открыть и сравнить публичный черновик | Публичное чтение; идентификатор не даёт права изменять данные. |
| Создать issue от имени администратора | GitHub-сессия на самом GitHub или пользовательский токен App; автором должен быть человек, не подпись в тексте. |
| Внести изменения в чужую issue | Авторизованный пользователь с фактическими правами GitHub; отдельно определить доверенного отправителя и проверить его роль. |
| Подтвердить результат комментарием | Токен установки App; GitHub покажет бота App. Это не авторизация отправителя. |
| Применить заявку | Доверенная проверка личности и роли активного Owner **организации**, данных, базы и неизменности после Submit; не роль администратора репозитория. |

[Пользовательский токен App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app#use-the-appropriate-token-type)
ограничен правами **и пользователя, и App** и приписывает действие пользователю и
приложению. Токен установки приписывает действие боту. Если бот создаст issue сам,
её автором станет бот: проверка из #344 для `issues.opened` с `sender = issue.user`
не докажет, кто из людей отправил данные. Не обходить права человека токеном бота.

## Два пути создания по шаблону

**A. Отложенная альтернатива без входа в редактор.** Страница формирует ссылку на
[форму GitHub с заполненным заголовком и телом](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue#creating-an-issue-from-a-url-query).
Администратор сам входит в GitHub и подтверждает создание, поэтому GitHub видит его
автором. Это дополнительный ручной переход, а не бесшовная запись или синхронизация;
страница автоматически не получает номер созданной issue. Содержимое URL попадает в
историю и может превысить лимит GitHub; секреты в URL запрещены. До финального Submit
issue должна оставаться черновиком. Публичная форма GitHub сама по себе не запрещает
посторонним создать issue и не обеспечивает условие «общие черновики пишут только
администраторы»; принимать можно только проверенные заявки Owner. Это ограниченный
временный вариант для сравнения, а не утверждённое конечное решение.

**B. Вход внутри редактора — выбранное направление.** GitHub App выполняет пользовательскую
[web-авторизацию](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#using-the-web-application-flow-to-generate-a-user-access-token):
администратор подтверждает доступ GitHub, приложение получает проверяемую личность,
а запрос на создание работает в пределах прав пользователя и App. Редактор должен
сам собрать `title`/`body` по утверждённому шаблону: API создания issue принимает эти
поля, а не гарантирует применение GitHub issue form. Проверку Owner проводить в
доверенном контуре до записи общего черновика и отдельно в точках обработки заявки.

Для обычного web-flow GitHub требует `client secret`, а также рекомендует `state` и
PKCE. GitHub Pages — статический хостинг; в опубликованных файлах нельзя хранить
приватный ключ App, client secret, токены или сессии других пользователей. Поэтому
этому варианту нужен безопасный обмен кода и хранение секретов вне страницы, например
в доверенной серверной функции; место, стоимость, домен и способ сессии не выбраны.
Обходные варианты не объявлять готовыми. Device flow без отдельного решения не
включать: GitHub рекомендует его для headless-клиентов и отмечает риск фишинга.

### Предварительные варианты защищённого компонента

Интерфейс сайта остаётся на GitHub Pages. Кандидаты ниже — только чтение тарифов,
не выбор провайдера и не создание аккаунта; доступность регистрации и конкретная
стоимость для владельца не проверены. Сессии, защита CSRF, отзыв, лимиты хранения и
атомарное одноразовое использование состояния требуют отдельного проектирования.

| Вариант | Условия по официальной документации на 01.11.2026 |
|---|---|
| [Cloudflare Workers Free](https://developers.cloudflare.com/workers/platform/pricing/) | До 100 000 запросов в день и 10 мс CPU на вызов; при превышении [выдаётся ошибка](https://developers.cloudflare.com/workers/platform/limits/). Хранилища имеют собственные лимиты. |
| [Netlify Free](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/) | 300 общих кредитов в месяц с жёстким пределом; функции входят в план, вычисления и трафик расходуют кредиты. После лимита проекты могут быть [приостановлены](https://docs.netlify.com/manage/accounts-and-billing/billing/resume-paused-projects/). |

Квота запросов сама по себе не доказывает безопасность или нулевую стоимость решения;
при недоступном компоненте вход и запись должны останавливаться, а не обходить проверку.

## Что предстоит

1. **Права и установка.** Владелец подтвердил `Issues: read and write` в установке и
   выбор нужного репозитория; помощник независимо настройки не проверял. `Members:
   read-only` — прежнее право для проверки роли. `Issues:write` шире комментариев:
   оно позволяет менять другие issues выбранных репозиториев. Не запрашивать ключи,
   токены, OAuth-коды или пароли в чате.
2. **Безопасный обмен.** Владелец выбрал бесшовную web-авторизацию, но не выбирал
   хостинг, сервис, хранение сессии или стоимость. Сравнить варианты защищённого
   компонента; перед созданием, платой, callback или живой интеграцией получить
   отдельное решение владельца.
3. **Спроектировать границы.** Установить пользователя через GitHub, проверить Owner
   через доверенный контур, описать защиту сессии, `state`/PKCE, отказы и отзыв доступа.
   Определить точные файлы будущего редактора и контракт шаблона; не доверять полям
   `author`, коду issue, кнопке в браузере или отображённому логину как доказательству.
4. **Отдельно спроектировать Submit и журнал.** `issues.opened` создаёт черновик и не
   должен автоматически применять его. Когда B отправляет данные в issue A, проверить
   фактического отправителя B; модуль #344 этот случай не покрывает. После Submit до
   записи правка заголовка/тела блокирует применение; исправление — новая issue.
   Сохранить приоритет первой отправки и `HOLD`, пока полнота очереди и отсутствие
   правок/гонок не доказаны. Отдельный комментарий бота не меняет тело заявки.
5. **Проверять поэтапно.** Сначала фиктивные данные и тесты без сети или записи,
   затем независимая проверка безопасности перед реальным OAuth. Создание тестовой
   issue, изменение настроек и подключение живой обработки — только после отдельного
   разрешения владельца. Текущий источник Sheets и sync не менять.

## Критерии будущей реализации

- Нет входа, пользователь отменил доступ, роль не Owner, API недоступен или ответ
  неоднозначен → запись общего черновика и применение запрещены; ошибка видна человеку.
- GitHub удостоверяет пользователя, а защищённый контур проверяет его текущую роль;
  публичный идентификатор и браузерный UI не становятся источником полномочий.
- Токены и секреты не оказываются в репозитории, браузерном коде, ссылках или логах;
  сессия, OAuth callback, CSRF и повторный вход рассматриваются отдельно. Доступ к
  чужому черновику не означает разрешение его изменить или обойти очередь.
- Результат в issue формируется из подтверждённой записи; публикация подтверждается
  отдельно. Учитываются лимиты, уведомления, повторы событий и циклы от комментария
  бота. Неопределённый исход нельзя считать ни успехом, ни отказом и повторять вслепую.
