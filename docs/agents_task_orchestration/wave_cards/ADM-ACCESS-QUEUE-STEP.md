## Итог A0-M и уточнение

Воркер предложил цепочку от исходного события и журнала до проверки, записи и
подтверждённой публикации. Автор и Owner проверяются по доверенным источникам;
комментарий сам по себе ничего не доказывает. На имеющихся свидетельствах полнота,
порядок Submit и отсутствие правок не доказаны: живая очередь остаётся `HOLD`.

| Сценарий | Вывод A0-M |
|---|---|
| Первая заявка задержана или потеряна; порядок двух неразличим | Не применять конкурирующие заявки наугад. |
| `edit→restore` или удалённая история | При неизвестности не применять; исправление — новой issue. |
| Одна база, одно поле | При доказанном порядке — первая допустимая заявка, вторая конфликтует. |
| Одна база, разные поля | Возможны только последовательная проверка и повторная валидация общего результата. |
| Повтор или таймаут после записи | До сверки с журналом и источником данных повторную запись запретить. |

Уточнение: новый приёмник или журнал **сами по себе** не доказывают, что GitHub
доставил все события, установил порядок отправки или сохранил всю историю правок.
Срок ожидания и отказ отдельной заявки также не доказывают отсутствия пропущенной
более ранней заявки и не разрешают автоматически продвигать очередь. Между проверкой
роли/issue и записью остаётся гонка; её допустимость владелец не выбирал. Пока Sheets —
источник, sync может перезаписать результат записи в репозиторий.

Воркер предложил модель `decideQueue(snapshot)` с условным `ready`. Чтобы не
подменить недоказанные гарантии фиктивными флагами, следующий шаг более узкий:
только проверка конфликта переданных значений, без решения о готовности к записи.
[Ограничения доставки](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks) ·
[история правок](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/editing-an-issue) ·
[concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) — источники из отчёта воркера.

## Проверка метаданных правки, 01.11.2026

По разрешению владельца создана публичная тестовая [issue #347](https://github.com/Timeline-Project-SC2/Timeline-Project-SC2.github.io/issues/347)
с фиктивным текстом. Интеграция помощника получила `403` при редактировании; владелец
сам изменил заголовок и описание, восстановил их и закрыл issue. Права и настройки не
менялись; этот отказ не устанавливает права зарегистрированного проектного App.

До правок GraphQL показывал `lastEditedAt: null`, ноль элементов `userContentEdits`
и переименований. После возврата оба текста вновь совпали с исходными, но дата
`lastEditedAt` осталась непустой, появились три записи `userContentEdits` (включая
создание) и три `RenamedTitleEvent`; `hasNextPage: false`.

Затем владелец удалил одну тестовую ревизию. Повторный запрос показал у неё и время
правки `editedAt`, и время удаления `deletedAt`; `lastEditedAt` и три события
переименования сохранились, issue осталась закрытой, исходные тексты — восстановлены.
В ответе этой GitHub-интеграции поле `diff` удалённой ревизии равно маркеру `deleted`;
содержимое не выводилось, видимость другим пользователям не проверялась. Это наблюдение
одного случая, не гарантия полноты и не атомарная проверка.

GitHub [документирует](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment),
что при удалении содержимого ревизии в истории остаются автор и время; максимум —
100 правок с исходной и 99 последними версиями. Гарантия доступности признаков
через API во всех случаях, при другой видимости и после усечения истории не установлена.

Для восстановления: GitHub [разрешает повторную доставку](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks)
попыток webhook за последние три дня, но сам не повторяет неудачные доставки. Это
относится к настроенному webhook, не автоматически к триггеру Actions; его настройка
и отдельный приёмник не выбраны. [Общий Events API](https://docs.github.com/en/rest/activity/events)
ограничен 300 событиями за 30 дней, а [IssuesEvent](https://docs.github.com/en/rest/using-the-rest-api/github-event-types#issuesevent)
не перечисляет `edited`; его нельзя считать полной историей правок или очередью.
