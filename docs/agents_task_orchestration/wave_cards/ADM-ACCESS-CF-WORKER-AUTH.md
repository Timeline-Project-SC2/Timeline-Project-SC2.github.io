## 2. Что выбрано владельцем 02.11.2026

1. Снят прежний запрет на внешний сервис/доступ через zapret **в части этого сценария**. Админы обеспечивают доступ к `*.workers.dev`; вопрос «что именно добавлять в zapret» отложен владельцем и в эту карточку не входит.
2. Подключается **Cloudflare Worker как узкий OAuth-посредник**: только для входа в GitHub и автоматического создания/отправки issue после подтверждения в панели. Не прокси всего сайта, не постоянный рантайм Pages, не отдача контента.
3. Владелец сообщил оценку «установка на 100 000 запросов в месяц, бесплатно». Это **решение/оценка владельца**, не доказанный факт: воркер должен сверить лимит с официальной документацией и отделить документированную гарантию от наблюдения.
4. Целевой UX не меняется: правки → подтверждение в панели → вход/разрешение GitHub при необходимости → автоматическое создание issue → проверки → автоматическое применение и публикация **без второй ручной модерации**. Автоматизация — «насколько это возможно»; неподтверждённые шаги не выдавать за готовые.
5. Ручная предзаполненная форма GitHub — не выбранная замена. Общая корневая issue и общий код группы не предполагались; код issue не авторизация.

**Наблюдение:** без zapret/VPN тестовый `*.workers.dev` даёт `ERR_CONNECTION_RESET`; по словам владельца, с доступом работает. Сеть в этой задаче не проверять.

**Доказано только по документации/метаданным:** обычный web-flow GitHub App требует `client_secret` и callback URL; installation token приписывает действие боту App, user token — человеку и App; SPA-режим roadmap #1153 остаётся `Paused`; факт живой реализации в проекте отсутствует.

## 6. Критерии будущего теста — не запускать сейчас

Тест только после отдельного сигнала владельца о готовности редактора; сервер в песочнице не поднимать.

1. С настроенным доступом `*.workers.dev` открывается; без доступа остаётся наблюдавшийся `ERR_CONNECTION_RESET`.
2. Вход → GitHub → согласие → callback без ошибок.
3. В URL, логах, issue и браузерном коде нет `client_secret`, приватного ключа, токена, OAuth-кода и непубличных данных.
4. После подтверждения в панели issue создаётся автоматически; автором показан человек, не бот.
5. Проходит только активный Owner организации; repo-админ, неактивный и не-Owner не проходят.
6. До Submit черновик правится; после Submit правка блокирует старую заявку → нужна новая issue; без доказательства неизменности — стоп.
7. Результат виден в той же issue, комментарий от бота App; при успехе нет второй ручной модерации, при сбое — честный статус без слепого повтора.
8. Сайт остаётся доступен без Worker; Worker не отдаёт контент и не проксирует весь домен.
