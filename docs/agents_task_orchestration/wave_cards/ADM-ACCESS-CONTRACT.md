## 1. Сценарий и граница

Редактор подготавливает локальный черновик и открывает **новую предзаполненную issue**;
пользователь входит в GitHub и сам нажимает Submit. Открытие ссылки — не отправка.
GitHub Actions проверяет оригинальный снимок и автора; автоматический служебный
аккаунт оставляет результат в той же issue. Проверка привязана к заявке, а не
устанавливает сессию на сайте. Сам комментарий не выполняет запись рабочих данных.

Конечная цель — автоматическое применение изменений после проверок, не ручное
рассмотрение: [общая цепочка](ADM-ACCESS-AUTO.md). Этот документ описывает только
контракт авторства, а не готовый применитель. При реализации нельзя доверять старому
комментарию как разрешению записывать; рабочая запись пока не подключена.

Заявка, комментарий и журналы могут быть публичны. Перед Submit пользователь должен
увидеть предупреждение, что текст, автор и результат проверки могут раскрыть его роль,
даже если членство в организации скрыто; никаких секретов и непубличных данных.
Формат и размер предзаполненной ссылки ещё предстоит проверить: переполнение нельзя
молча обрезать. Непланетарный формат разрешено проектировать отдельно от `ADM-0P`;
планеты на паузе, реальный запуск записи требует отдельного согласования.

## 2. Доверенные входы и идентичность

- Только GitHub-событие `issues.opened` целевого репозитория
  `Timeline-Project-SC2/Timeline-Project-SC2.github.io` от кода доверенной основной
  ветки. `edited`, `reopened`, комментарий, ручной dispatch и данные браузера не дают
  нового подтверждения. События и состав payload — по документации GitHub [2](https://docs.github.com/en/webhooks/webhook-events-and-payloads).
- Предлагаемый технический маркер заголовка `[ADM-ACCESS] ` отбирает предназначенные
  заявки; это **не** доказательство прав. Без маркера не проверять членство и не
  комментировать обычные issue. Точный маркер нуждается в проверке стыка UI и Actions.
- Сверить стабильные ID репозитория, организации, issue, `sender` события и автора
  исходного снимка; `sender.id` должен совпасть с `issue.user.id`, тип — человек, не bot.
  Запрос текущей issue должен вернуть ту же issue и того же автора. Данные автора из
  текста, маркера или произвольного имени не использовать как идентичность.
- Получить членство в конкретной организации `Timeline-Project-SC2` через доверенный
  GitHub API и проверить совпадение ID пользователя и организации, `state=active`,
  `role=admin` (Owner организации, не админ репозитория). ID сверяются без потери
  точности; логин используется для адреса API, но не как единственный идентификатор.
- При отсутствии обязательного поля, ошибке/неполном ответе API, противоречии ID,
  неподходящем событии или неопределённой роли — **не подтверждать**.

## 3. Снимок, правки и повторная отправка

Подтверждаемый снимок должен включать как минимум исходные ID организации,
репозитория, issue, автора и точные `title` и `body` из события открытия. Заголовок
и тело сверяются с текущими значениями до публикации результата; пробелы, переводы
строк, Unicode и отсутствие поля нельзя незаметно нормализовать или сливать с пустой
строкой. Единственное подтверждаемое содержание — `title` и `body`: метки, исполнители,
поля GitHub, комментарии, файлы по ссылкам и внешние ресурсы не являются инструкциями
и не подтягиваются. Заявку, смысл которой зависит от них, нельзя подтверждать молча.
Изменение прочих метаданных не подтверждает новое содержимое.

Кандидат идентификатора версии — SHA-256 однозначного версионированного представления
этих полей, с UTF-8 и разделением длин, без усечения. Точное представление байтов,
обработка `null`, лимиты и тестовые векторы **не согласованы**: критик должен их
оценить до назначения кодовых задач. Хеш — метка снимка, не подпись автора и не
доказательство отсутствия промежуточных правок.

Любое редактирование `title`/`body` после Submit делает прежнее подтверждение
неприменимым. Даже автору для исправления требуется отправить новую issue; `reopened`
или очередная проверка автора старой issue не утверждают новую версию. При сравнении
обнаружено расхождение — не подтверждать. Закрытая issue не получает подтверждение
как открытая; порядок и смысл повторных событий отдельно оцениваются.

**Открытый блокер:** совпадение двух снимков не доказывает отсутствие правки и
возврата текста. Источник полной истории заголовка и тела, его права, полнота,
пагинация и доступность не доказаны. Нельзя превращать отсутствие обнаруженного
расхождения в гарантию «не редактировалось». Если условие нельзя надёжно установить,
не выдавать успешный результат; отдельно оценить задержанные и пропущенные события.

Кандидат для исследования: GraphQL `userContentEdits`/`lastEditedAt` тела приведён в
обсуждении GitHub [4](https://github.com/orgs/community/discussions/33551); для
заголовка документирован `renamed` [1](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types).
Это ориентиры, не доказательство полноты, своевременности или фактических прав App.

## 4. Результат и срок его действия

После проверки исходного события повторно прочитать текущую issue и членство как
можно ближе к выдаче результата. Зафиксировать отдельные времена обоих чтений:
они последовательные и **не атомарные**. Варианты публичного результата:

- `подтверждено` — только при выполнении всех условий выше для исходного снимка;
- `не подтверждено` — достоверный отказ по условиям авторства или роли;
- `проверить не удалось` — недоступное доказательство, ошибка API, таймаут или спорный
  ответ, включая неоднозначные 403/404/429; никогда не превращать его в успех;
- `изменено` — содержание не совпало с исходным; нужна новая issue.

Каждый комментарий указывает номер issue, версию исходного снимка, время проверок и
смысл: «это результат на указанные моменты, не разрешение применить изменения».
Правка или отзыв роли могут произойти после чтения. Старый комментарий GitHub сам не
исчезнет и не должен выглядеть как доказательство текущего содержимого или прав;
способ безопасно донести это до пользователя — часть критического гейта. Если
комментарий не удалось создать, отсутствие ответа не считается подтверждением.

Повтор запуска не является новой отправкой. Результаты связываются с ID события/issue,
версией снимка и попыткой запуска; нельзя выбирать «последний комментарий» как истину.
Без устойчивого состояния нет гарантии единственного комментария или упорядочивания;
повтор и конкурирующие события нужно явно проверить. Будущий автоматический применитель
нуждается в доверенных проверках прав и снимка перед записью. Отдельное согласование
требуется для **включения** живой записи, не для ручного утверждения каждой заявки.

## 5. Права и недоверенные данные

- Отдельный GitHub App с организационным `Members: read` — кандидат для чтения роли;
  фактические установка, политика, доступность и точные настройки не проверены.
  Стандартному `GITHUB_TOKEN` не предполагаются права на членство организации.
- Для ответа в issue нужен токен с `Issues: write`; GitHub не ограничивает этот уровень
  только публикацией одного комментария [1](https://docs.github.com/en/rest/reference/permissions-required-for-github-apps).
  Возможен отдельный минимально ограниченный `GITHUB_TOKEN` при разрешённой политике.
  `Contents: write`, секреты в браузере, публичный PAT и обход защиты не нужны.
- Работать только с доверенным кодом основной ветки; не исполнять текст issue, не
  вставлять выражения из события в shell и не использовать произвольные пути/URL.
  Ограничить запросы и размеры, не логировать тело, токены и подробности членства.
- Комментарий от постороннего аккаунта, имитация служебного текста и снимок с неверным
  репозиторием недоверенны. Конкретная неизменяемая идентичность служебного аккаунта и
  способ её проверки ещё должны быть определены; текст комментария сам по себе не ACL.
