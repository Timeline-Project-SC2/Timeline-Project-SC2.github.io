## 1. Цель и проверяемые критерии готовности

Сделать джоб `scripts` бинарной: каждый её шаг либо честно зелёный, либо блокирует PR.
Известные 8 планетарных падений остаются исполняемыми, но переводятся в явную базу, выход за
которую краснеет; `lint` и `check:planet-core` начинают реально выполняться в CI.

**Готово = одновременно:**

1. Монолитный `run:`-блок джобы `scripts` разбит на именованные шаги; в прогоне PR все шаги
   джобы `scripts` имеют conclusion `success` (доказательство — выгрузка jobs API в отчёте).
2. Страж базы: при текущем наборе тестов шаг зелёный и печатает 8 имён из базы; любое падение
   вне базы или устаревание базы (исчезновение базового падения) — ненулевой код с именами.
3. `check:planet-core` и `lint` — отдельные шаги джобы, реально отработавшие (`success` в API),
   а не скрытые за обрывом.
4. ESLint распространён на `tools/**` и `tests/**` (правило `no-undef`, стилевых правил не
   добавлять); `node --check` охватывает все `tools/**/*.mjs` и `tests/**/*.{mjs,js}`.
5. 8 планетарных тестов **не тронуты**: никаких `skip`/`todo`/правок их кода; полный прогон
   `npm test` сохраняется (страж вызывает тот же список файлов из `package.json`).
6. `git diff --name-only origin/main...HEAD` — только 6 файлов из §3. `verify:docs` зелёный.

**Не входит (E6):** починка 8 планетарных падений (`И-11`, контур `rc-02`), ужесточение
бенчпорогов `planet-perf`, правки других workflow (`pages.yml`, `assets.yml`, `sync.yml`),
любые изменения `src/`, `site/`, `data/`.

## 2. Границы роли

- Контракт §4 противоречит фактическому поведению — **стоп и вопрос**, не догадка. Лимит попыток —
  три, третья неудача — эскалация владельцу.
- Правило минимального изменения: никаких новых ESLint-правил кроме распространения `no-undef`,
  никакого рефакторинга тестов и верификаторов «заодно».
- Находки `no-undef` в `tools/`/`tests/` чинятся точечно; если находка требует поведенческой
  правки или ослабления правила — стоп и эскалация, отключать правило запрещено.

## 4. Контракт до буквы

### 4.1. Структура джобы `scripts` в `check.yml`

После `actions/checkout` и `setup-node` — отдельные именованные шаги (имена по-русски, как в
джобе `build`):

1. `npm ci` — отдельным шагом.
2. «Проверка типов» — `npm run typecheck`.
3. «Синтаксис скриптов» — существующий цикл `node --check` по `site/**/*.js`, плюс такие же
   циклы по `tools/**/*.mjs` и `tests/**/*.mjs`, `tests/**/*.js`; явный вызов
   `travel-planner.test.js` убирается (покрывается циклом).
4. «Верификатор: адреса сектора» — `npm run verify:address`.
5. «Верификатор: ядро сектора» — `npm run verify:sector-core`.
6. «Верификатор: ноль растра» — `npm run verify:no-raster`.
7. «Тесты node:test со стражем базы» — `node tools/check_test_baseline.mjs`.
8. «Wasm-ядро planet-core: сверка байтов» — `npm run check:planet-core`.
9. «Линт ESLint (site, src, tools, tests)» — `npm run lint`.

Старый комментарий про «верификаторы стоят ДО npm test намеренно» удаляется: причина исчезла,
вместо него — короткий комментарий о страже базы со ссылкой на `known-test-failures.json`.

### 4.2. Страж `tools/check_test_baseline.mjs`

- Читает `scripts.test` из `package.json`, разбирает её на аргументы и запускает ту же команду
  `node --test ...` с добавлением `--test-reporter=tap` (список файлов не дублируется —
  единственный источник остаётся в `package.json`).
- Парсит TAP: имена из строк `not ok N - ...` с учётом вложенности (полное имя подтеста).
- Множество фактических падений сравнивает с базой `known-test-failures.json`:
  - совпало полностью — выход `0`, в лог строка «известные падения: 8/8 по базе, новых нет»;
  - есть падение вне базы — выход `1`, секция «НОВЫЕ ПАДЕНИЯ:» с именами;
  - имя из базы не упало (починка/переименование) — выход `1`, секция «БАЗА УСТАРЕЛА:»
    с требованием обновить JSON в этом же PR;
  - крэш процесса тестов (не-нулевой выход без TAP-итогов) — выход `1`, отдельное сообщение,
    под базу не маскируется.
- Без сети, без `Math.random`/времени; детерминирован; русский текст лога.

### 4.3. База `tools/known-test-failures.json`

Массив из ровно 8 объектов, поля: `name` (точное TAP-имя из прогона шага 0), `file`,
`contour: "планетарный"`, `knownSince` (идентификатор этапа: Stage-8.5, Stage-8.10b, A-17,
W26b, контракт ядра — с числом повторов ×2, где они есть). Никаких имён сектора/атласа в базе
быть не должно.

### 4.4. ESLint для `tools/**` и `tests/**`

- Новый блок flat-config: `files: ['tools/**/*.mjs', 'tests/**/*.mjs']`,
  `sourceType: 'module'`, `languageOptions.globals: globals.node`
  (плюс `globals.nodeTest`, только если шаг 0 покажет использование глобального `test` без
  импорта — иначе не добавлять).
- Для `tests/travel-planner.test.js` — отдельный блок с фактическим `sourceType`
  (определить на шаге 0: модуль или script/commonjs).
- Единственное правило — `'no-undef': 'error'`, как в существующих блоках. Шапка-комментарий
  про локальный запуск TS6 обновляется, если алиас `typescript` в `package.json` уже даёт TS6
  из `npm ci` (проверка шага 0).
- `package.json`, строка `lint`: `eslint site src tools tests`.

### 4.5. Self-test стража `tests/check-test-baseline.test.mjs`

На синтетических TAP-строках (фикстуры в самом тесте, реальный набор не запускается):
зелёный случай «ровно база»; красный — новое имя; красный — устаревшая база; красный — крэш;
проверка разбора `scripts.test` из `package.json`. Файл добавляется в строку `test`
(`package.json`), счётчик файлов становится 37.
