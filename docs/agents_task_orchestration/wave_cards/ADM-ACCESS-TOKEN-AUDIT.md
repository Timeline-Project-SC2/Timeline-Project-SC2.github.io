## Задание: воркер 2 (A0-G / A0-H / A0-K) → A0-K2

Задание выполнено в **прежнем чате воркера 2**, не независимого критика; текст ниже
исторический, повторно не выдавать. Цель — выяснить, можно ли безопасно сузить права
встроенного токена, не нарушив CI, sync и публикацию сайта.

~~~~text
Ты — воркер 2, продолжение A0-G/A0-H/A0-K. Новая задача A0-K2: read-only аудит
перехода на минимальные права GITHUB_TOKEN. Результат — факты и план, не код.

База: origin/main 70cd3c19f98faac79974fd9b5cc258976acf1a92. Выполни read-only
fetch origin main, укажи HEAD своей ветки, origin/main и SHA реально прочитанного
снимка. Если main изменился — сообщи расхождение, не переноси старые выводы. При
различии HEAD и базы читай файлы именно из зафиксированного main, например git show
<проверенный-SHA>:<путь>; состояние локального worktree отдельно укажи.

OWNED_FILES: пусто; FORBIDDEN_FILES: все. Не меняй ветку, файлы, настройки, правила,
секреты, права, App, Sheets и данные. Не запускай workflows, sync, тесты, сборки или
код, не создавай PR и issue. Не запускай настоящий App и не проверяй реальных членов.
Не обращайся к спискам секретов через API/UI, не проверяй их наличие, не читай
значения, токены, ключи или секретные логи. Если имя секрета встретится в исходнике,
не публикуй его: в отчёте назови только тип «отдельный секрет».
Разрешены только чтение исходников, Git-метаданных и официальных документов; 403 —
неизвестно, доступ не повышать.

Факты от владельца: App виден в списке установок организации; на прежнем снимке
Read access to members и No repositories, но аккаунт на том кадре не виден. Ключ
скачан; его размещение не подтверждено. В репозитории есть второй администратор.
По экрану Actions: разрешены все actions, глобальное требование полного SHA выключено;
fork PR от первого вкладчика требует одобрения. Workflow permissions выбран Read and
write; опция создания/одобрения PR через Actions на экране не отмечена и недоступна
для изменения. Секреты на снимке имеют скрытые значения; их не исследовать.

Проверь все существующие .github/workflows/*.yml и *.yaml на указанной базе и только
необходимые вызываемые локальные файлы, не исполняя их. Для каждого workflow/job:
1. Триггеры, явные permissions на уровне workflow/job или отсутствие декларации;
   отдельно checkout credentials и использование GITHUB_TOKEN. Укажи путь:строка.
2. Нужные реальные операции и от какого типа учётных данных они зависят: встроенный
   токен, отдельный секрет или не установлено. Не публикуй названия секретов.
   Разбери CI для fork и внутренних PR, sync по расписанию/dispatch и публикацию Pages.
3. Что потенциально изменится при default Read repository contents and packages:
   каждый работающий job — «зависит / явно определён / неизвестно», последствия для
   сайта, CI и sync. Не делай вывод о фактических runtime-правах только по настройке:
   учитывай overrides, политику организации и ограничения событий. Не используй логи.
4. Проверь наличие и покрытие .github/workflows/actions.lock и refs actions: теги сами
   по себе не полные SHA, но GitHub workflow dependency lockfile может закреплять action
   и удовлетворять политике для покрытого workflow. Не создавай lockfile и не ставь
   расширения. Отличай reusable workflows и транзитивные зависимости; где данных нет —
   неизвестно. См. https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles
5. Составь поэтапный план перехода к least privilege: конкретные минимальные разрешения
   по каждому job с обоснованием, какие могут потребовать будущей правки, независимая
   проверка и безопасные проверки совместимости прежде, чем владелец изменит default.
   Покажи отдельно, что нельзя доказать без запуска. Не включай глобальный SHA-флажок,
   не изменяй существующий отдельный секрет и не предлагай обход защиты main.

Учти, что официальный GitHub разрешает задавать permissions на уровне workflow/job,
при явном перечислении остальные права становятся none; token доступен action также
через github.token без явной передачи. Read-only default не обязательно запрещает
workflow запросить отдельные write-права, но политики организации и событие могут
ограничить результат. Проверь по документации:
https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions
https://docs.github.com/en/actions/tutorials/authenticate-with-github_token

Итог до 25 строк: SHA и чистота worktree; таблица workflow/job → триггер → текущая
декларация → необходимая операция/тип токена → риск при смене default; точные пути и
строки, lockfile, вывод «можно / HOLD / неизвестно», порядок безопасных шагов и что
не проверено. Никакой второй ручной модерации каждой пользовательской issue; прежние
HOLD на размещение ключа, реальный тест и живую запись остаются.
~~~~
