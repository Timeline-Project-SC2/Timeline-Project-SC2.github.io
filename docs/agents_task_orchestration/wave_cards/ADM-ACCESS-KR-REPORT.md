## 1. База и границы

По отчёту критика, он читал план на `0a1337273cf35b9c2ec165c76c3c6270bd0b252b`:
`FETCH_HEAD`, удалённая ветка и HEAD draft PR #342 совпали; `main` был
`70cd3c19f98faac79974fd9b5cc258976acf1a92`, HEAD его ветки — `661165b`.
Гайдлайнер отдельно подтвердил текущие HEAD ветки и `main`; чтение документов и
отсутствие запуска кода — со слов критика. Worktree воркера 2 и полные политики не
проверены. Публичный PR сохраняет документацию, но ещё не слит.

## 2. Три вердикта

| Гейт | Результат и условия |
|---|---|
| **STORE — хранение ключа** | `HOLD`: на момент критики неизвестны целевая установка и границы доверия к `main`, workflow, Actions, будущему окружению и обходу защиты. Позже владелец подтвердил App в списке установок организации; фактические права этой установки ещё сверить. Отдельный environment — только кандидат; `.pem` не размещать до новой оценки. |
| **READ-ONLY TEST — проверка App** | `HOLD` до подтверждения установки, минимальных прав, защищённого кода и способа запуска. Сначала спроектировать тесты с фиктивными ответами, отказами и враждебным вводом; затем отдельно согласовать разовый реальный тест без записи данных. Критик их не выполнял. |
| **LIVE APPLY — применение изменений** | `HOLD`: первый Submit, edit→restore, гонка отзыва роли, повторы, существующий sync и версия Pages не доказаны. Отдельный успех по ключу не разрешит запись. |

Критик назвал три конкретных сценария: изменение доверенного workflow для утечки;
подмену action/tag или артефакта; исполнение вредного содержимого issue при доверенном
`GITHUB_REF`. Возможное усиление прав App расширяет ущерб от того же `.pem`. Меры для
будущего секретного job: проверенные полные SHA actions, изоляция зависимостей и
артефактов, трактовка issue как данных и минимальные права. Это требования к проекту,
а не подтверждение готовности. Вероятности и полная стоимость защиты не оценены.

По отчёту, `DELETE /installation/token` отзывает токен вызова, а не доказанно все
неизвестные токены. При подозрении на утечку кандидатный порядок: приостановить
затронутые установки, ротировать ключ и секрет, отозвать известные токены, расследовать
и восстановить доступ после проверки. Немедленное инвалидирование всех уже выданных
токенов заменой `.pem` не доказано; конкретный порядок — по документации GitHub
[1](https://docs.github.com/en/rest/apps/installations)
[2](https://docs.github.com/en/apps/maintaining-github-apps/suspending-a-github-app-installation).
Если ключ единственный, GitHub требует создать новый перед удалением старого
[3](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps#deleting-private-keys).
Инцидент или утечка не подтверждены; это не поручение менять настройки сейчас.

## 3. Что владелец может проверить без изменений

**Установка:** владелец подтвердил, что App есть в списке установленных в организации
`Timeline-Project-SC2`. Гайдлайнеру список установок через read-only `gh` вернул `403`;
членство и App через API он не проверял. Ранее показанные `Members: read` и
`No repositories` относились к экрану без видимого аккаунта; владелец сообщил, что
разрешения и репозиторный выбор не менял. Связь того кадра с организационной установкой
через API не проверялась. Для одного `Members` репозиторные права не выдавать. На
новом снимке виден существующий секрет репозитория и сообщение об отсутствии секретов
в показанном разделе окружения; значения не видны. Наличие ключа в других окружениях
или другом секрете этим не доказано. Имена и содержимое секретов сюда не заносить.

**Границы доверия:** read-only GitHub API на `main` показывает `protected: true`, но
доступный ruleset `BotsOverwrite` содержит только `creation`/`deletion`; два других
видимых ruleset нацелены на ветку `ClassicRule`, не `main`. Это не полная проверка
защиты: полный endpoint branch protection и политики Actions вернули `403`.

**Новые сведения владельца, 31.10.2026:**
- На снимке [Branches](https://github.com/Timeline-Project-SC2/Timeline-Project-SC2.github.io/settings/branches)
  классические правила в видимой области не показаны. Это не отменяет rulesets и не
  доказывает полную конфигурацию за пределами кадра.
- На снимке [Actions → General](https://github.com/Timeline-Project-SC2/Timeline-Project-SC2.github.io/settings/actions)
  выбраны `Allow all actions and reusable workflows` и `Require approval for first-time
  contributors`; глобальный `Require actions to be pinned to a full-length commit SHA`
  не отмечен. Срок хранения показан как 90 дней. На последующем кадре `Workflow
  permissions` установлен в `Read and write`; создание/одобрение PR через Actions
  не отмечено и показано неактивным, причина не установлена.
- Владелец сообщил о втором администраторе **репозитория**. Кто ещё имеет запись,
  роли организаций и доступ приложений не установлены; второй администратор репозитория
  не становится автоматически Owner организации и не получает права подачи заявки.

Фактические права каждой задачи зависят также от деклараций workflow/job, ограничений
организации и события. `GITHUB_TOKEN` — встроенный токен GitHub, не `.pem` App; он
может быть доступен action через контекст без явной передачи
[1](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).
Перед изменением default нужно проверить совместимость CI, sync и Pages: выдана
[read-only разведка A0-K2](ADM-ACCESS-TOKEN-AUDIT.md). Доверие ко второму
администратору и факт размещения `.pem` остаются открытыми, без имён и секретов.
Внешние fork PR по выбранной политике требуют запуска с одобрением только для первых
вкладчиков, а не для всех внешних участников; это относится к PR CI, не заявкам-issue.

Можно прислать кадр или описать выбранные настройки. Ключ, токены, пароли, содержимое
секретов и URL webhook не показывать. `github-pages` не доказывает защиту нового
окружения. Не менять правила, не создавать environment/секреты и не запускать тесты
при осмотре. Глобальный SHA-пиннинг способен сломать незафиксированные workflow;
наличие/покрытие actions.lock ещё не проверено. Не включать его до отдельной проверки
и согласования; существующий секрет не менять и не удалять.

## 4. Что дальше

Кандидат дальнейшего плана, не утверждённая настройка:

1. Уточнить доверенных управляющих репозиторием, затем защитить изменения `main`,
   workflow и выполняемого кода. Оба администратора входят в контур доверия, пока
   не показана более сильная граница. Правила для кода — не модерация каждой issue.
2. Отдельно спроектировать автоматического записывающего субъекта и его ограничения:
   простое `только через PR` может заблокировать автоматическую запись, а общий
   bypass или `Contents: write` не ограничивают украденный токен папкой данных.
3. Секретный job проектировать с выбранной `main`, проверенными SHA actions,
   изоляцией от недоверенного кода/артефактов и фиктивными тестами. Отдельный
   environment без reviewer на каждую заявку — кандидат, а не гарантия безопасности.
4. После независимой оценки отдельно согласовать размещение ключа и реальный
   read-only тест; они не снимают `HOLD` с автоматической записи. Синтетические
   проверки можно проектировать, но код требует контракта, границ файлов и критики.

Текущие Sheets, синхронизация, реальные данные и планетарный контур не меняются.
