## Что требуется владельцу

Увидеть конкретный путь «поля будущего редактора → текст issue → последующие
изменения» на существующих непланетарных именах полей. Значения должны быть
вымышленными, а фактические имена и типы — по данным и коду, не наугад. Отдельно
разобрать 7–8 и более заявок, забытые правки и идентификатор для доступа к своей issue.

Два правила уже выбраны: обычная заявка после проверок применяется автоматически,
без второй ручной модерации; если title/body изменили до записи, старую issue не
применять, исправление — новая issue. Отсутствие доказательства неизменности означает
остановку. Возможные новые варианты сравниваются, но не подменяют этих решений.

## Уточнение владельца: идентификатор своей issue

Владелец уточнил: он имел в виду не общий корень и не общий код для группы заявок,
а **свою issue у каждого администратора** и код-идентификатор конкретной issue,
которым можно поделиться. Ранее описанная группировка под общей опорной issue была
ошибочной трактовкой и не является выбранным направлением.

Предложенный код автоматически создаётся, может изменяться и храниться в браузере;
это несекретный идентификатор, не право на запись. Получив код, другой человек
сможет найти соответствующую публичную issue, если способ привязки заработает.
Код не доказывает автора, роль или порядок, а также не синхронизирует черновики.
Автор и активный Owner **организации** по-прежнему проверяются для каждой заявки.

Случайный код сам по себе не содержит номер issue. Возможны ссылка/код с номером
issue либо произвольный редактируемый код с общедоступным разрешением соответствия;
выбор, хранение и получение номера после Submit ещё не определены. При конфликте
или неоднозначном совпадении нельзя молча переходить к другой issue. Локальная
память одного браузера не является общей для других пользователей; смена кода в
панели не должна переписывать уже отправленную issue.

`Ctrl+F5` обычно не очищает cookie или localStorage; для предсказуемого сброса
понадобится отдельная команда, а браузер может удалить данные по своей политике.

Владелец уточнил, что хотел бы позволить другому администратору вносить данные в
чужую issue, и интересуется синхронизацией. Точный механизм не выбран. Существующее
правило сохраняется: если title/body изменили до записи, старую заявку не применять,
исправление — новая issue. Живая запись, права и настройки не включены.

## Чтение и возможное добавление данных

По [GitHub REST API](https://docs.github.com/en/rest/issues/issues#get-an-issue)
публичную issue можно читать без авторизации; REST поддерживает [CORS](https://docs.github.com/en/rest/using-the-rest-api/using-cors-and-jsonp-to-make-cross-origin-requests)
для браузера. HEAD тестовой #347 без явно заданного `Authorization` вернул `200` и
`Access-Control-Allow-Origin: *`; содержимое не выводилось. Среда показала лимит
`5000`, поэтому это не измерение анонимной квоты и не проверка реального браузера,
политики сайта или отсутствия промежуточной авторизации.

Кандидат: открыть известную issue, прочитать опубликованные данные и показать в
редакторе после проверки формата; не исполнять текст. Обновление показывает только
сохранённое на GitHub, не несохранённый черновик другого браузера. Начать с загрузки
по открытию и кнопки «Обновить»; частое опрашивание и «мгновенный общий документ» не
обещаны. По [лимитам GitHub](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
неавторизованным запросам обычно доступно 60 в час на IP, общий для пользователей.

Чтобы писать в чужую issue, случайного кода недостаточно: нужны GitHub-авторизация и
права соответствующего пользователя, а для применения — отдельная проверка Owner
организации. Вход в GitHub на другом домене не является готовой авторизацией нашего
статического редактора. Личные токены и ключи нельзя встраивать в страницу или issue.

Вариант по действующим правилам: B загружает данные issue A, меняет свою копию и
отправляет новую issue от своего имени. Это не записывает данные внутрь issue A и не
отменяет автоматически A; предложения A нельзя считать уже применённой базой, а
зависимые или пересекающиеся изменения надо проверить.
Вариант ближе к пожеланию: отдельный новый комментарий B как новая команда в issue A;
GitHub поддерживает [комментарии](https://docs.github.com/en/rest/issues/comments) и
событие [`issue_comment`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment).
Это изменение контракта, не выбранная реализация: проверять автора каждого комментария,
роль, правки, порядок и повторы, отличать сообщения бота; исправления комментарием
вместо новой issue требуют отдельного решения владельца. Отправка через GitHub может
потребовать ручной вставки текста; прямая отправка из редактора требует отдельно
спроектированной авторизации. Ни один вариант не устраняет блокеры очереди и записи.
