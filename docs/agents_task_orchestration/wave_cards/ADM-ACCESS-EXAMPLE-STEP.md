## Что требуется владельцу

Увидеть конкретный путь «поля будущего редактора → текст issue → последующие
изменения» на существующих непланетарных именах полей. Значения должны быть
вымышленными, а фактические имена и типы — по данным и коду, не наугад. Отдельно
разобрать 7–8 и более заявок, забытые правки, объединение в сессию и временный токен.

Два правила уже выбраны: обычная заявка после проверок применяется автоматически,
без второй ручной модерации; если title/body изменили до записи, старую issue не
применять, исправление — новая issue. Отсутствие доказательства неизменности означает
остановку. Возможные новые варианты сравниваются, но не подменяют этих решений.

## Предложение владельца: общий код сессии

Владелец предложил автоматически генерировать случайный код для любого пользователя,
показывать его в панели, разрешать изменить и передать другому администратору,
закреплять за конкретной issue и долго хранить в браузере. Это кандидат удобства, не
секрет и не право записи. Для общей сессии разных авторов группировка не должна
разделять их только по автору; при этом каждая отдельная заявка проходит проверку
своего автора и активного Owner **организации**.

Код может быть скопирован, изменён или потерян: он не доказывает автора, порядок,
зависимость и право записи. Чтобы по произвольному коду открывать конкретную issue,
потребуется обнаружить и сохранить соответствие; способ пока не выбран. Локальная
память одного браузера не является общим хранилищем для двух администраторов.
Изменение локального кода не должно переписывать уже отправленную issue.

`Ctrl+F5` или жёсткая перезагрузка страницы обычно не очищает cookie или localStorage;
для предсказуемого сброса понадобится отдельная команда, а браузер также может
удалить данные по своей политике. Место и срок хранения не выбраны.

Владелец не настаивает на числе issue, если это не создаст проблем GitHub и людям.
Рабочий выбор для дальнейшего проектирования: одна локальная корзина до отправки,
затем отдельная issue на каждую отправку; общий код позволяет группировать заявки
разных администраторов. Первую заявку можно рассматривать как опорную для перехода,
не создавая дополнительную служебную issue только ради сессии. Способ надёжно найти
опорную issue по коду ещё нужно определить; при неоднозначности нельзя угадывать.

Код выдаётся и меняется локально, никакие issue или запросы не создаются автоматически
только из-за генерации кода. Каждая заявка — отдельная проверка автора и конфликта;
отправленный title/body не редактируется для нового изменения. Автоматическое
применение после проверок по-прежнему без второй модерации, но живая запись на HOLD.
Число issue само по себе не доказывает нагрузку; учитывать уведомления, лимиты API,
избегать лишних запусков и бесконтрольных повторов. Статусный комментарий не доказывает
запись и не заменяет состояние. Это выбор направления, не готовая реализация.

Одну issue с командами в комментариях или общий изменяемый черновик нужно отдельно
проектировать: комментарии сейчас не команды. Общая метка не синхронизирует
черновики, не устраняет конфликты и не подтверждает, что чужая заявка относится к
сессии. Способ и частота получения состояния ещё не выбраны.
