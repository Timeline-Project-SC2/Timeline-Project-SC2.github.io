# Документация TIMELINE PROJECT — карта и правила

Этот файл — единственная точка входа в документацию. Здесь описано, **как
устроены документы**, где лежит нужный контекст и куда писать новое знание.

## 1. Паспорт этапа и пять типов данных

Каждый этап описан единым паспортом `plan.md` в `docs/stages/stage-NN/`
(гибридная модель консолидации): пять типов данных живут секциями одного
файла, отдельный файл регистра заводится только когда секция перерастает
~60 строк или самостоятельно цитируется.

| Секция паспорта / файл | Тип | Что внутри | Лимит |
|---|---|---|---|
| [Паспорта этапов](stages/README.md), секция плана | **ПЛАН** | цель, границы, вход/выход, артефакты, гейты, статус, журнал и исходный план-первоисточник | 200 строк на файл |
| Секция «Ошибки» или вынесенный `errors.md` | **ОШИБКИ** | ошибки проектирования и реализации: симптом → причина → урок → исправление | вынос при росте секции > ~60 строк |
| Секция «Баги» или вынесенный `bugs.md` | **БАГИ** | дефекты среды, выполнения, данных и нестыковки контрактов | то же |
| Секция «Решения» или вынесенный `decisions.md` | **РЕШЕНИЯ** | ADR-записи: ID, дата, решение, причина, альтернативы, источник | то же |
| Секция «TODO» или вынесенный `todo.md` | **TODO** | что работает, что в работе, что предстоит, что заблокировано | то же |
| `notes/*.md` | **ПРИЛОЖЕНИЕ** | детальные отчёты, замеры и исторические журналы по контексту | 200 строк |

`plan.md` — паспорт и единственная точка входа этапа. Паспорт ссылается
на приложения и вынесенные регистры, они — обратно на паспорт.

### Различие «ошибка» и «баг»

- **Ошибка** — неверное решение или реализация внутри этапа: регрессия,
  неверное допущение, пропущенный инвариант. Исправляется изменением кода или
  плана, урок остаётся в секции «Ошибки» паспорта этапа.
- **Баг** — сбой внешней среды или стыка: CI, GitHub Pages, песочница,
  Google Sheets, браузер, версии инструментов, рассинхронизация данных.
  Часто не зависит от кода этапа и повторяется в разных волнах.
- Повторяющиеся ошибки → [`registers/errors-systemic.md`](registers/errors-systemic.md)
  (без лимита размера). Повторяющиеся баги → `registers/bugs-*.md` по темам,
  каждый файл ≤ 200 строк.

### Как читать рабочие обозначения

Короткие обозначения нужны для ссылок на задачи и проверки, но не заменяют
понятного объяснения. При первом упоминании в отчёте или новом тексте пишите,
что означает термин, к чему он относится и почему это важно. Ссылка на
словарик не заменяет объяснение прямо в сообщении. Если нужна помощь владельца,
опишите варианты, последствия и свою рекомендацию без требования знать код.

| Слово или обозначение | Простое объяснение |
|---|---|
| **Задача / карточка** | Описание работы: что нужно сделать, зачем и как проверить результат. Буквы и цифры вроде `UP-1` — лишь её название. |
| **Ветка** | Отдельное место для подготовки изменений; сама по себе ещё не меняет основную версию проекта. |
| **`main`** | Основная версия проекта, в которую изменения попадают после согласованного объединения. |
| **PR** (*pull request*, запрос на изменение) | Предложение добавить подготовленные изменения в основную версию. Открытый PR ещё не означает, что изменения приняты или опубликованы. |
| **Слияние** (*merge*) | Добавление подготовленных изменений в основную версию проекта. |
| **CI** (*continuous integration*, автоматические проверки) | Проверки, которые запускает GitHub для изменений. Зелёный результат означает, что проверки завершились по заданным правилам; известные исключения могут оставаться неисправленными. |
| **Тест** | Автоматическая проверка конкретного поведения проекта. `pass` — прошёл, `fail` — не прошёл. |
| **`skip` / `todo`** | Пропущенная проверка / отмеченная как незавершённая. Их наличие само по себе не доказывает, что проверяемое поведение работает. |
| **TODO** | Список того, что ещё нужно сделать; это не отметка о завершённой работе. |
| **TAP** (*test anything protocol*) | Текстовый формат, в котором программа сообщает о результатах автоматических проверок. |
| **`N/A`** | «Не применимо» или «нет измеримого значения»: это не ноль и не успешная проверка. |
| **Карантин тестов** | Способ временно учитывать известные падения отдельно. Зелёный результат с карантином не означает, что эти проблемы исправлены; полный прогон остаётся важным. |
| **Страж тестов** | Скрипт, предназначенный для сверки результатов со списком известных падений. Его наличие само по себе не доказывает, что все нужные проверки были запущены. |
| **`test:raw`** | Запуск перечисленных тестов без исключений, добавленных карантином. Его результат нужно отличать от результата прогона со стражем. |
| **Фикстура** (*fixture*) | Подготовленный пример входных данных для проверки. Если заменить пример, может измениться и то, что именно проверяется. |
| **Эталон** (*golden*) | Заранее сохранённый ожидаемый результат для сравнения. Если он изменился, нужно объяснить причину, а не просто переписать его. |
| **Гейт** (*gate*) | Контрольное условие: что должно быть проверено или выполнено, прежде чем работа считается готовой. |
| **SSoT** (*single source of truth*) | Единый источник: место, где хранится основная актуальная версия сведения, а остальные документы на неё ссылаются. |
| **ADR** (*architecture decision record*) | Запись о решении: что выбрали, почему и какие варианты рассматривали. |
| **API** (*application programming interface*) | Правила, по которым одна часть программы может пользоваться возможностями другой. |
| **Сборка** | Подготовка файлов сайта к запуску или публикации. Успешная сборка не заменяет проверку того, как сайт выглядит и работает. |
| **Предпросмотр** (*preview*) | Временный просмотр подготовленной версии сайта до её принятия и публикации. |
| **`DPR`** (*device pixel ratio*) | Плотность изображения экрана: сколько физических пикселей приходится на один условный пиксель интерфейса. Влияет на проверку отображения на разных устройствах. |
| **`LOD`** (*level of detail*, уровень детализации) | Способ показывать близкие объекты подробнее, а далёкие проще, чтобы сайт не тормозил. |
| **Юбка горизонта** | Продолжение поверхности вокруг видимого участка карты, которое заполняет дальний горизонт. |
| **`A-17`** | Обозначение замечания и связанных проверок: переход к соседнему участку должен соответствовать окружающей местности и подписям. |
| **`m.14`** | Название одного измерения качества: насколько совпадают подробное и упрощённое представления одного участка рельефа. |
| **`W23`** | Рабочая метка отдельной задачи о детализации удалённой местности; сама метка не означает, что решение принято или работа выполнена. |
| **`UP-1` / `UP-1-review`** | Названия задания об упрощении проекта, документов и тестов и карточки его проверки. |

Названия конкретных задач и измерений локальны для проекта; при обсуждении
нужны их смысл и ссылка на источник. Подробнее: [карточка `UP-1`](agents_task_orchestration/wave_cards/UP-1.md),
[описание `A-17`](stages/stage-08/notes/audit-a16-a18-checkpoints.md),
[заметка о `m.14` и `W23`](stages/stage-08/notes/w28-field-results.md).
Словарь о мире проекта и планетных данных — отдельно в [приложении к плану](plan/appendices.md).

## 3. Правила ведения

1. **Один файл — один контекст.** Не более 200 строк; если контекст больше,
   добавляйте под-файл в `notes/` с именем по смыслу, а не по дате.
2. **Заголовок и навигация.** У каждого файла есть H1 и строка «Назад» на
   паспорт этапа или индекс. Новые файлы ссылаются на источники.
3. **Без дублей.** Одно число, правило или решение живёт в одном месте
   (SSoT). Остальные документы ссылаются, а не копируют.
4. **Регистры обновляются в том же PR,** что и работа. Закрытый пункт TODO
   переносится в «Работает» с датой и ссылкой на PR.
5. **Проверка перед PR.** `npm run verify:docs` (он же шаг CI) проверяет лимит
   200 строк, ровно один `H1`, лестницу заголовков без прыжков, отсутствие
   битых относительных ссылок и якорей, а также файлов-сирот без входящих
   ссылок.
6. **Ошибки не прячутся.** Откат, регрессия и неверная гипотеза фиксируются
   в секции «Ошибки» паспорта этапа с уроком; если ошибка повторилась — в систематический регистр.
7. **Ссылки обязательны.** PR, коммит, файл кода, замер и решение — со
   ссылкой. Если ссылки нет, пункт считается недоказанным.
8. **Язык — русский.** Тексты, заголовки и комментарии.

## 4. Жизненный цикл записи

```text
идея/требование → секция паспорта plan.md (границы и гейт)
   → секция «Решения» паспорта (выбранный вариант)
   → выполнение → секции «Баги» / «Ошибки» паспорта (что сломалось)
   → секция TODO паспорта (что работает, что осталось)
   → notes/ (замеры и подробности); секция >~60 строк выносится в файл
```

Если этап завершён, `plan.md` получает статус «завершён», а незакрытые
пункты переезжают в `todo.md` следующего этапа или в общий
[`registers/todo.md`](registers/todo.md).

## 5. Проверка

```bash
python3 tools/check_docs.py      # лимит строк, H1, битые ссылки
npm run verify:docs              # то же через npm
```

CI выполняет проверку в каждом PR. Исключение по размеру только одно —
[`registers/errors-systemic.md`](registers/errors-systemic.md).
