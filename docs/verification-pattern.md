# Паттерн проверок: где какой гейт и почему локальный цикл раздувается

> Назад: [документация](README.md) · [работа с ИИ-агентами](ai-workflow.md) ·
> [карта репозитория](handoff/repo-zoom-and-rules.md) · [быстрый гейт](../tools/check_fast.mjs)
>
> **Адресат этого документа — исполнитель (воркер) и QA-роль `rc-04`.**
> Для Гайдлайнера оркестратора (`rc-07`) ничего не меняется: действует правило О-5
> ([`agents_task_orchestration/waves/protocol.md`](agents_task_orchestration/waves/protocol.md)),
> он не читает и не запускает код, тесты и сборки, и `check:fast` его исключением **не**
> становится. Исключение в О-5 по-прежнему одно — `npm run verify:docs`.

Документ отвечает на один вопрос: **какую проверку запускать и в каком порядке**, чтобы
локальная правка не стоила минуты ожидания. Второй смысл — объяснить, почему при
аккуратной на вид работе красных прогонов бывает много и как этого не допускать.

## 1. Устройство проверок в репозитории (факт на 10.11.2026)

Проверки разделены на слои по **цене запуска** и по **охвату**. Разрыв в цене —
два порядка, и он определяет весь локальный цикл.

| Слой | Команда | Время | Что видит | Что НЕ видит |
|---|---|---|---|---|
| Стык импортов и синтаксис | `node tools/check_fast.mjs` | **≈ 3 с** на 50 файлов | несуществующий экспорт и путь импорта в `src/`, `site/`, `tests/`, `tools/` | имена экспортов `node:*`, поведение |
| Типы | `npm run typecheck` (`tsc --noEmit`) | **≈ 1.2 с** | `src/**`, `site/**`, `tools/*.ts` по строгим флагам | `tests/**`: каталог не входит в `tsconfig.json` |
| Линт | `npm run lint` (`eslint site src tools tests`) | **≈ 8 с** | обращение к необъявленной переменной (`no-undef`), включая `tests/**` и `tools/**` | имена экспортов, типы |
| Один тест-файл | `node --test tests/<имя>.test.mjs` | **≈ 1 с** | поведение этого файла | остальные файлы |
| Все тесты (тест-поток) | `node --test --test-reporter=tap <список из test:raw>` | **≈ 71 с**, 614 тестов | поведение набора, 8 известных падений этапа 8 | — |
| Страж карантина | `npm test` (`tools/check_test_baseline.mjs`) | **≈ 135 с** | два прогона: целостность реестра + применение карантина | — |
| Сборка публикации | `npm run build` | **≈ 3 с** | что сайт собирается в `.publish/` | поведение тестов |
| Документация | `npm run verify:docs` | **≈ 0.4 с** | лимит 200 строк, H1, битые ссылки | — |

Вывод: «долгие проверки» — это **только прогон тестов**. Всё остальное укладывается
в 15 секунд. Поэтому удлиняют цикл не гейты, а то, что дешёвые гейты не покрывают
стык `tests/ → src/`.

## 2. Дыра, из-за которой локальный цикл раздувается

`tsconfig.json` включает `src`, `site`, `tools/*.ts`. Каталог `tests/` — вне проверки
типов; ESLint проверяет там одно правило `no-undef`, а имена экспортов не проверяет
никакой прибор. Эффект (воспроизведено 10.11.2026):

- фальшивый импорт `import { nothingHere } from '../src/atlas/sector-areas-contract.ts'`
  проходит `npm run typecheck` **и** `npm run lint` без замечаний, а `node --test` падает
  через 110–570 мс с `SyntaxError: does not provide an export named`;
- единственная дешёвая проверка, способная поймать выдуманное имя, — запуск кода,
  самый дорогой шаг.

Отсюда наблюдаемый рисунок: 12 подряд красных проб при 0 потерь в репозитории —
0.1–0.5 с на прогон, но полный раунд на исправление. Это не «плохой код», а
**отсутствующий быстрый гейт**.

## 3. Быстрый гейт `npm run check:fast`

`tools/check_fast.mjs` собирает каждый выбранный файл через `esbuild` в памяти
(`bundle`, `write: false`) и **не исполняет** его: отсутствующий экспорт — ошибка сборки.

```bash
node tools/check_fast.mjs                        # изменённые файлы: рабочее дерево + diff базы
node tools/check_fast.mjs --base origin/main     # явная база, если локальной main нет
node tools/check_fast.mjs --probe tests/x.test.mjs
node tools/check_fast.mjs --probe src/atlas/x.ts
node tools/check_fast.mjs --all                  # список scripts["test:raw"] + сам гейт
node tools/check_fast.mjs --probe tests/x.test.mjs --run   # плюс прогон теста
```

Через `npm` аргументы передаются **только с разделителем** `--`:
`npm run check:fast -- --probe tests/x.test.mjs`. Форма без `--` до скрипта не доходит
(`npm` забирает флаг себе).

Что именно проверяется в каждом режиме:

| Режим | Стык импортов | Типы (`tsc --noEmit`) | Линт (eslint) | Тесты |
|---|---|---|---|---|
| изменённые файлы (по умолчанию) | да | да | да, только по выбранным | по `--run` |
| `--probe tests/*.mjs` | да | **нет** — файл вне `include` `tsconfig.json`, гейт печатает «НЕ ПРОВЕРЯЛОСЬ» | да | по `--run` |
| `--probe src/*.ts` | да | да | да | по `--run` |
| `--all` | да | для `tests/**` и `.mjs` не покрыто: печатается отдельной строкой с перечнем; `tsc` при этом выполняется, если в наборе есть покрытые файлы | да, 50 файлов | по `--run` |

**Область `--all` — точная:** список тест-файлов из `scripts["test:raw"]` (`package.json`,
единственный источник, правило карточки `CI-2`) плюс сам `tools/check_fast.mjs`. Это
**не все тесты репозитория**. Файлы вне `test:raw` гейт не сканирует: он знает и печатает
один такой случай (`tests/sector-admin-edit.test.mjs` из `npm run test:sector-admin-edit`),
а полный перечень вести не берётся — за него отвечает `test:raw`.

**Смешанный набор.** Наличие файлов вне `include` `tsconfig.json` (`tests/**`, `.mjs`, JS при
`allowJs: false`) **не отключает** проектный `tsc --noEmit`: он выполняется всегда, когда в
наборе есть хотя бы один покрытый файл, а непокрытые перечисляются отдельной строкой
«типы: не покрыты проверкой типов (N) — …». Если покрытых файлов нет вовсе, печатается
«типы: НЕ ПРОВЕРЯЛОСЬ — в наборе нет файлов, попадающих в include tsconfig.json».

**Покрытие проверок считается по правилам, а не по каталогу.** Типы выполняются только
для файлов, попадающих в `include` `tsconfig.json` (`src/**/*.ts`, `site/**/*.ts`,
`tools/*.ts`, `vite.config.mts`); при `allowJs: false` файлы `.js`, `.mjs`, `.cjs` не
типизируются вовсе. Линт выполняется только для путей, у которых есть блок с правилами в
`eslint.config.mjs` (`site/**/*.js|ts`, `src/**/*.ts`, `tools/**/*.mjs`, `tests/**/*.mjs|js`);
для остальных ESLint молча возвращает `0`, ничего не проверив. Оба случая печатаются как
«НЕ ПРОВЕРЯЛОСЬ» / «без правил» и **не попадают** в список проверенного.

**`--all --run` — это не `npm test`.** Запуск идёт напрямую, без карантинного стража:
восемь известных падений этапа 8 остаются падениями, прогон идёт с
`--test-concurrency=1`. Зелёный `--run` не доказывает зелёный набор.

Коды возврата различают три разных состояния, потому что «не смог проверить» нельзя
выдавать за «чисто»:

- `0` — проверено и чисто; либо проверять нечего, и это **явно** напечатано (`ПРОПУСК`);
- `1` — найдены проблемы (стык, типы, линт, тесты);
- `2` — проверить **невозможно**: нет Git, не найдена база для diff, нет `node_modules`
  (`tsc`/`eslint`/`esbuild`), неизвестный флаг, `--probe` без значения, файл не найден.

Отчёт всегда перечисляет, что было проверено, и какие пути остались вне зоны, чтобы
«зелёный» нельзя было прочитать шире, чем он есть.

## 4. Правило локального цикла (исполнитель и `rc-04`)

1. **Пишу пробу или тест файлом, а не inline-heredoc.** Проба — это `tests/<имя>.test.mjs`;
   правка строки — `edit_file`, а не перепечатка десятикилобайтного скрипта.
2. **Сразу `npm run check:fast -- --probe <файл>`.** Красный стык импортов → чиню имя или
   путь. Помню оговорку: для `tests/**` гейт **не** проверяет типы (см. таблицу §3).
3. **Имя символа не угадываю, а смотрю:** `grep -n '^export' src/atlas/<модуль>.ts`
   (это действие исполнителя; Гайдлайнер по О-5 такого не делает и получает факт
   спецификацией поиска через воркера).
4. **Прогон `node --test <файл>`** — только когда стык зелёный: он проверяет поведение,
   а не имена.
5. **Полный `npm test` (страж, ≈ 135 с) и `npm run build`** — один раз перед отчётом и
   перед пушем, а не после каждой правки.
6. **Фикстуры — билдерами контракта того контура, в котором работаешь.** Для областей
   сектора это `emptySectorAreasDoc`, `createArea`, `createPair` и т. п.; для другого
   модуля набор свой. Это пример, а не универсальное правило: литерал «по памяти» падает
   на валидации контракта, и виновата фикстура, а не валидатор.
7. **Shell-дисциплина:** heredoc `<<'EOF'` всегда с новой строки; переменные окружения —
   отдельной командой или через `env VAR=… cmd`, никогда не «доклеенные» к предыдущей
   (`sed -i … node file.mjs` превращается в `sed: can't read node`); после `done`
   цикла — перевод строки, а не `done git clone …` (это `syntax error`).
8. **`ls`, `grep`, `diff` с ненулевым кодом — не ошибка исполнения.** Отсутствующий путь
   и отсутствие совпадений дают `exit 1` по смыслу; в статистике такие строки красные,
   но поломки в них нет.

## 5. Пределы гейта (что он честно не проверяет)

- **Имена экспортов `node:*`.** `esbuild` собирает с `external: ['node:*']`, поэтому
  импорт несуществующего имени из `node:fs` проходит гейт зелёным и падает в рантайме.
- **Динамические импорты** с вычисляемым путём, `require` в CJS, условные `exports`
  и различия Node/browser.
- **AssemblyScript** (`src/planet/assembly/**`): декораторы `@inline`/`@fastMath` не
  парсятся esbuild — гейт отказывается с `exit 2` в любом режиме. Путь канонизируется
  перед проверкой: `./`, `.` и `..` внутри репозитория, двойные и обратные слэши дают один
  и тот же результат; путь, выходящий за корень (`../x.ts`, `/etc/passwd`), отклоняется
  отдельным сообщением. Контур проверяет `npm run check:planet-core`.
- **Типы тестов.** Полноценная проверка `checkJs` по `tests/**` не включена: прогон даёт
  373 замечания, из них 343 в существующих тестах. Это отдельная карточка, а не
  побочный эффект гейта.
- **Поведение.** Гейт отвечает «сходится ли стык», а не «правильно ли считается».
- **CI.** Шаг в `.github/workflows/check.yml` не добавлен: гейт локальный, CI по-прежнему
  выполняет типы, линт, стража карантина и сборку.
