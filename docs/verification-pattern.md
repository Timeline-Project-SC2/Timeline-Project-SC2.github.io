# Паттерн проверок: где какой гейт и почему локальный цикл раздувается

> Назад: [документация](README.md) · [работа с ИИ-агентами](ai-workflow.md) ·
> [карта репозитория](handoff/repo-zoom-and-rules.md) · [быстрый гейт](../tools/check_fast.mjs)

Документ отвечает на один вопрос: **какую проверку запускать и в каком порядке**, чтобы
локальная правка не стоила минуты ожидания. Второй смысл — объяснить, почему при
аккуратной на вид работе красных прогонов бывает много и как этого не допускать.

## 1. Устройство проверок в репозитории (факт на 10.11.2026)

Проверки разделены на слои по **цене запуска** и по **охвату**. Разрыв в цене —
два порядка, и он определяет весь локальный цикл.

| Слой | Команда | Время | Что видит | Что НЕ видит |
|---|---|---|---|---|
| Стык импортов и синтаксис проб | `node tools/check_fast.mjs` (`npm run check:fast`) | **≈ 3.5 с** на 50 файлов | несуществующий экспорт, кривой путь импорта, синтаксис, типы, `no-undef` | поведение: тест ещё не запускался |
| Типы | `npm run typecheck` (`tsc --noEmit`) | **≈ 1.2 с** | `src/**`, `site/**`, `tools/*.ts` по строгим флагам `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` | `tests/**`: каталог не входит в `tsconfig.json` |
| Линт | `npm run lint` (`eslint site src tools tests`) | **≈ 8 с** | обращение к необъявленной переменной (`no-undef`), включая `tests/**` и `tools/**` | имена экспортов, типы |
| Один тест-файл | `node --test tests/<имя>.test.mjs` | **≈ 1 с** | поведение этого файла | остальные файлы |
| Все тесты (тест-поток) | `node --test --test-reporter=tap <список из test:raw>` | **≈ 71 с**, 607 тестов | поведение всего набора, 8 известных падений этапа 8 | — |
| Страж карантина | `node tools/check_test_baseline.mjs` (`npm test`) | **≈ 135 с** | два прогона: целостность реестра падений + применение карантина | — |
| Сборка публикации | `npm run build` | **≈ 3 с** (после правки: `prebuild` гоняет `sector-admin-edit`) | что сайт собирается в `.publish/` | поведение тестов |
| Документация | `npm run verify:docs` | **≈ 0.4 с** | лимит 200 строк, H1, битые ссылки | — |

Вывод: «долгие проверки» — это **только прогон тестов**. Всё остальное укладывается
в 15 секунд. Поэтому удлиняют цикл не гейты, а то, что дешёвые гейты не покрывают
стык `tests/ → src/`.

## 2. Дыра, из-за которой локальный цикл раздувается

`tsconfig.json` включает `src`, `site`, `tools/*.ts`. Каталог `tests/` — вне проверки
типов; ESLint проверяет там одно правило `no-undef`, а имена экспортов не проверяет
никакой прибор. Практический эффект, воспроизведено 10.11.2026 на пробе из 12 правок:

- фальшивый импорт `import { nothingHere } from '../src/atlas/sector-areas-contract.ts'`
  проходит `npm run typecheck` **и** `npm run lint` без замечаний (обе команды зелёные),
  а `node --test` падает через 110–570 мс с `SyntaxError: does not provide an export named`;
- то есть единственная дешёвая проверка, которая способна поймать выдуманное имя, —
  это запуск кода, самый дорогой шаг.

Отсюда наблюдаемый рисунок: 12 подряд красных проб при 0 потерь в репозитории —
0.1–0.5 с на прогон, но полный раунд на исправление. Это не «плохой код», а
**отсутствующий быстрый гейт**.

## 3. Ответ: быстрый гейт `npm run check:fast`

`tools/check_fast.mjs` собирает каждый тест/инструмент через `esbuild` в памяти
(`bundle`, `write: false`) и **не исполняет** его. Сборка резолвит импорты, поэтому
отсутствующий экспорт — это ошибка сборки, видна за доли секунды:

```bash
node tools/check_fast.mjs --probe tests/sector-areas.test.mjs   # моя проба/тест
node tools/check_fast.mjs                                       # изменённые файлы (git)
node tools/check_fast.mjs --all                                 # все тесты и инструменты
node tools/check_fast.mjs --probe tests/foo.test.mjs --run      # плюс запустить сам тест
```

Порядок по цене в самом гейте: стык импортов → типы (`tsc`) → линт только по
затронутым файлам → (по флагу `--run`) прогон только затронутых тестов. Список
тест-файлов гейт не ведёт свой: единственный источник — `scripts["test:raw"]`
(правило карточки `CI-2`, как у стража карантина). Код возврата: `0` — чисто,
`1` — проблема, `2` — ошибка окружения.

## 4. Правило локального цикла (рабочий порядок)

1. **Пишу пробу или тест файлом, а не inline-heredoc.** Проба — это `tests/<имя>.test.mjs`;
   правка строки — это `edit_file`, а не перепечатка десятикилобайтного скрипта.
2. **Сразу `npm run check:fast --probe <файл>`.** Красный стык импортов → чиню имя или
   путь; `tsc` и `eslint` дают типы и опечатки. Это секунды, а не минуты.
3. **Имя символа не угадываю, а смотрю:** `grep -n '^export' src/atlas/<модуль>.ts`.
   Дешевле любого падения и не требует запуска.
4. **Прогон `node --test <файл>`** — только когда стык зелёный. Он проверяет поведение,
   а не имена.
5. **Полный `npm test` (страж, ≈ 135 с) и `npm run build`** — один раз перед отчётом и
   перед пушем, а не после каждой правки.
6. **Фикстуры — только билдерами контракта** (`emptySectorAreasDoc`, `createArea`,
   `createPair`, …). Литерал «по памяти» падает на валидации `parseSectorAreas` и даёт
   красный раунд при правильном валидаторе — виноват не код, а фикстура.
7. **Shell-дисциплина:** heredoc `<<'EOF'` всегда с новой строки; переменные окружения —
   отдельной командой или через `env VAR=… cmd`, никогда не «доклеенные» к предыдущей
   (`sed -i … node file.mjs` превращается в `sed: can't read node`); после `done`
   цикла — перевод строки, а не `done git clone …` (это `syntax error`).
8. **`ls`, `grep`, `diff` с ненулевым кодом — не ошибка исполнения.** Отсутствующий путь
   и отсутствие совпадений дают `exit 1` по своему смыслу; в статистике такие строки
   красные, но поломки в них нет.

## 5. Что теперь закрыто автоматически, а что осталось за человеком

- Стык `tests/ → src/` — быстрый гейт (сборка через `esbuild`) плюс `no-undef` в ESLint.
- Типы тестов как таковых (полноценный `tsc` по `tests/**`) **не** включены: проверено
  10.11.2026, что такой прогон (`tsconfig` с `include: tests/**/*.mjs`, `checkJs`)
  даёт 373 замечания, из них 343 — в существующих тестах (нестрогие фикстуры, `any`
  в помощниках). Это отдельная работа, а не побочный эффект гейта: её нужно вести
  карточкой по образцу `CI-1`/`CI-2`, а не включать в `tsconfig.json` вслепую.
- Поведение по-прежнему доказывает только прогон тестов. Быстрый гейт его не заменяет:
  он отвечает «сходится ли стык», а не «правильно ли считается».
