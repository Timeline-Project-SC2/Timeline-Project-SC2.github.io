## 1. Видео за 30 секунд

Автор год работал в режиме «дал промпт — подождал — посмотрел результат» и
показывает, почему результат ломается уже после слов агента «готово, всё
работает». Лекарство — не более сильный промпт, а пайплайн из пяти вещей,
которых не хватает большинству: **опрос → план и спецификация → тесты до
кода → оркестратор → изолированные ветки**. Сильная модель планирует и
проверяет, исполнители пишут код в отдельных копиях проекта, а факт
готовности подтверждают запущенные тесты, а не слова агента. В конце —
реклама VibeForge (среда, собирающая пайплайн в одном окне); для этого
проекта она не нужна: тот же контур уже дают Git, PR и `check.yml`.

## 2. Четыре ошибки обычного вайбкодинга

| № | Ошибка из видео | Что происходит | Цена именно здесь |
|---|---|---|---|
| 1 | Промпт без деталей | Агент сам решает, что и как делать; критериев «готово» нет | Правка не того маршрута (`/`, `/sector/`, `/planet-globe/`), выдуманные числа вместо SSoT гайдлайнера |
| 2 | Контекст только в чате | По мере диалога агент забывает задачу и дрейфует | Расхождение с инвариантами `И-*`, контрактом планет и доменным `AGENTS.md` |
| 3 | Проверка после кода | «Готово, всё работает» — вежливость, а не факт; ошибку находит владелец | Красный `check.yml`, регрессия видна только на опубликованном сайте |
| 4 | Один агент, нет workflow | Всё последовательно, медленно, правки в одной папке | Параллельные агенты трут общие файлы (`sector-scene.ts`, `styles.css`, `atlas-shell.html`) |

Отдельно в видео разобран частный случай ошибки 3: **тесты после кода не
работают**. Агент пишет их под уже сделанную реализацию, они зелёные
всегда и проверяют не то, что хотел владелец, а то, что придумал агент.

## 3. Пять правил (ядро методики)

1. **Сначала вопросы, не код.** Даже короткий промпт обрастает деталями из
   ответов владельца; без ответов агент додумывает молча.
2. **План и специфика живут в файле, а не в чате.** Файл переживает потерю
   контекста, новую сессию и смену модели; чат — нет.
3. **Тест — это контракт, а не пожелание.** Не «сделай авторизацию», а
   «верный пароль → токен, неверный → 401, три неверных → блокировка».
   Вход → ожидаемый выход, без двусмысленности.
4. **«Готово» = вывод команд, а не фраза.** Зелёный прогон показан, красный
   означает «не готово»; владельцу не нужно лезть в код за агента.
5. **Параллельность — только с изоляцией и владельцами файлов.** У каждой
   подзадачи своя копия/ветка, свой список файлов и свои критерии приёмки;
   сильная модель раздаёт и проверяет, а не пишет всё сама.

## 4. Пайплайн «от и до» для TIMELINE PROJECT

### Шаг 0. Контур сохранения (до любой правки)

Проверить ветку (`git branch --show-current`, не `main`), чистоту
(`git status --short`), среду Node 24 / Python 3.12 и `npm ci`. Первый
содержательный коммит — сразу с `git push`, дальше пуш после каждого
логического шага (подробно — §6 корневого `AGENTS.md`). В Arena одна
сессия уже равна одной ветке: чужие ветки не создавать.

### Шаг 1. Опрос (агент спрашивает первым)

До плана агент задаёт вопросы и ждёт ответов. Минимальный чек-лист здесь:
цель и явное «не цель»; маршрут и домен (какой `AGENTS.md` — `site/`,
`src/`, `tools/`); источник чисел и данных (гайдлайнер, `data/*.csv`,
контракт, а не «на глаз»); затрагиваемые инварианты и общие файлы; чем
проверяем (какие тесты и верификаторы из шага 3); что принимает владелец
глазами. Если ответ меняет объём — объём переписывается до кода, а не
выясняется на приёмке.

### Шаг 2. План и спецификация (файл, а не чат)

Куда писать — по размеру задачи: малая — план и критерии прямо в описание
PR; этапная — `docs/stages/*/plan.md` + запись в `decisions.md`; волна —
карточка в [`wave_cards/`](agents_task_orchestration/wave_cards/) с
`OWNED_FILES`/`FORBIDDEN_FILES`. Спецификация фиксирует: входы и выходы,
границы («не трогаем»), контракт символов и чисел (только из SSoT),
критерии готовности по пунктам и риски. Каждый пункт плана обязан
отвечать на вопрос «каким тестом это проверяется» — пункт без теста
возвращается на доработку плана.

### Шаг 3. Тесты до кода (сначала красные)

Для каждого пункта плана пишется тест, запускается, и фиксируется, что он
**красный по правильной причине** (нет функции/поведения, а не опечатка в
самом тесте). Красный вывод приводится в отчёте/PR — это доказательство,
что тест вообще что-то проверяет. Какой инструмент брать:

| Что меняем | Тест/гейт, который пишем или запускаем первым |
|---|---|
| Чистая логика TS (`src/atlas/*`, `src/local-map/*`) | `tests/<имя>.test.mjs` (`node --test`) и сразу строка в `npm test` в `package.json` |
| Контракт планет, Wasm-ядро | `npm run verify:contract`, `npm run check:planet-core`, `npm run verify:hashes` |
| Сектор: адрес, ядро, отказ от растра | `npm run verify:address`, `verify:sector-core`, `verify:no-raster` |
| Данные и синхронизация | `python3 tools/sync.py --strict`, `planet_generation.py validate`, `npm run test:py` |
| Публикация и маршруты | `npm run build`, `npm run verify:publish` |
| Типы, стиль, документация | `npm run typecheck`, `npm run lint`, `npm run verify:docs`, `git diff --check` |
| Визуал, WebGL, эффекты | Сборка + предпросмотр; тесты это не заменяют — финальная приёмка за владельцем |

### Шаг 4. Код (цикл до зелёного)

Агент пишет код малыми шагами и **после каждого изменения сам запускает
тесты**: упало — читает ошибку и чинит сам, а не зовёт владельца. Цикл
«написал → запустил → красное → починил → зелёное» и есть обратная связь,
которой нет в режиме «дал промпт и жду». Каждый зелёный шаг — коммит и
пуш. Остановка и вопрос владельцу — только если ошибка упирается в
нехватку решения, данных или доступа, а не в очередную красную строку.

### Шаг 5. Оркестратор и изолированные ветки (только если задачи независимы)

Применять, когда подзадачи не делят файлы (`Zero File Overlap`); регламент
уже есть: оркестратор `rc-07` ставит волну, критик `rc-08` ищет векторы
отказа, воркеры работают по
[`worker_instruction_on_splitwork.md`](agents_task_orchestration/worker_instruction_on_splitwork.md),
приёмку закрывает `rc-04`. Локально изоляция делается worktree:

```bash
git worktree add ../tl-<задача> -b agent/<задача> origin/main
# каждый агент: своя папка, своя ветка, свой PR; основная копия не трогается
git worktree list && git worktree remove ../tl-<задача>   # после слияния
```

Не применять, если файлы общие: волна `F` (сектор) идёт строго
последовательно именно потому, что `sector-scene.ts`,
`canvas-renderer.ts`, `styles.css` и `atlas-shell.html` нужны всем.
Оркестратор не пишет весь код сам: он режет план, задаёт пункты валидации
каждой подзадачи и принимает по тестам — так дорогая модель тратится на
решения, а не на рутину.

### Шаг 6. Приёмка (факт, а не вежливость)

Полный набор гейтов своего домена из шага 3 + зелёный `check.yml`,
обновлённые в том же PR `CHANGELOG.md`, статус в
[`handoff/status.md`](handoff/status.md) и регистры этапа. В описании PR:
что сделано, чем проверено (с числами прогонов) и что **не** проверено
(например, WebGL2 на реальном GPU, визуал). Слияние — только по правилам
`AGENTS.md` и после визуальной приёмки владельца, если менялся интерфейс.

## 5. Готовые промпты (копировать как есть)

Четыре первых — из видео, с подстановкой под этот репозиторий:

> **Опрос:** «Прежде чем делать, задай мне уточняющие вопросы по задаче:
> цель и не-цель, маршрут, доменный AGENTS.md, источник чисел, чем
> проверяем. Код не пиши, пока я не отвечу».

> **План:** «Составь план и спецификацию на основе моих ответов и запиши
> в файл по правилам docs/README.md: входы, выходы, границы, критерии
> готовности по пунктам. У каждого пункта укажи, каким тестом он
> проверяется».

> **Тесты:** «Прежде чем писать код, составь тесты по спецификации для
> каждого пункта плана: что проверяем, какой вход, какой ожидаемый
> результат. Запусти их и убедись, что они красные, и покажи вывод».

> **Код:** «Теперь пиши код, пока все тесты не станут зелёными. После
> каждого изменения запускай тесты сам. Если упало, читай ошибку и чини,
> а не проси меня. Коммит и пуш после каждого зелёного шага».

> **Приёмка:** «Покажи доказательства, а не вывод “готово”: команды,
> числа прогонов, что красное и почему, что не проверено. Обнови
> CHANGELOG и статус, остановись перед слиянием».

## 6. Что в проекте уже есть, а что усилить

| Звено видео | Состояние здесь | Что делать |
|---|---|---|
| План/спека в файлах | Закрыто: SSoT `AGENTS.md`, планы этапов, карточки волн, `HANDOFF` | Не плодить новые форматы; опрос шага 1 — единственное недостающее звено для малых задач |
| Тесты и CI | Сильно: 35 файлов в `tests/`, верификаторы, матрица `check.yml` | Держать правило «тест до кода» и красный прогон в отчёте |
| Тесты подключены к прогону | Частично: в `npm test` 30 из 35 файлов; вне его `faction-net`, `place-types`, `sector-bounds`, `sector-overlays` (`travel-planner` запускается в CI отдельно) | Новый тест в том же коммите подключать в `package.json` или явно в CI; список вне прогона — разобрать отдельной задачей |
| Оркестратор и роли | Закрыто: `Tri-Agent Wave`, карточки `rc-01…rc-08`, `OWNED_FILES` | Использовать как есть; VibeForge и новые оркестраторы не внедрять без решения владельца |
| Изоляция | Ветки+PR и запрет записи в общие файлы; worktree не описан | Worktree — по шагу 5 для локальных мультиагентных запусков; в Arena изоляцию даёт сама сессия |

## 7. Когда задача считается готовой

- [ ] На вопросы шага 1 есть ответы; план и специфика лежат в файле.
- [ ] У каждого пункта плана был красный тест до кода, сейчас он зелёный.
- [ ] Агент сам гонял тесты в цикле; в отчёте — команды и числа, не слова.
- [ ] Гейты домена и `check.yml` зелёные; известные чужие падения названы явно.
- [ ] Коммиты запушены, `CHANGELOG`/`HANDOFF`/регистры обновлены в том же PR.
- [ ] Непроверенное (визуал, WebGL, данные) честно перечислено; приёмка владельца получена, если нужен глаз.
