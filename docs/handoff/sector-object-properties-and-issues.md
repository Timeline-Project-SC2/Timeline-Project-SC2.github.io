# Передача: свойства объектов сектора и заявка на изменения

## Задача владельца

Добавить редактирование описания и остальных собственных свойств установленных
точек карты. Поля, логически принадлежащие другим сущностям/редакторам, не
дублировать. Подготовить переход от разведки форматов к реализации и оформлению
изменений для GitHub Issues. Этот отчёт не означает готовую отправку или применение.

Критерий: первый администратор создаёт/правит объект, изменения публикуются;
второй на следующий день видит объект на `/sector/`, открывает редактор и
продолжает работу без чужой сессии, черновика и передачи файла. Публикация не
должна терять структуру редактирования. Личная история Undo не обязана переноситься.

Проверено по `src/atlas/data-loader.ts`, `sector-bounds.ts` и заголовкам CSV.
Отдельная точка POI определяется отсутствием system_id при наличии координат.
В карточке системы/места `dossier-card.ts` выводит `note` как «Описание» с

привязки к исходному полю нельзя без явного адаптера.

Загрузчик смешивает источники: исходные записи атласа, строки CSV, overrides.

## FACT: источник истины и опасность простого PR с CSV

`data/sources.json` связывает systems, places, planet_generation и faction_details
с опубликованными Google Sheets. `tools/sync.py` получает внешние данные;

## Уточнения владельца при продолжении

- Постоянные утверждённые правки должны храниться во внутренних файлах
  репозитория, как слой поправок поверх данных Sheets. Конкретная схема слоя,
  его применение и политика конфликтов ещё требуют проработки; sync не должен
  стирать принятые изменения.
- Первый срез свойств систем, отдельных POI и мест внутри систем: название,
  тип, фракция, описание и ссылка на источник. Фракция редактируется в
  свойствах объекта. ID не редактируется; координаты и связь с системой —
  отдельные операции, а не произвольные поля свойств.
- Не добавлять заранее текстовое описание в модель границы, гало или
  туманности. Владелец подтвердил отделение от предполагаемого модуля
  интерактивной информации, который может, но не обязан описывать объекты
  через иерархию и цепочки. Его контракт и реализация здесь не установлены.
- Цель подачи — заявка в GitHub с автоматическим применением через ранее
  созданное приложение, не ручная выгрузка как замена. Согласно прежней
  [передаче ADM-ACCESS](../agents_task_orchestration/wave_cards/ADM-ACCESS-ORCHESTRATOR-HANDOFF.md),
  целевой сценарий также включает узкий Cloudflare Worker для GitHub-входа и
  создания issue от имени пользователя, проверку активного Owner организации
  и автоматическое применение/публикацию без второй ручной модерации. Это
  целевая схема, не свидетельство готовности: ранее подтверждён только ручной
  read-only тест App; текущие настройки, живое применение и публикация не
  проверены. Нельзя включать живую запись, менять настройки или создавать
  реальные заявки под видом локальной разработки. См. также
  [выбор Worker и блокеры](../agents_task_orchestration/wave_cards/ADM-ACCESS-CF-WORKER-AUTH.md).

## Слой поправок: чтение

`src/atlas/sector-property-overlay.ts` — ядро слоя; загрузчик читает пустой по
умолчанию `data/sector-property-overlay.json` в обычном и inline путях, после
legacy overrides. При недоступном или некорректном слое загрузка карты
останавливается с сообщением. Редактор, sync и заявки пока не записывают слой.
Схема: `{version: 1, changes: [{dataset, recordId, field, base, value}]}`;
`dataset` — systems/places, поле — одно из пяти согласованных. `base` хранит
сырое значение upstream или `null` для отсутствующей колонки, `value` — строка,
включая явную пустую. Отсутствие поправки означает отсутствие записи в слое;
`null` не означает очистку. Принимается только целый корректный документ;
повтор одного поля и неизвестные поля запрещены.

Ядро сопоставляет только точный `system_id` / `ID` в своём dataset, не имя;
пропавшую или неоднозначную запись не создаёт и сообщает о проблеме. Если
upstream изменился после утверждения, утверждённая поправка пока применяется,
но возвращается `upstream_changed` для рассмотрения. Это поведение — кандидат
для интеграции, не реализация проверки новых заявок и не автоматическая запись.
Проверка автора, конфликтов заявки и предметная валидация на применении
остаются отдельными этапами. Формат заявки и отправка Issue против
фиктивного GitHub API сделаны и описаны в
[заявке на свойства точек](sector-property-issue-submission.md); живая
отправка, применение и публикация по-прежнему `HOLD`. В док добавлен локальный экран
«Свойства точек»: собственная история, сравнение и снимки raw/effective, без
записи и отправки. Черновик можно скачать и повторно загрузить только при
совпадении raw/effective и отсутствии других правок. `baseRevision` — отпечаток
сверенных входов сборки или null; это не доказательство публикации или прав.
Сборка создаёт манифест байтов скопированных входов; обычный загрузчик сверяет
байты своих HTTP-ответов, inline не получает отпечаток; при расхождении метка
не выдаётся. Предпросмотр и его подтверждение локальны и после правки
сбрасываются. Тесты покрывают inline, обычную загрузку и очистку после legacy
overrides; реальный браузер и публичная карточка с непустым слоем не
проверены. При сбое загрузки systems/places CSV загрузка карты также
останавливается; видимое управление проблемами upstream не реализовано.

## Проверки следующей реализации

- Админ A меняет описание → источник/сборка → админ B без localStorage видит
  его в публичной карточке и может снова изменить в редакторе.
- Очистка описания не восстанавливает устаревший fallback.
- Переименование не меняет ID и не ломает связи; одинаковые ID в разных
  datasets не смешиваются. Переносы строк, кавычки CSV, кириллица и HTML безопасны.
- Разные поля одного объекта допускают независимые правки; одно поле на
  устаревшей базе даёт конфликт. Удалённая запись не воскресает молча.
- Следующий sync не теряет принятую правку; повтор запроса не дублирует запись.
- Показывать отдельно: черновик / запрос отправлен / применён к источнику /
  опубликован. Не маркировать результат как опубликованный по факту создания issue.
