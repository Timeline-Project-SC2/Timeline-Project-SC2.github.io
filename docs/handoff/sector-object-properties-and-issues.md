# Передача: свойства объектов сектора и заявка на изменения

## Задача владельца

Добавить редактирование описания и остальных собственных свойств установленных
точек карты. Поля, логически принадлежащие другим сущностям/редакторам, не
дублировать. Подготовить переход от разведки форматов к реализации и оформлению
изменений для GitHub Issues. Этот отчёт не означает готовую отправку или применение.

Критерий: первый администратор создаёт/правит объект, изменения публикуются;
второй на следующий день видит объект на `/sector/`, открывает редактор и
продолжает работу без чужой сессии, черновика и передачи файла. Публикация не
должна терять структуру редактирования. Личная история Undo не обязана переноситься.

## FACT: где сейчас находятся данные точек

| Сущность | Исходные поля | Представление для карты |
|---|---|---|
| Система | `data/systems.csv`: `system_id,name,type,x,y,faction,net_id,description,source_url` | `SystemRecord`: `id,name,systemType,coord,primaryFaction,note,sourceUrl,net_id` |
| Место/планета/отдельная точка | `data/places.csv`: `ID,name,type,system_id,x,y,faction,description,source_url` | `mapPlaceRow`: `id,name,placeTypes,systemId,coord,pointOfInterest,note,sourceUrl` |
| Граница/гало/туманность | `data/sector-bounds.json` | `id,kind,label,points,style,blink?,soft?`; поля description сейчас нет |
| Область | `data/sector-areas.json` | отдельная модель областей, состояний, групп и пар |

Проверено по `src/atlas/data-loader.ts`, `sector-bounds.ts` и заголовкам CSV.
Отдельная точка POI определяется отсутствием system_id при наличии координат.
В карточке системы/места `dossier-card.ts` выводит `note` как «Описание» с
экранированием HTML. Добавлять параллельное поле description в runtime вместо
привязки к исходному полю нельзя без явного адаптера.

Загрузчик смешивает источники: исходные записи атласа, строки CSV, overrides.
`mergeSystemTypes` применяет note из CSV только при непустом значении;
`resolveSystem` применяет override.description также только при truthy.
**Риск:** очистка описания не равнозначна отсутствию правки и может вернуть
старое описание из другого источника. Проверить все пути загрузки, включая inline.

## FACT: источник истины и опасность простого PR с CSV

`data/sources.json` связывает systems, places, planet_generation и faction_details
с опубликованными Google Sheets. `tools/sync.py` получает внешние данные;
`.github/workflows/sync.yml` запускается по расписанию раз в шесть часов,
вручную и repository_dispatch, затем записывает изменённые data/.
Прямая правка CSV в GitHub без решения о приоритете источников рискует быть
перезаписана очередной синхронизацией. Не обещать постоянное изменение сайта
только потому, что issue создана или CSV однажды попал в Pages.
Живые Sheets, sync, OAuth/App/секреты в этой разведке не проверялись и не менялись.

## Предлагаемый следующий шаг — не принятое архитектурное решение

1. Зафиксировать, какие «точки» входят в первый срез: системы и отдельные POI;
   места внутри систем включать через тот же адаптер places, но не путать
   свойства записи с отдельным контрактом генерации планеты.
2. Составить разрешённую матрицу полей по типу. Начать с description и
   source_url, затем name/type. Идентификаторы read-only; координаты —
   пространственные операции, system_id — связь, faction — согласовать с
   политическими слоями. Не показывать редактор произвольного JSON.
3. Для каждого поля сохранить исходный raw-снимок и эффективное значение
   отдельно; определить семантику null, пустой строки и удаления значения.
4. Сделать локальную сессию свойств, Undo/Redo, просмотр карточки «до/после».
   Общий список «Системы», его порядок и положение не перестраивать.
5. До отправки выбрать постоянный источник записи: либо применять в Sheets
   с последующим sync, либо согласовать версионированный слой поправок поверх
   upstream. Это решение владельца; в этом отчёте ни один вариант не утверждён.
6. Собирать версионированный пакет изменений: тип пакета, идентификатор,
   база/хэш источника, массив полевых изменений, человекочитаемое резюме.
   Существующий формат полевого конфликта можно использовать внутри пакета,
   но он не покрывает создание/удаление объектов и геометрию сам по себе.
7. Сначала офлайн-выгрузка/проверка пакета, затем подтверждение в UI и
   авторизованная отправка в GitHub. Не вводить токены в браузерный код/issue.
   Issue — запрос; запись в источник и публикация имеют отдельные статусы.
8. Перед применением проверить роль, схему/allowlist, базу, конфликты и
   идемпотентность. Повтор/правка текста issue не должны повторно применять
   устаревший запрос. Не создавать новую процессную систему ради этого шага.

## Проверки следующей реализации

- Админ A меняет описание → источник/сборка → админ B без localStorage видит
  его в публичной карточке и может снова изменить в редакторе.
- Очистка описания не восстанавливает устаревший fallback.
- Переименование не меняет ID и не ломает связи; одинаковые ID в разных
  datasets не смешиваются. Переносы строк, кавычки CSV, кириллица и HTML безопасны.
- Разные поля одного объекта допускают независимые правки; одно поле на
  устаревшей базе даёт конфликт. Удалённая запись не воскресает молча.
- Следующий sync не теряет принятую правку; повтор запроса не дублирует запись.
- Показывать отдельно: черновик / запрос отправлен / применён к источнику /
  опубликован. Не маркировать результат как опубликованный по факту создания issue.
