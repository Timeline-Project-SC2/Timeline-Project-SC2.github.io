# Локальное OAuth-ядро для заявки сектора

Статус: код ядра подключён к тестовому Worker'у и к редактору (кнопка
отправки), но **ничего не развёрнуто** и живых запросов к GitHub не было.
Порядок отправки и защита от дублей — в
[заявке на свойства точек](sector-property-issue-submission.md). Применение
правки и публикация по-прежнему `HOLD`.

- `src/issue-gateway/oauth-state.ts` создаёт случайные state и PKCE S256, хранит хэш state и привязку к браузеру, ограничивает жизнь пятью минутами и требует атомарных операций создания и извлечения. Проверка извлекает запись даже при неверной привязке: повторное использование не допускается.
- `src/issue-gateway/github-oauth.ts` содержит обмен одноразового кода и запрос `/user` через внедрённый транспорт; тесты используют фиктивные ответы. Это идентификация, не проверка членства Owner, разрешения на Issue или права на применение. Указание repository ID не доказывает ограничения токена.
- GitHub возвращает одноразовый code в query callback URL. Передавать его в редактор нельзя. До развёртывания необходимо доказать отсутствие утечек в логах платформы, истории и Referer; задать безопасные cookie, CSRF и точный callback, защитить секреты, ограничить запросы и обеспечить уничтожение временных данных и токенов.
- `src/issue-gateway/oauth-sql-store.ts` реализует отдельный адаптер SQLite: вставка без перезаписи, извлечение и удаление одной SQL-командой, ограниченная очистка истёкших записей. Тесты используют локальный SQLite и конкурентные вызовы, но не доказывают работу в Cloudflare или между отдельными инстансами. Нужны интеграция, плановая очистка, routing одного ключа в один объект и проверка гонок в реальном runtime. Обычный Workers KV имеет eventual consistency и не подходит для атомарного одноразового извлечения; возможный вариант — SQLite-backed Durable Objects. См. [Cloudflare KV](https://developers.cloudflare.com/kv/concepts/how-kv-works/) и [Durable Objects storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).
- `src/issue-gateway/property-conflicts.ts` проверяет локальный черновик против переданных исходного и текущего снимков: сверяет отпечаток с исходным, raw и видимые значения по каждому полю. Изменения других полей допускаются как кандидат; повтор после изменения и смена upstream дают конфликт. Пропущенный или неоднозначный объект, неверная база и повреждённый черновик дают неопределённый результат. Функция не устанавливает происхождение снимков, не проверяет историю промежуточных изменений и не авторизует запись; предупреждения локальной валидации требуют отдельного решения.
- Ещё нужны доказанные доверенные версии данных, формат заявки, проверка Owner и содержимого, обработка повторов и неизвестного результата создания Issue, сериализация применения, восстановление и отдельное подтверждение публикации. Выбор и настройка реального контура требуют владельца; создание Issue не подтверждает применение или публикацию.
