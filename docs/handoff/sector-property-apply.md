# Применение заявки к слою поправок

Статус: **чистое ядро, ничего не записывает**. Живое применение, коммит
App'ом и публикация — `HOLD`. Писатель слоя — следующий шаг после приватной
цепочки v2 и отдельного разрешения владельца.

Назад: [контракт и отправка](sector-property-issue-submission.md) ·
[свойства объектов](sector-object-properties-and-issues.md) · [индекс](../README.md).

## Что решает модуль

`src/issue-gateway/property-apply.ts` — `planPropertyApply(...)` по заявке v2,
доверенной базе, текущим данным и текущему слою возвращает:

| Результат | Значение |
|---|---|
| `apply` | новый документ слоя, добавленные поправки, ключ идемпотентности |
| `already_applied` | нужное значение уже стоит; писать нечего |
| `refused` | `invalid_request`, `base_mismatch`, `record_missing`, `conflict`, `indeterminate` |

Порядок проверок: форма → база → запись → значение. Отказ называет первопричину.

## Правила, закреплённые тестами

1. Сопоставление только по ID внутри своего набора данных; дубль ID не
   выбирает «первую подходящую» запись.
2. База обязательна: отпечаток и значение «до» должны совпасть с доверенной базой.
3. Конфликт не перезаписывается: третье значение в источнике или слое даёт `conflict`.
4. Повтор идемпотентен по ключу `issue:<repositoryId>:<issueNumber>:<requestId>`.
5. Слой расширяется, прежние поправки сохраняются; входные документы не мутируются.
6. Отсутствие колонки и явная пустая строка различаются.
7. Слой приоритетнее источника; расхождение после sync видно как `upstream_changed`.

## Чего это не делает

- Не проверяет роль Owner; `tools/issue_owner_check.mjs` остаётся отдельным
  свидетельством и не подключён к применению.
- Не доказывает свежесть данных: базу и текущие строки передаёт вызывающий код.
- Не пишет слой, не создаёт коммит и не публикует сайт.
- Не решает спор двух авторов по времени отправки.
- Не является транзакцией: окно между проверкой и записью должен закрывать
  применитель через `expectedHeadOid` и повторную проверку HEAD.

## Проверки

`tests/issue-property-apply.test.mjs` — применение, повтор, база, конфликты,
независимые поля, пропавшая/неоднозначная запись, разные наборы, пустые ID,
отсутствие колонки, невалидные входы, ключ, журнал, два автора, чистота
входов, чтение слоя загрузчиком и сохранение правки после синхронизации.

## Что должен сделать применитель (не реализовано)

1. Взять доверенную базу и текущие данные из развёрнутого сайта.
2. Проверить роль Owner и авторство заявки внутри тела, созданного ботом.
3. Вычислить план; при отказе — комментарий в Issue с причиной, без записи.
4. Записать слой и журнал ключей одним коммитом с `expectedHeadOid`; при
   расхождении HEAD — остановиться и перечитать состояние.
5. Отдельно подтвердить публикацию Pages. Успешный коммит не равен «сайт обновлён».
