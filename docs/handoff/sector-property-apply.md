## Что решает модуль

`src/issue-gateway/property-apply.ts` — функция `planPropertyApply(...)`,
которая по четырём входам возвращает одно из трёх:

| Вход | Что это |
|---|---|
| заявка | разобранная `readPacket(...)`, не текст Issue |
| доверенная база | отпечаток входов + значения полей на момент правки |
| текущие данные | строки `systems`/`places` с их колонками (`system_id`, `ID`) |
| текущий слой | документ `data/sector-property-overlay.json` |

| Результат | Значение |
|---|---|
| `apply` | новый документ слоя, список добавленных поправок, ключ идемпотентности |
| `already_applied` | в слое уже стоит нужное значение: писать нечего |
| `refused` | `invalid_request`, `base_mismatch`, `record_missing`, `conflict`, `indeterminate` |

Порядок проверок: форма → база → запись → значение. Поэтому отказ называет
первопричину, а не следствие.

## Правила, которые закреплены тестами

1. **Совпадение только по ID** внутри своего набора данных. Одинаковый ID в
   `systems` и `places` — разные записи; пустой ID не индексируется; дубль
   ID в источнике даёт `record_missing`, а не «первая подходящая».
2. **База обязательна.** Отпечаток заявки должен совпасть с доверенным, а
   значение «до» — с доверенным значением поля. Иначе `base_mismatch`:
   правка на устаревшей базе не применяется.
3. **Конфликт не перезаписывается.** Если в источнике или в слое значение
   уже стало третьим — `conflict`. Две независимые правки разных полей
   одного объекта проходят; две правки одного поля одним объектом — нет.
4. **Повтор идемпотентен.** Ключ `issue:<repositoryId>:<issueNumber>:<requestId>`
   не зависит от текста Issue: правка заголовка или тела не создаёт новую
   работу, а второй автор с другим Issue — создаёт другой ключ.
5. **Слой расширяется, а не перезаписывается.** Прежние поправки
   сохраняются, новые сортируются по набору, ID и полю — диффы читаемые.
   Входные документы не мутируются.
6. **Отсутствие колонки ≠ пустая строка.** Если колонки нет, а «до» было
   пустым значением, это конфликт, а не тихая перезапись.
7. **Слой приоритетнее источника.** После синхронизации Sheets утверждённое
   значение сохраняется, а расхождение возвращается как `upstream_changed`
   через обычный загрузчик (`applyPropertyOverlay`) — проверено отдельным
   тестом на реальном коде карты.

## Чего это не делает

- **Не проверяет роль.** Owner-проверка (`tools/issue_owner_check.mjs`)
  остаётся отдельным свидетельством; модуль не принимает решение о правах.
- **Не доказывает свежесть данных.** Отпечаток базы и текущие строки
  передаёт вызывающий код; модуль не ходит в сеть и не читает файлы.
- **Не пишет слой.** Запись, коммит `expectedHeadOid`, обновление журнала
  обработанных ключей и публикация — следующий шаг, который потребует
  отдельного подтверждения владельца.
- **Не решает спор по времени.** При двух заявках на одно поле выигрывает
  та, что применена первой; «доказанно отправленная раньше» этим модулем не
  устанавливается.
- **Не является транзакцией.** Между проверкой и записью остаётся окно:
  закрывать его должен применитель через `expectedHeadOid` и повторную
  проверку HEAD.

## Проверки

`tests/issue-property-apply.test.mjs` — 16 проверок: применение, повтор,
база, конфликты (источник и слой), независимые поля, пропавшая и
неоднозначная запись, разные наборы данных, пустые ID, отсутствие колонки,
невалидные входы, ключ идемпотентности, журнал, два автора на одном поле,
чистота входов, чтение нового слоя загрузчиком карты и сохранение правки
после синхронизации.

Полный прогон: `npm test` — 955 pass / 0 fail / 8 skip; `tsc`, `eslint`,
`build`, `verify:publish`, `verify:docs`, `test:py` — зелёные.

## Что должен сделать применитель (не реализовано)

1. Взять **доверенную базу и текущие данные из развёрнутого сайта**, а не из
   локальной сессии: иначе отпечаток ничего не значит.
2. Проверить роль Owner и что автором Issue является тот же пользователь.
3. Вычислить план (`planPropertyApply`) и при отказе — комментарий в Issue с
   причиной, без записи.
4. Записать слой и журнал ключей **одним коммитом** с `expectedHeadOid`;
   при расхождении HEAD — остановиться и перечитать состояние.
5. Отдельно подтвердить публикацию Pages для нужной версии. Успешный коммит
   не равен «сайт обновлён».
