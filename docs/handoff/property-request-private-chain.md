# Передача: приватная цепочка заявок — что решено и где шероховатости

Отчёт о сессии, где обсуждалась **конечная схема** подачи заявок на правку свойств точек: публичный сайт + закрытый репозиторий только под заявки, любой желающий может оставить заявку, применяет только Owner организации.

Это отчёт **о решениях и размышлениях**, не о коде: кода в этой сессии почти не было. Код, который уже существует, живёт в `main`, а не в обсуждавшейся ветке.

Назад: [статус и состояние](status-and-state.md) · [индекс документации](../README.md) · [путь игрока для админов](../admins/property-request-player-path.md) · [свойства точек и заявки](sector-object-properties-and-issues.md).

## 1. Главное предупреждение следующему агенту

Ветка `arena/aaae4083-timeline-project-sc2-github-io` отведена от `0612994` и **не содержит** работу, слитую позже в `main` (`property-apply.ts`, `property-issue-contract.ts`, защита слоя в `tools/sync.py`, `docs/handoff/sector-property-apply.md`). Перед любой работой над кодом:

```
git fetch origin main && git merge origin/main
```

либо ветку от `origin/main`. Иначе агент будет писать код поверх состояния недельной давности и заново решать решённое.

## 2. Что решено в этой сессии

| Вопрос | Решение | Обоснование |
|---|---|---|
| Кто может оставить заявку | админ — всегда; **любой желающий** — через кнопку на сайте | требование владельца: «либо админ, либо любой желающий» |
| Кто одобряет | **только Owner организации**, в момент применения | прежнее правило, не отменялось |
| Где живут заявки | **второй, приватный репозиторий** только под Issue | основной репозиторий обязан остаться публичным: на этом стоит бесплатность GitHub Pages |
| Заявка = Issue? | да, но в закрытом репозитории | скрыть отдельную Issue в публичном репозитории нельзя |
| Кто создаёт Issue | **бот (GitHub App)**, не игрок | игрок не имеет доступа к закрытому репозиторию |
| Публичная Issue или скрытая | выбрано скрытое (вариант 2) | заявки видны только автору на сайте и владельцу в GitHub |
| Изменение своей заявки | **новая версия в той же нити**, не перезапись | перезапись после просмотра = подмена содержимого |
| Токен «править ту же Issue» | **отклонён** | GitHub не даёт токена на одну Issue; правка после отправки делает невозможным доказать, что одобрено именно применённое |
| Формат шапки заявки | кто / когда / что меняется, затем поля «было → стало» | требование владельца: админ должен считывать заявку с одного взгляда |

## 3. Что выяснено про GitHub (факты, проверенные по источникам)

- Настройка **Settings → Features → Issues → Collaborators only** (июнь 2026) пускает только роли **triage и выше**; обычный read — нет. Для организации «collaborator» = triage/write/maintain/admin.

  <https://docs.github.com/en/enterprise-server@3.20/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/disabling-issues>
- **Скрыть отдельную Issue в публичном репозитории нельзя.** Единственный способ — сделать приватным весь репозиторий. Официальный запрос на такую функцию открыт и не реализован.

  <https://github.com/orgs/community/discussions/206760>
- Вкладку Issues можно **спрятать** (снять галочку Features → Issues), но прямые ссылки и API продолжат работать. Это косметика, не приватность.
- Роль пользователя в репозитории читается через `GET /repos/{owner}/{repo}` → поле `permissions` (`admin`/`maintain`/`push`/`triage`/`pull`).
- Лимита открытых Issue от не-коллабораторов **пока нет**: он был заявлен, но на октябрь 2026 оставался в разработке.

  <https://github.blog/open-source/maintainers/how-pull-request-limits-are-cutting-down-the-noise/>

## 4. Что выяснено про Cloudflare (бесплатный план достаточен)

| Ресурс | Бесплатно | Нужно нам |
|---|---|---|
| Workers | 100 000 запросов/день, 10 мс процессора | десятки |
| Durable Objects (SQLite) | 100 000 запросов/день, 1 ГБ | `OAuthState` |
| Cron | 5 на аккаунт | 1 |

Наш `worker/wrangler.jsonc` использует `new_sqlite_classes` — попадает в бесплатный вариант, переезд не нужен. Главный риск — 10 мс процессора на запрос.

## 5. Разбор риска, который владелец считал защитой

Владелец предположил: «заявка не от админа с админскими данными будет отклонена на основе прав, подделать не получится». Это верно **только наполовину**, и различие принципиально:

| Угроза | Закрывает ли проверка прав |
|---|---|
| Чужой выдал себя за админа | да — номер пользователя не совпадёт |
| Подпись «одобрено владельцем» в тексте | да — проверка смотрит на номер, не на текст |
| Игрок предлагает **неверные** данные | **нет** |
| Игрок предлагает выгодные ему данные | **нет** |
| Спам и поток заявок | **нет** |

Вывод для следующего агента: проверка прав защищает личность, но **не содержание**. Смысл правки автоматически не проверяется и проверяться не будет — это решение владельца при ручном чтении.

## 6. Шероховатости и открытые вопросы

1. **Второй репозиторий и токен.** Сейчас Worker создаёт Issue **токеном пользователя** со scope `public_repo`. В приватный репозиторий с этим токеном не записать. Нужен выпуск токена GitHub App внутри Worker и приватный ключ App в секретах. Кода нет.
2. **Жёстко зашитый репозиторий.** `PROPERTY_REPOSITORY_ID = 1421259694` и `confirmRepository()` сверяют один номер. Для двух репозиториев нужен явный выбор цели.
3. **Автор станет ботом.** При создании через App автором Issue будет бот. Значит номер и логин человека обязаны попадать **внутрь заявки** и читаться оттуда, а не из полей GitHub. В контракте такого поля пока нет.
4. **Экрана «Мои заявки» нет.** В закрытом репозитории у игрока нет доступа, ссылку ему дать нельзя. Без экрана у игрока не будет обратной связи вообще.
5. **Лимит заявок.** Внешнего лимита нет, нужен свой счётчик открытых заявок на человека.
6. **Кнопка «Отложить»** (третье решение, кроме принять/отклонить) предложена, но **не подтверждена** владельцем. Меняет список статусов в [документе для админов](../admins/property-request-player-path.md).
7. **Причины отклонения** предложены таблицей; слово «обман» применимо только к подделке личности. Не утверждено.
8. **Уведомлений нет.** Почту не собираем намеренно; игрок узнаёт о решении, только открыв сайт.
9. **Публичная и приватная схемы расходятся в транспорте, не в контракте.** Это важно: переезд не выбрасывает работу по контракту и ядру применения.
