Бинарный кэш геометрии, бенчмарки и совместимость.

## Бинарный кэш

### 7. Бинарный кэш топологии v1

#### 7.1. Заголовок

Все числа little-endian независимо от хоста:

| Смещение | Тип | Значение |
|---:|---|---|
| 0..3 | bytes | `GEO\0` |
| 4..5 | `uint16` | format version = 1 |
| 6..7 | `uint16` | flags = 0 |
| 8..11 | `uint32` | endianness marker `0x01020304` |
| 12..15 | `uint32` | первые 32 бита SHA-256 канонического JSON метаданных |
| 16..19 | `uint32` | header length = 32 |
| 20..23 | `uint32` | payload length |
| 24..27 | `uint32` | CRC32C payload |
| 28..31 | `uint32` | `v` |

Канонический JSON имеет ровно отсортированные ключи
`{addressSchema, gridVersion, topologySchema, v}` без пробелов.

#### 7.2. Payload

Первые 32 байта payload — layout v1, `v`, `cellCount`, `triangleCount`,
`cellCornersLength`, `bodyIndex`, `chunkBlockSteps`, резерв. Далее секции в
фиксированном порядке, каждая выровнена до 4 байт:

1. `centers` (`Float32`)
2. `corners` (`Float32`)
3. `triangles` (`Uint32`)
4. `cellCornerStart` (`Uint32`)
5. `cellCorners` (`Uint32`)
6. `neighbors` (`Int32`)
7. `neighborCount` (`Uint8`)
8. `areas` (`Float32`)
9. `addrFace` (`Uint8`)
10. `addrI` (`Uint16`)
11. `addrJ` (`Uint16`)

Chunk-метаданные в payload не дублируются: они детерминированно
восстанавливаются из канонических адресов и топологии при загрузке.

На little-endian хостах секции копируются байтовыми блоками; на big-endian
используется поэлементный `DataView` fallback. CRC32C считается
slicing-by-4 таблицами и сверен с контрольным вектором
`crc32c("123456789") = 0xe3069283`.

#### 7.3. Поведение при ошибках

`deserializeGridCache(bytes, expectedMeta)` не бросает на битых данных. Он
возвращает `{ ok:false, reason }` при проблемах magic, версии, flags,
endianness marker, длины, `v`, `paramsHash`, CRC, границ секций или полной
валидации топологии.

`loadGridWithCache({ readCache, writeCache, rebuildGrid, expectedMeta })`:

- возвращает `{ grid, source:'cache' }` для валидного кэша;
- при miss/битом/старом кэше или ошибке чтения перестраивает сетку;
- после rebuild best-effort пишет новый бинарный кэш и не падает из-за квоты
  или ошибки записи;
- возвращает `{ grid, source:'rebuilt', reason }`.

Тестовый стенд и worker хранят этот формат в IndexedDB под новым префиксом
`gp-v1-bin:`. Старые structured-clone записи `gp-v0:` игнорируются.

### 8. Контракт данных Этапа 2

`tools/planet_generation.py`:

- новый дефолт `grid_version=goldberg-gp-v1`;
- явная историческая `goldberg-gp-v0` по-прежнему поддерживается валидатором;
- шум, география и пресеты пока остаются v0 до Этапа 4;
- golden `generation_key` для тестового профиля обновлён, потому что версия
  сетки входит в географический манифест:
  `PG1-Y6MQHGY72BADEFMKSV5KRH5B44`.

Живых профилей в `planet_generation` пока нет, поэтому миграция замороженных
ключей не требуется. Если позже появится профиль v0, смена его на v1 должна
идти новой ревизией, а не молчаливой заменой ключа.

## Бенч и совместимость

### 9. Bench и валидация

Команда:

```bash
node tools/bench_planet_stage3.mjs --v=128 --reps=3 --picks=1000
```

Результат в песочнице разработки (Node, медианы трёх повторов):

| Метрика v=128 | Значение |
|---|---:|
| Ячеек / треугольников | 163 842 / 327 680 |
| Build | 484,7 мс |
| Typed arrays | 19,70 МиБ |
| Chunk-ов | 200 |
| Ячеек в chunk-е: средн. / мин. / макс. | 819,2 / 496 / 1 024 |
| Угловой радиус chunk-а: средн. / макс. | 13,15° / 16,02° |
| Fast pick mean / p95 | 0,0207 / 0,0517 мс |
| Brute pick mean / p95 | 0,4707 / 0,5526 мс |
| Расхождений fast/brute на 1 000 направлений | 0 |
| Бинарный кэш | 19 988 652 байта |
| Serialize / deserialize | 305,3 / 366,6 мс |
| `validate().ok`, `validateChunks().ok` | true / true |

CI CPU-бенч относительно baseline 2026-10-20:

| v | Build было → стало | Typed memory было → стало |
|---:|---:|---:|
| 64 | 230,2 → 94,1 мс | 4,80 → 4,93 МиБ |
| 128 | 922,7 → 444,7 мс | 19,22 → 19,70 МиБ |
| 192 | 2 154,8 → 1 034,5 мс | 43,24 → 44,32 МиБ |

То есть build ускорился примерно в 2,1 раза, а рост типизированной памяти от
chunk-индексов составил 2,5% при разрешённом CI-пороге +30%.

Дополнительная проверка v=192: 420 chunk-ов, максимум 1 024 ячейки,
fast pick mean 0,0391 мс против 1,1049 мс полного перебора, расхождений нет.

Автоматические тесты:

- `tests/geodesic-grid.test.mjs` — адреса/обратный поиск, chunk-контракт,
  fast pick против brute force, каноническая плотность;
- `tests/planet-grid-cache.test.mjs` — заголовок/SHA/CRC, round-trip всех
  сериализуемых массивов, битый байт, старая версия, mismatch метаданных и
  ошибка чтения с rebuild;
- `tests/test_planet_generation.py` — дефолт v1, поддержка legacy v0, новый
  golden PG1 и весь прежний контракт;
- `tools/check_planet_spike.mjs` — прежняя проверка топологии/шумов/геометрии
  на новом ядре;
- CI `planet-perf` дополнительно запускает Stage 3 bench на v=128.

### 10. Совместимость и миграция

- Адреса `goldberg-gp-v0/...` не читаются parser-ом v1. Публичных замороженных
  ссылок и профилей на v0 нет; старые скриншоты и отчёт Этапа 1 остаются
  историческими.
- Числовые индексы ячеек изменились из-за chunk-упорядочивания. Это допустимо:
  индекс никогда не был публичным ID.
- Поля планеты считаются по непрерывному направлению центра, поэтому сама
  география не привязана к старому порядку. Порядок обхода может изменить
  только служебные хэши/очерёдность при равенствах, но не канонический адрес.
- Старый IndexedDB-кэш не мигрирует: новый префикс заставляет один раз
  перестроить сетку и записать бинарный v1.
- Публичная форма grid для спайка сохранена; `addrFace` сужен с `Uint16Array`
  до `Uint8Array`, значения и доступ по индексу не изменились.

### 11. Ограничения и следующий этап

- Node-выигрыш deserialize против build на v=128 умеренный (366,6 против
  484,7 мс), потому что загрузка честно проверяет CRC и всю топологию.
  Главный выигрыш формата — детерминированный переносимый контракт и быстрый
  отказ от битого кэша; браузерный выигрыш нужно подтвердить на устройствах.
- Chunk-и пока не уменьшают GPU-работу спайка: рендер всё ещё строит всю
  сферу. Этап 6 должен использовать диапазоны, bounding spheres и соседей для
  frustum/horizon culling и стыковки LOD.
- Для очень больших радиусов формула честно даёт большие v; предел полной
  сетки без chunk-стриминга остаётся решением Этапа 6 (D10).
- Следующий содержательный этап — Этап 4: поля/C100-soft на ядре v1 и
  перекалибровка пресетов под Землю v=128.
