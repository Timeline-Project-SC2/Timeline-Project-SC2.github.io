## 1. Зачем области действия

Модуль рисования границ должен быть **отдельным** и подключаемым к разным
геометриям: туманностям, границе сектора Копрулу, области вне сектора и
пограничному миру. Область действия (scope) — это маска/референс, а не
разбиение данных. Геометрия области остаётся в мировых координатах `0…10000`.

## 2. Два режима «окраса»

- **Свободный** — произвольный полигон/линия; scope подрезает/подсвечивает;
  адрес вычисляется справочно; пересечение scope допустимо с предупреждением.
- **Секториальный** — кисть снапится к ячейке текущего уровня через
  `prefixOf`/`rectOf` (`src/atlas/sector-address.ts`); адрес канонический;
  родитель — ячейка предыдущего тира; каскад по адресной иерархии.

Оба режима дают одну и ту же модель `Area`/`State`; режим хранится как
`source`/`snapMode` для журнала. Режим окраса — свойство инструмента, а не
область действия: scope можно выбрать и в свободном, и в секторном режиме.

## 3. Подключение существующих границ

- `data/sector-bounds.json`: `sector.outline` (Сектор Копрулу), `halo.dashed`,
  `nebula.lost-signals`, `nebula.fog-echos`. В v1 — read-only scope; правка
  исходных границ — отдельная версионируемая операция.
- `src/atlas/sector-bounds.ts`: `pointInPolygon`, `distanceToRing`,
  `smoothPolyline`, `smoothBoundaryAtMapEdge` — геометрия scope и hit-testing.
- `src/atlas/nebula-model.ts`: контур туманности можно взять как scope; мазки
  `NebulaBrushStroke` — это текстура, не семантическая граница; не смешивать.
- `src/atlas/sector-scene.ts`: добавить примитив `kind: 'brush'`; scope —
  производная маска, исходные границы не меняются.
- `src/atlas/sector-field.ts`: поле не зависит от кисти; достаточно 2D-оверлея.

Ядро кисти не импортирует field/renderer: оно потребляет интерфейс `Scope` и
возвращает `Area`/`State`. Адаптеры подключают существующие границы.

## 4. Модель области действия

```ts
type ScopeKind = 'free' | 'sector' | 'nebula' | 'outside' | 'border-world' | 'custom';
interface Scope {
  id: string;
  kind: ScopeKind;
  label: string;
  rings?: readonly Ring[];      // для polygon-скоупов
  predicate?: (x: number, y: number) => boolean; // для border-world
  source: string;               // 'sector-bounds.json', 'border-world', ...
  visibleFrom: number;
  visibleTo: number;
  style: { fill: string; stroke: string; dash: number[]; opacity: number };
}
```

- `Area.scopeId` — ссылка на scope; `Area.location` — `inside | outside |
  border | core | inner | outer | band`; `Area.distance` — для border-world;
  `Area.detail` — целое/перечисление.
- Scope может быть вложенным: туманность внутри сектора; «вне сектора» —
  дополнение сектора; пограничный мир пересекает границы.
- Кисть использует `isInside(x,y)` и клип при рендере; область может частично
  выходить за scope — это предупреждение, а не запрет.

## 5. Детализация «где именно объект»

Детализация — классификация области относительно scope, а не отдельная
геометрия:

- `core`, `inner`, `outer`, `border`, `outside`, `unknown`;
- для пограничного мира — полоса `b0…b3` по расстоянию до центральных систем;
- вычисляется из центра/геометрии и scope; админ может переопределить;
- хранится в `Area`/`State`, показывается в журнале, влияет на стиль;
- включается/выключается на scope; без неё объект просто «в scope».

## 6. Пограничный мир

Лорный аспект: область параметризуется расстоянием от конкретных систем,
обозначенных «центральными».

- `BorderWorld`: `centralSystemIds`, полосы `[0,r1)`, `[r1,r2)`, …,
  `bandAt(x,y)`, стиль и подпись на полосу.
- Центральные системы — из `data/systems.csv`; выбор админа; расстояние в
  мировых единицах/св.г.; пороги настраиваются.
- Это поле, а не фиксированный полигон: кисть может быть ограничена полосой;
  у области хранятся `distance` и `band`; рендер рисует полосы как фон.
- Расстояние — `min_i dist(p, c_i)`; для нескольких центральных систем дешево;
  для многих — пространственный индекс.
- Scope-предикат пересекается с сектором и туманностями; кисть клипается по
  предикату, а не по одному полигону.

## 7. Как это подключается к кисти

- Ядро: `sector-areas.ts` + `Scope`-адаптеры; UI: выбор scope, детализация,
  выбор центральных систем и полос; рендер: маска scope → области → состояния
  → анимации; журнал: scope, location, detail, distance, band.
- Свободный и секторный режимы — оба в v1; свободный по умолчанию.
- Существующие границы в v1 — read-only scope; редактирование исходников —
  отдельная задача.
- Пограничный мир — отдельный модуль-предикат; области остаются общими.

## 8. Валидация и тесты

- Scope: уникальный id, корректная геометрия/предикат, диапазон видимости,
  отсутствие циклов в ссылках; адаптер не мутирует исходные границы.
- Area: scope существует; `location` валиден; `distance` конечен; `band`
  существует; пересечение scope — предупреждение; секторный режим — адрес и
  родитель; свободный — адрес справочный.
- Border world: центральные системы существуют; полосы упорядочены и не
  пересекаются; `bandAt` детерминирован; производительность.
- Тесты: hit-testing scope, классификация detail, полосы border-world,
  cross-scope, адрес секторного режима, свободный режим.

3. Детализация и журнал; UI выбора scope.

5. Анимации, force-fill, публикация.

## 10. Открытые вопросы владельцу

1. Какие существующие границы редактируемые, а какие только scope? Рекомендация:
   в v1 только scope.
2. Пересечение scope: разрешать с предупреждением или запрещать? Рекомендация:
   разрешать с предупреждением.
3. Какие системы «центральные» для пограничного мира? Выбор владельца; данные
   в `data/systems.csv`.
4. Сколько полос и какие пороги? Рекомендация: 3–4, настраиваемо.
5. Набор значений детализации: `core/inner/outer/border/outside` достаточен?
6. Пограничный мир — scope или отдельный слой? Рекомендация: scope-предикат.
7. Править контур туманности кистью? Рекомендация: в v1 нет, только scope.
