## 1. Зачем области действия

Модуль рисования границ должен быть **отдельным** и подключаемым к разным
геометриям: туманностям, границе сектора Копрулу, области вне сектора.
Пограничный мир — не scope, а отдельный уровень систем (см. §6). Область
действия (scope) — это маска/референс, а не разбиение данных. Геометрия
области остаётся в мировых координатах `0…10000`.

## 2. Два режима «окраса»

- **Свободный** — произвольный полигон/линия; scope подрезает/подсвечивает;
  адрес вычисляется справочно; пересечение scope допустимо с предупреждением.
- **Секториальный** — кисть снапится к ячейке текущего уровня через
  `prefixOf`/`rectOf` (`src/atlas/sector-address.ts`); адрес канонический;
  родитель — ячейка предыдущего тира; каскад по адресной иерархии.

Оба режима дают одну и ту же модель `Area`/`State`; режим хранится как
`source`/`snapMode` для журнала. Режим окраса — свойство инструмента, а не
область действия: scope можно выбрать и в свободном, и в секторном режиме.

## 3. Подключение существующих границ

- `data/sector-bounds.json`: `sector.outline` (Сектор Копрулу), `halo.dashed`,
  `nebula.lost-signals`, `nebula.fog-echos`. Все существующие границы
  редактируемые (решение владельца); правка исходников — версионируемая
  операция с provenance, source vs derived.
- `src/atlas/sector-bounds.ts`: `pointInPolygon`, `distanceToRing`,
  `smoothPolyline`, `smoothBoundaryAtMapEdge` — геометрия scope и hit-testing.
- `src/atlas/nebula-model.ts`: контур туманности — отдельный вид границ, как
  сектор или гало; мазки `NebulaBrushStroke` — текстура, не семантическая
  граница; не смешивать. Модули «интерактивной» информации и
  системно-планетарный стратегический режим — отдельные модули, не scope.
- `src/atlas/sector-scene.ts`: добавить примитив `kind: 'brush'`; scope —
  производная маска, но исходники при редактировании сохраняются с историей.
- `src/atlas/sector-field.ts`: поле не зависит от кисти; достаточно 2D-оверлея.

Ядро кисти не импортирует field/renderer: оно потребляет интерфейс `Scope` и
возвращает `Area`/`State`. Адаптеры подключают существующие границы.

## 4. Модель области действия

```ts
type ScopeKind = 'free' | 'sector' | 'nebula' | 'outside' | 'custom';
interface Scope {
  id: string;
  kind: ScopeKind;
  label: string;
  rings?: readonly Ring[];      // для polygon-скоупов
  source: string;               // 'sector-bounds.json', 'nebula-model.ts', ...
  visibleFrom: number;
  visibleTo: number;
  style: { fill: string; stroke: string; dash: number[]; opacity: number };
}
interface ScopeRule {
  a: string;                    // id первого scope
  b: string;                    // id второго scope
  dominance: 'a' | 'b' | 'equal';
}
```

- `Area.scopeId` — ссылка на scope; `Area.location` — `inside | outside |
  border | core | band | unknown`; `Area.distance` и `Area.band` — для
  детализации пограничного мира, не для scope.
- Scope может быть вложенным: туманность внутри сектора; «вне сектора» —
  дополнение сектора.
- Пересечение scope разрешено; `ScopeRule` задаёт, кто главенствует (`a`, `b`)
  или «на равных» (`equal`). Без правила — предупреждение и безопасный
  режим «оба сохраняются».
- Кисть использует `isInside(x,y)` и клип при рендере; область может частично
  выходить за scope — это предупреждение, а не запрет.

## 5. Детализация «где именно объект»

Детализация — классификация области относительно scope, а не отдельная
геометрия. Рекомендуемый минимум:

- `inside` — внутри scope;
- `outside` — снаружи;
- `border` — у границы (в пределах порога);
- `core` — глубоко внутри (дальше порога от границы);
- `band` — для пограничного мира: полоса `b0…b3` по расстоянию до
  центральных систем;
- `unknown` — не вычислено.

`inner`/`outer` избыточны: `core`/`border`/`outside` уже задают глубину.
Детализация вычисляется из центра/геометрии и scope; админ может
переопределить; хранится в `Area`/`State`, показывается в журнале, влияет на
стиль; включается/выключается на scope; без неё объект просто «в scope».

## 6. Пограничный мир — уровень систем, не scope

Это формальное именование при достижении определённого расстояния от
«центральных» систем. Входит в редактор, но на уровне подробностей систем и их
созависимости, а не как ещё одна область действия кисти.

- `BorderWorld`: `centralSystemIds`, полосы `[0,r1)`, `[r1,r2)`, …,
  `bandAt(x,y)`, формальное имя/подпись на полосу.
- Первый тест: центральная — **Корхал** (`system_id: 1`, `5720, 6257`),
  пограничная — **Коло** (`system_id: 9`, `6180, 6739`). Расстояние между
  ними `≈ 666,3` мировых единиц (св.г.).
- Полосы — это интервалы расстояния от центральной системы. Для Корхал/Коло
  предлагаю 4 настраиваемые полосы: `core` `0…200`, `inner` `200…450`,
  `border` `450…700`, `outside` `>700`. Коло (`≈ 666`) попадает в `border`.
  Пороги — решение владельца, не жёсткий код.
- Расстояние — `min_i dist(p, c_i)`; для нескольких центральных систем дешево;
  для многих — пространственный индекс.
- Кисть может использовать `band` как детализацию области, но сам пограничный
  мир не является scope и не ограничивает геометрию.

## 7. Как это подключается к кисти

- Ядро: `sector-areas.ts` + `Scope`-адаптеры; UI: выбор scope, детализация,
  выбор центральных систем и полос; рендер: маска scope → области → состояния
  → анимации; журнал: scope, location, detail, distance, band.
- Свободный и секторный режимы — оба в v1; свободный по умолчанию.
- Все существующие границы редактируемые; правка исходников версионируется,
  source vs derived сохраняется; кисть не затирает историю молча.
- Пограничный мир — отдельный модуль на уровне систем; не scope; области могут
  использовать `band` для детализации.

## 8. Валидация и тесты

- Scope: уникальный id, корректная геометрия, диапазон видимости, отсутствие
  циклов в ссылках; адаптер не мутирует исходные границы без версионирования.
- Area: scope существует; `location` валиден; `distance` конечен; `band`
  существует; пересечение scope — предупреждение; `ScopeRule` определяет
  главенство/равенство; секторный режим — адрес и родитель; свободный — адрес
  справочный.
- Border world: центральные системы существуют; полосы упорядочены и не
  пересекаются; `bandAt` детерминирован; производительность.
- Все границы: source vs derived, provenance, история; кисть не теряет
  исходную геометрию при редактировании.
- Тесты: hit-testing scope, классификация detail, полосы border-world,
  cross-scope и dominance, адрес секторного режима, свободный режим.

## 9. Порядок работ

1. Scope-модуль и адаптеры к `sector-bounds.json`/`nebula-model.ts`; все
   границы редактируемые, source vs derived; тесты.
2. Пограничный мир на уровне систем: Корхал/Коло, полосы, `bandAt`; тесты.
3. Детализация (`inside/outside/border/core/band/unknown`) и журнал; UI scope.
4. Кисть в двух режимах; `ScopeRule` для пересечений; рендер состояний.
5. Анимации, force-fill, публикация.

## 10. Решения владельца и что осталось

Решено:

1. Все существующие границы редактируемые: сектор, гало, туманности.
2. Пересечение scope разрешено; выбор — кто главенствует или «на равных».
3. Пограничный мир — теория/функционал; первый тест: Корхал (центральная) и
   Коло (пограничная).
4. Пограничный мир — уровень систем и их созависимости, не scope.
5. Туманность — отдельный вид границ, как сектор или гало; модули
   «интерактивной» информации и системно-планетарный режим — отдельные модули.

Осталось уточнить:

- пороги полос для Корхал/Коло (предложение: `0…200`, `200…450`,
  `450…700`, `>700`; Коло ≈ 666 попадает в `border`);
- финальный набор детализации (предложение: `inside`, `outside`, `border`,
  `core`, `band`, `unknown`);
- как UI показывает `ScopeRule` «кто главенствует / на равных».
